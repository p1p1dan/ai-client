台账读出来的三条结论（本页三个维度的立论基础）

① 「对比太弱」不是正文的问题——正文 18.78 / 11.38 已经是 AAA 上限，亮色下 #100F0F 就是 Flexoki 的黑，没有更深的地方可去。 弱的是次要层：chat 目录里 text-muted-foreground 用了 104 处、text-foreground 只有 49 处—— 用户视野里大部分「字」（整条工具行、时间戳、耗时、状态、次级标题、引用块、脚注）都落在 4.48:1（暗）和 3.11~3.61:1（tool-arg）上。所以 D2 的动作在次要层，不在正文。

② 「没有区分度」有精确解释——用户气泡的底 card 对时间线底只有 1.027:1（亮），边框 primary/8 对底只有 1.111:1。 两个信号都在人眼可辨阈以下，等于气泡根本没画出来；再加上 D26 ④ 把 85% 宽度与右对齐也拿掉了，用户消息与助手消息就只剩「有没有圆角」这一个几乎看不见的差别。

③ 「太密集」是行高 1.5 用在中文上——1.5 是拉丁文正文的下限档。CJK 无升降部、字面率高，同一 line-height 下视觉上更挤； 再叠上段距只有 10px（= 0.44 行），段落之间几乎没有呼吸位。

出处依据（诚实标注）

行业量级锚点（本轮未在本机实测第三方产品，以下是公开实现与规范里的通行取值，只作量级参照）： @tailwindcss/typography 的 prose 长文基线是正文行高 1.75、段落上下 margin 1.25em、 li margin 0.5em；GitHub 的 markdown 样式是行高 1.5 + 段落 margin-bottom 16px（= 1em）； Material / HIG 正文普遍在 1.5 附近。也就是说：1.5 是「界面正文」的档，1.75 是「长文阅读」的档， 而聊天时间线在本项目里已经是长文场景。

CJK 修正：中文字形满格、无升降部，同一 line-height 的视觉行距比拉丁文更紧，通行做法是再放 0.1~0.2； 中文正文常见落点是 1.6~1.8。所以 D1-b 的 1.625 大致等效于拉丁文的 1.5（即「先补回中文欠的那一档」）， D1-c 的 1.75 才是真正的「宽松」。

字距不设变体：CJK 正文加 letter-spacing 会破坏字面节奏， design-system.md:489 已裁定正文 / UI 一律 0，本页三档全部保持 0，密度只从行高 / 段距 / 项距三个轴取。

D3-a：最省。但它只是把一条看不见的线变成看得见的线——区分度的来源仍然是「有没有框」这一个二值信号， 在一屏塞进三四个回合时，仍要靠扫描边框来找自己问过什么。收益上限较低，风险也最低。

D3-b：把助手也装进盒子，等于宣布「一切都是卡片」，反而让两边更像； 而且助手回复里本来就有代码块（自带 border-border + 圆角 8px）和表格（自带全边框），套一层外盒会出现三层嵌套框。 我不推荐它，列出来是因为它是原任务点名要评估的方向，且它是 design-system.md:210-211 判据 #3 「中性提示盒 = bg-muted + border-border」的合法写法——不是不能做，是做了不划算。

D3-c：区分度来自形状（右对齐 + 收窄）而不是新容器，这是 ChatGPT / Claude 网页版等主流客户端的通行做法， 也正是本仓 A07 :848-850 与 phase0a :419-429 最初的形态——D26 ④ 才把它废掉的。 所以 D3-c 严格说不是「发明新方案」，是回滚一条裁定。 底色用 bg-accent 是词表内动作：design-system.md:102 明写「需要真正拉开的第三级底色时，用 --accent / --selection（交互层）或 --input（填充层）」； 用户气泡本身没有 hover 态，不会和 hover 语义打架。描边取 --input 也有语义依据——它的定义就是「填充语义，兼作输入框描边」，而气泡正是用户输入的回显。

为什么 D3-c 需要重新讨论 D26 ④：D26 ④ 当初的理由是「满宽后没有 slack 可对齐，85% 与右对齐是死重量」。 这个理由在气泡看得见的前提下成立；但现状是气泡根本看不见（1.027 / 1.111），当初的判断建立在一个未被量化的前提上。 本页把这个前提量化了，所以值得复议——这属于「有新证据的复议」，不是推翻裁定。

三条通用纪律（改动时别踩）

① 禁任意值：行高 1.75 只能走新 token，不能写 leading-[1.75]；色值只能走语义 token，不能写 text-[#575653]（design-system.md:218-232 硬编码色禁令）。

② 新增 token 必须双写：任何新 --* 都要同时在 globals.css 的 @theme 补 --color-* / 对应桥接，否则 Tailwind v4 不生成工具类（design-system.md:234-238，已有 bg-sidebar-* 死件先例）；新字号 token 还要注册进 lib/utils.ts 的 tailwind-merge font-size 组，否则 cn() 会静默吞掉颜色类。

③ 不许用 dark: 表达可读性差异（design-system.md:115-124）：本页所有变体都靠语义 token 自身随 .dark 换值，没有一处 dark:。
