颜色纪律（照抄时最容易破的三条）

  • 零硬编码：本页原型内一个十六进制值都没有，全是 var(--*)；唯一的 color-mix 用在用户气泡描边（--primary 8%），沿用 A01 已验收写法。
  • --selection / --hover 不叠 alpha：globals.css 已把上游的半透明预合成成实色，再叠 /N 会二次衰减。本页选中行/悬停一律裸用。
  • --accent-primary 只做填充与圆点：亮色下它对 bg 只有 1.82:1，导轨小圆点可以，文字绝对不行。
  • --status-running 不是 warning：Flexoki 的 warning 与 primary 同值，运行态用 info 系的 --status-running（T-21 已替掉全仓唯一的 bg-amber-500）。

字体纪律

  • D18③：sans / mono / heading 三者同为 ui-monospace，本页原型内没有第二种字族。
  • 中英混排宽度节奏是已登记风险（open-q #10）——本页有意在下拉与侧栏里放了中英混排文案（「新建 worktree…」「本机运行」），验收时请重点看这几行的纵向节拍。
  • 路径与分支名走 13px code 档 + tabular-nums（时间戳），保证右对齐相对时间列不抖动。

一、口径变更：D18③「三者统一 ui-monospace」撤销 → D25 分域

D18③ 原口径「sans / mono / heading 三键统一为同一条等宽栈」自 2026-07-30 起撤销， 改为分域：UI 走系统比例栈，等宽只保留给代码 / 终端 / 内容中的标识符。 上位依据 D25（docs/plans/2026-07-30-d25-font-domain-design.md）；触发是 open-q #10「中英混排风险」实测结项——风险坐实，不是理论洁癖。

域的判据不是「是不是标识符」，是「内容 vs 控件」。同一个字符串 WorkspaceShell.tsx， 出现在正文里用 mono，出现在下拉按钮 / 文件卡上用 sans。一句话测法——用户会不会去逐字符读它、比对它、复制它？ 会 ⇒ mono；只是拿它当一个「名字」点一下 ⇒ sans。完整域映射表见 D25 §2。

两栈的三条硬约束（已写进 globals.css 注释，防后人「顺手优化」）： ① Latin 段在前、CJK 段在后——字体匹配是逐字符的，顺序反了会让拉丁字母落进 CJK 字面（中文环境的经典丑拉丁 bug）； ② 刻意不写 system-ui——Chromium / Windows 下它按系统区域解析，zh-CN 机器上正好触发 ① 要防的那个失败； ③ 零随包字体——本仓 @font-face 0 处、字体资产 0 个，写任何非系统字族都是空头支票（design-system 既有红线）， 且「随包拉丁 + 系统 CJK」比厂商成对设计的系统栈更难看，而 CJK 全量随包是 MB 级资产、与 C-15 的未决体积问题叠加。

四、屏⑤ 工具行字体口径（D25 生产版）

屏⑤ 的 .ct-row verb 与 .ct-a arg 在原型里同族同号 15px，属 D18③ 全等宽的遗留呈现， 自 D25 起不再是施工依据。生产口径：verb → var(--font-sans) @ --text-markdown(15px)； <pre> 输出体 → var(--font-mono) @ --text-code(13px)；arg 则不是单一口径。

arg 槽是多态的，「arg 一律 mono」是错的。同一个 {view.arg} 槽会装两类完全不同的东西： vflow/package.json / shell 命令 / URL 这类机器串，与 2 files, 3 searches / for 1s / Bash 里人写的 description 这类散文。 不区分的话，「刚清掉的等宽」会原样撒回中列最显眼的三个位置。落地为 ToolRowView.argKind: 'ident' | 'prose'， 在 toolCard.ts / turnTiming.ts 生成侧判定，渲染侧只消费：

argKind 落地口径（as-built）

  • 'ident' → font-mono + --text-code(13) + tracking-normal（走 <Ident> 原语）。行内 mono 降一档是硬要求不是审美偏好：同 px 下 mono 的视觉体量比 sans 大 8~12%（平均 advance 0.6em vs 0.5em），15/13 的档比 = 0.867 正落在推荐带内。
  • 'prose' → 不加任何字族类（继承 sans）+ --text-markdown(15) + tabular-nums——Worked for 1s 的秒数是原地跳变的数字。
  • 未枚举的工具（Grep / Glob 等尚未进分类表的）argKind 缺省 ⇒ 走 sans。这是刻意选择的良性降级：漏标一处只会渲染成比例字体（参照图里 Cursor 的文件名本来就是比例，降级后仍在目标态附近）；反向落法（默认 mono + sans 白名单）漏标一处就渲染成等宽，正是要消灭的那个 bug。失败模式要选良性的那个方向。
  • 三级灰与 destructive 分级（P-01 / P-05）与本条正交——字族改动不动任何颜色裁定。

屏⑤ 的其余裁定（三级灰分配、失败态、展开规则、缩进 depth=0、hover 行为）全部继续有效。 两条支撑：实现侧 ToolRows.tsx 的 items-baseline 正好是对的——混字号混字族必须基线对齐； 行高由较大的 15px 行盒决定（leading-normal ≈22px），13px mono 行盒 ≈17px 顶不破，行高零抖动。 ChevronDown 的 size-[13px] 与 code 档同尺寸，保持不动。

七、实测归因：本页三处数值前提被证伪

撤销 :1632。本页 :1632 原文「Cursor 的 Fable 5 High 是一个合并控件；我们拆回现有的两个 select（ModelSelect + EffortSelect），零新控件」—— 用户第 5 条明示「model 和 effect 可以做到一个选项中」，该裁定正式撤销。 替代口径：单触发器 {模型} {档位} ⌄，基名 --muted-foreground、档位后缀 --foreground + font-medium， effort = Default 时后缀整段不渲染。 后缀「更粗」这半条以 D25 为硬前置——等宽栈下 500 是 no-op（多数系统 mono 只有 400 / 700），必须先有比例栈它才成立。

字号取 --text-ui(14)，不降到 13。用户第 4 条给的是一个二选一「字体可以相对小一点，或者外接框稍微大一点点」，采纳后者： 横内距 6px → 8px，字号维持 D25 §2.2 的 S11 = 14px。硬理由——模型 chip 与目标行三个控件同为 24px 高的 ghost chip，只是分处卡内 / 卡下两行； 单独把模型 chip 降到 13px 会在相邻两行之间造出一档 1px 的字号差，正是 polish-audit P-12 点名的「相邻档只差 1~2px、读不出层级」的病灶复制。 targetTriggerClass() 的内距一并提到 8px，使全 Composer 只剩一种 ghost chip 形制（两者的内距类与高度类可交叉断言）。

:810-819 .sel 的两处追记。裁定本身（无边框、无阴影、--r-sm、hover:bg-hover）完全正确，且正是本次的落地目标，只作两点补充： ① 横内距 0 6px → 0 8px（同步应用于 :736-753 的 .tgt-btn）； ② 补键盘态——:focus-visible 必须与 :hover 呈现同一层底色：「默认无框」的设计若只挂 hover，键盘用户会完全失去控件边界， Tab 上去时屏幕上除了一圈 outline 没有任何形状变化。outline 与底色两者叠加，不互相替代。 另记一条形态硬约束：「壳」是填充式（hover:bg-hover），不是描边式——写成 hover:border 会在悬停瞬间把控件撑高 2px 造成行抖动。

Cursor 弹层的裁剪判据（登记为方法论）。参照图 docs/design/refs/feedback-20260731-round4/ScreenShot_2026-07-31_134823_982.png 里的 搜索框 / Auto 开关 / 行内档位后缀 / ↺ Edit / Options 子面板（Thinking · Context · Effort）五件，本仓一件不搬： 前四件是「9 个模型跨 5 家供应商」与「每模型记忆档位」这两个规模 / 能力前提的产物，而本仓目录恒为 3~4 项、effort 是会话级的； 子面板三组里 Thinking 在本仓是 Host 能力门控（用户无权开关，做成开关等于给一个假旋钮）、Context 无对应协议字段，只剩 Effort 一组， 为一组单选开一个横向子面板得不偿失 ⇒ 降为主列表的第二个分组段。 可复用的一句判据：别人的搜索框和子面板是他的规模与能力的产物，不是他的样式。
