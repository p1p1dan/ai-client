降级梯（开文件后生效）

  • L0 · W ≥ 1580：chat · editor · 右栏全在（展开态无 Rail）—— v2 的三列感，chat ≥400 / editor ≥520 不再被挤
  • L1 · 1244 ≤ W < 1580：右栏自动收起、Rail 出现（git dot 仍可见，一键唤回）
  • L2 · W < 1244：chat 隐去，editor max 占满中列；editor 头部 chat 按钮一键唤回
  • 手动 > 自动：任何时候手动展开右栏/唤回 chat，本次文件会话内自动降级让步；关文件清零

阈值怎么来的

  • 1580 = 280 side + 400 chat-min + 520 editor-min + 380 panel —— 展开态无 Rail，故不含 44
  • 1244 = 280 + 400 + 520 + 44 rail —— 收起态 Rail 在；低于此值 chat 与 editor 无法同时达标
  • chat-min 400：聊天气泡可读下限（48rem 是理想值，不是下限）；editor-min 520：13px 等宽 ~66 列 + gutter
  • 1366×768 笔记本开文件 = L2 直达（chat 隐），这是设计预期而非缺陷 —— §06-7 请确认

联动收展纪律（定稿）

  • 展开 = 右缘无图标：panel 展开时 Rail 不渲染，右缘干净；L0 阈值因此不含 44px（1580）
  • 收起 = Rail 出现：三图标 + git dot 随时唤回，点击 = 展开到该 tab（editor open 时记为手动覆盖）
  • 折叠入口三处：顶栏折叠钮 · tab 条 ✕ · Ctrl+J；Rail 激活态点击路径不存在（展开时 Rail 不渲染）
  • 自动降级同纪律：L1 自动收起后 Rail 出现，点击唤回 = 手动覆盖，本次文件会话内自动梯让步

对 v4 / v2 的取舍 —— 为什么修订成这样

adopt / reject

vs v4（editor = 动态第 4 tab）

  • 否决 · editor 塞右栏 tab：380px Monaco 看代码憋屈，文件名挤在 tab 条、chrome 残缺（无独立头部），maximize 要手动多走一步 —— 观感「奇怪」的根源
  • 否决 · Rail 底栏三图标：terminal 有更近的落点（tab 条动作区），bell 未拍板，settings 与 Sidebar 重复 —— 底栏清空，Rail 回归纯内容导航
  • 采纳：Rail 常驻 + 面板分段 tab · BottomDock · per-tab 宽度记忆 · git-only dot · session strip 等全部内容规格

vs v2（中列三列 · 固定 0.75fr）

  • 采纳 · editor 中列：真实 editor chrome（文件名头 + 操作按钮），chat 与代码同框对照 —— 这是 v2 最值钱的部分
  • 否决 · 固定三列硬挤：1400px 下 chat <400px 的老问题不解；改降级梯：宽则三列同框，中则收右栏，窄则隐 chat，每档都保住可读下限
  • 否决 · 省略 Rail / 右栏恒 400：v4 已论证（收起态无入口、指示不可见）；本版 Rail + tab 双 chrome 原样保留

vs 方案二 · 常驻不折叠（已否决 2026-07-30）

  • 否决原因：v5 壳内 A/B 实测对比后拍板 —— 联动收展更符合使用者操作习惯：展开时右缘干净无干扰，收起态图标唤回路径明确
  • 接受的代价：收展交替时右缘有 44px 跳变 —— 收展本即是布局切换，跳变可预期；换来展开态纯净右缘 + L0 阈值降 44px（1580）
  • 保留的共性：git-only dot · 三图标顺序 · 自动降级后 Rail 唤回 —— 两案共通部分原样进入定稿

定稿新增（v1–v5 都没有）

  • 贯通顶栏：Session · 终端 · 折叠 横贯 chat+editor+panel+rail，面板 tab 条明确降一级 —— 壳层级从「并列」变「包含」
  • 画幅降级梯：以容器宽度为输入的布局状态机，手动操作优先级高于自动 —— 响应式从「挤一挤」变成「有纪律地让位」
  • editor head chat 按钮：L2 下 chat 的一键唤回入口，避免「开了文件就找不到对话」的迷失感
  • 联动收展 rail：Rail 存在时机与 panel 收展严格联动 —— 展开无图标、收起出图标，单一路径不分叉
