这个结构解决了什么

  • 流式期间不需要判终稿，所以没有抖动。你上一版问的 C 项（"变灰绑什么"）在这套结构里不存在——因为流式期间没有任何东西被提前点亮。没有提前点亮，就没有"突然变灰"。这是这个结构最大的好处，比我之前给的几个方案都干净。
  • "流式完毕"这个信号已经存在。MessageTimeline.tsx:1997 的 processSettled 就是它（!turnActive && !(isLastTurn && inFlightSession && !statusOwnedByPendingHead)），"工作中 / 已工作"那两态已经靠它在切。提取终稿可以直接挂在它上面，不需要新增状态。
  • 头里只有数量，正好回到 T106 的 D6 / D5 形态。这也顺带解决上一轮那个"头一直在动"的问题：数量是单调递增的，最后一段旁白是会被替换的。数量可以动，因为它是进度。

操作合不合并 —— 我的意见：合并，但只在"没被打断"的连续区间内

  • 连续同类操作 → 聚合成一条（上面的「读取 3 个文件」）。一轮十几次读取摊成十行是"太杂"的主要来源。
  • 但旁白和思考会打断聚合，前后各自成段。理由不是洁癖：旁白是在解释它下面那批操作，这个"解释 → 被解释"的相邻关系一旦被打散，旁白就失去意义了。这也正是仓库现在的行为（groupTimeline 遇到 text / thinking 会 flush()，mergeAdjacentToolGroups 只合并相邻的组），所以这条不需要改代码。
  • 不要按类型跨段合并。即不要把整轮所有"读取"抽出来堆一起——那会破坏时间顺序，你再也读不出"先读、再想、再改"这条线。
  • 带授权的操作不要并进聚合（现有决策 031 已有此例外）：它是你需要动手的东西，埋进去要多点一次才看得到。
