## ② 注入接缝清单

**agent-host（已有、天然可复用的接缝）**
- `src/agent-host/claudeSettings.ts:40` `loadClaudeSettingsEnv(settingsPath)` 是唯一的凭据读入函数，签名已支持自定义路径（测试用）。若凭据改为 app 私有托管，**最小改动点**就是把这个函数的实现换成读 app 私有存储（而不是文件），返回同样的 `{env, diagnostics}` 形状——下游 `ensureRuntime()`（`index.ts:130-166`）、`mergedEnv`（`claudeRuntime.ts:556`）、SDK `options.env`（`claudeRuntime.ts:756`）三层管道完全不用动。这是 **env 注入机制**，且已经是端到端打通的（settings.json → agent-host process.env → SDK 子进程 env）。
- `CLAUDE_CONFIG_DIR` 重定向机制在 agent-host 侧**已支持读**（`claudeSettings.ts:31`、`historyReader.ts:241`），但**主进程/agent-host 自身从未写过它**（全仓 `grep "CLAUDE_CONFIG_DIR\s*="` 在 `src/` 下零命中）。`src/main/services/agent-host/hostEnv.ts:37-45` (`buildAgentHostEnv`) 是 Main 注入 agent-host 环境变量的唯一契约点，目前只有 4 个 key（driver/cometixVersion/nodeExecPath/appVersion/codexHomeDir），**没有 `CLAUDE_CONFIG_DIR` 或等价的 `AICLIENT_CLAUDE_HOME`**——对比 Codex 已经有 `AICLIENT_CODEX_HOME` 做隔离私有 home，Claude 侧没有对应机制。这里是一个**现成但空缺的接缝**：给 `buildAgentHostEnv` 加一个 key，`AgentHostProcess.start()`（`src/main/services/agent-host/AgentHostProcess.ts:43-49`，`spawn(..., {env:{...process.env,...}})`）会自动透传给 agent-host 子进程，agent-host 侧 `defaultSettingsPath()` 已经认这个变量。

## ③ 坑与依赖

- **`CLAUDE_CONFIG_DIR` 读取口径不统一**：`ClaudeHookManager.ts:71-76`、`ClaudeProviderManager.ts:8-13`、`ClaudeIdeBridge.ts:92-96`、`claudeSettings.ts:29-34`、`historyReader.ts:241` 五处都遵循 `process.env.CLAUDE_CONFIG_DIR ?? ~/.claude`；但 `ClaudeRuntimeConfig.ts:5-7`（`disableClaudeAutoUpdates`/`mergeClaudeEnvSettings`）和 `OnboardingService.ts:243-244,337,453,473`（现有邮箱验证码登录的全部落盘点）**硬编码 `os.homedir()/.claude`，完全不看 `CLAUDE_CONFIG_DIR`**。这意味着：如果 D47 打算用「把 `CLAUDE_CONFIG_DIR` 指到 app 私有目录」的方式做隔离，`OnboardingService.ts` 和 `ClaudeRuntimeConfig.ts` 这两个写手**不会跟着重定向**，会继续写用户真实 `~/.claude`——这两处必须同步改，否则「不再写 ~/.claude/settings.json」的目标不成立。
- **同一文件多写手竞态，且 `OnboardingService.ts:254-258` 注释已明确指出**：`writeClaudeConfig` 会跟 `ClaudeHookManager`/`ClaudeProviderManager` 抢写同一个 `settings.json`，所以做了「写后读回校验 + 重试一次」。这是当前架构脆弱性的直接证据：**多个独立写手管理同一份共享状态文件**，`writeSettingsWithEnvGuard`（`ClaudeHookManager.ts:115-137`）的存在本身就是给这个脆弱性打的监控补丁（发现丢失只打 log，不真正解决竞态）。若凭据改为 app 私有存储，至少能消掉 OnboardingService 这一个写手，但 hooks 相关的四个 `ensureXHook` 写手依然要写 `~/.claude/settings.json`（除非 hooks 机制也一起搬家）。
- **hooks 机制对「不再写 ~/.claude」的依赖**：`isClaudeInstalled()`（`ClaudeHookManager.ts:353-356`）= `fs.existsSync(configDir)`，是所有 `ensureXHook`/`setClaudeBridgeEnabled` 的**前置门禁**。今天 `~/.claude` 目录之所以「存在」，很大程度上是因为 `OnboardingService.writeClaudeConfig`（`mkdirSync`，行261）或用户自己装过真实 Claude CLI 创建的。如果 D47 落地后 app 完全不再触碰 `~/.claude`，且用户机器上从未装过官方 Claude Code CLI（很可能，因为这是无密码托管场景），`~/.claude` 目录可能永远不存在 → `isClaudeInstalled()` 恒为 `false` → **Stop/PermissionRequest/UserPromptSubmit/StatusLine 四个 hook 全部装不上，IDE bridge 也拒绝启动**（`ClaudeIdeBridge.ts:685-688`）。而这些 hook 是「Agent 完成通知」「AskUserQuestion 提醒」等功能的信号来源（`ClaudeHookManager.ts:211-238` 的 `postAgentHook` 转发机制），**hooks 本身完全不涉及凭据**（只操作 `settings.json.hooks`/`statusLine` 字段），但**门禁条件（目录存在性）间接绑死在"曾经写过 `~/.claude`"这件事上**——这是需要在规格里显式决策的点：要么改 `isClaudeInstalled` 的判定方式（比如改成"CLI 可执行文件存在"而非"配置目录存在"），要么 app 仍需在某处 `mkdirSync(~/.claude/hooks/...)`（只建 hooks 相关文件，不写凭据）来维持这条通知链路。
- **`scripts/dev.js:83-224` 是唯一的、已验证可行的"app 生成隔离 Claude home"参照实现**，直接可抄的模式：`seedIsolatedConfigDir(vars)`（行135-171）只写 `{env:{ANTHROPIC_AUTH_TOKEN/API_KEY/BASE_URL}, model}` 到隔离目录的 `settings.json`，另建 `.claude.json` 预置 `hasCompletedOnboarding:true` + 逐工作区 `hasTrustDialogAccepted:true`（跳过首启信任弹窗），目标目录是 `node_modules/.cache/aiclient-dev-credentials`（dev 专用，生产应换成 `app.getPath('userData')` 下的私有目录）。这个隔离目录**只在整个 Electron 进程启动前，通过外层 `spawn('npx', electronArgs, {env: buildChildEnv(...)})`（行243-249）把 `CLAUDE_CONFIG_DIR` 设进**整个子进程树的环境——即 Main 自己、agent-host（因为 `AgentHostProcess.start()` 透传 `process.env`）、以及所有 PTY 终端（因为 `PtyManager.ts:378` 也是 `...process.env` 起手）**全部**自动继承同一个隔离目录，这是一种"进程级全局重定向"，跟 D47 期待的"按子进程/按终端各自精确注入"的粒度不同——生产实现如果照抄这个模式会导致**用户在 AiClient 里开的任何终端，即使不跑 `claude`，只要开着任何普通 shell 也会带上这个 `CLAUDE_CONFIG_DIR`**（副作用小，因为只有跑 claude CLI 才读它，但语义上是"全局环境变量污染"而非"按需精确注入"）。
- `scripts/dev.js:92-100` `STRIPPED_KEYS`/`STRIPPED_PREFIX`（`ANTHROPIC_*`、`CLAUDE_CODE_OAUTH_TOKEN`、`CLAUDE_CONFIG_DIR` 等）先从继承的 shell env 里剥离再重新注入，是为了防止开发者本机 `~/.zshrc` 里的个人凭据泄漏进测试环境——这条"先清后填"的思路在设计 app 私有注入时也适用（比如 PTY spawn 前，若 shell 本身继承了用户系统级 `ANTHROPIC_*` 变量，需要决定是覆盖还是保留）。
- **`CLAUDE_RUNTIME_REGISTER_ENV`/`mergeClaudeEnvSettings`（`ClaudeRuntimeConfig.ts:49-73`，IPC `main/ipc/claudeRuntime.ts:60-76`）疑似死代码**：`preload/index.ts:1059-1060` 暴露了 `registerEnv`，但 renderer 全仓无调用点。规格阶段应确认这是遗留接口（可删）还是给未来功能预留的桩，避免误判成"现有可用的注入接缝"。
