## §2 逐条裁定细节

### 2.1 D1 — synthetic id 可达性（必裁点 1）

**a) 全量实测（本轮亲跑，脚本 `/tmp/scan_uuid.py`）**

| 指标 | 实测值 |
|---|---|
| 扫描文件 | **694** 个 `.jsonl`（`~/.claude/projects` 递归，含 subagents） |
| 总行数 / 坏行 | 116,413 / 5 |
| `type ∈ {user, assistant}` 行 | **101,319** |
| **其中缺 `uuid` 者** | **0** |
| 缺 uuid 的其它 type | 全部是控制行（`queue-operation` 1402、`last-prompt` 2064、`mode` 2020、`permission-mode` 1264、`ai-title` 1924、`file-history-*` 779、`started` 254、`result` 236…），**这些行 `historyReader` 根本不走 synthetic 分支** |
| 最大文件 | 26,760,683 B（25.5 MiB）= `94a3769d-…jsonl`，正是 RCA 引用的会话 |
| `> 32 MiB` 的文件 | **0 / 694**；`> 16 MiB` 仅 2 个 |

**「今天没越线」能不能当发射证据？——不能，但也不构成 blocker。** 裁定口径：
32 MiB 只是 synthetic 漂移的**第二道**必要条件，第一道是「u/a 行缺 uuid」，实测 **0/101319**。
两道条件是合取的，而第一道由 CLI 写侧的行为保证（不是我们能约束的），第二道会随会话增长自然逼近
（现值已达阈值的 80%）。所以：**不能把「文件还没到 32MiB」写进 as-built 当安全证据**（它会过期），
但**可以**把「u/a 行 100% 带 uuid（101319/101319）」写进去当**今天的**可达性判据。

**b) 读窗与 synthetic 生成段（实读源，非引用）**

- `historyReader.ts:700-704`：`inputTruncated = info.size > HISTORY_INPUT_TAIL_LIMIT_BYTES` ⇒
  `openTailLines` 只在**超 32 MiB** 时启用；否则 `openStreamLines` 整文件流式读。
- `historyReader.ts:195`：`HISTORY_INPUT_TAIL_LIMIT_BYTES = 32 * 1024 * 1024`（实读，规格与 A 引用一致）。
- `:769-771`（assistant）/ `:905-906`（user）：`entry.uuid` 为空才 `synthetic-${totalLines}`；
  `totalLines` 从**读源起点**开始计（`:706` 初始化 0）。
- `:745-756` `pushMessage` 环形缓冲：越限时 `messages.shift()` —— **只从头淘汰**。
  A 的这条实读成立：行**只会从头消失，不会在中段变新**。

**⇒「读窗移动导致同一行改号」的前提裁定**（B 引 :699-704/:767-774/:873-908，A 引 :750-755，两侧都没读全）：

> 必须**同时**满足：① 该行是 user/assistant 且**没有 uuid**（今天 0/101319）；
> ② 文件 **> 32 MiB**（今天 0/694）；③ 尾窗起点跨过该行之前的某个换行，使 `totalLines` 位移；
> ④ 锚点行仍在窗内（否则 guard 3a 直接停折）。
> 四条合取才产生 B 的反例。**结构可达、今天不可达。**

**c) 处置档位裁定：三档全取（合取），但主承重换人**

1. **停折守卫（取）**：不是 B 说的「见 synthetic 就停」，而是更强也更便宜的
   **定位对齐探针**（R-4）：快照的 bucket 序就是上一次合并的输出序，锚点在两侧的下标必须相等；
   不等即证明「读窗/编号已漂移」，此时**一切锚点前认领全部关闭**。这条同时覆盖 synthetic 漂移、
   头部淘汰、JSONL 重写三种漂移源，且不需要认识 `synthetic-` 这个字符串。
2. **synthetic 行不参与吸收（不单独取）**：被 1 完全包住，且会在「全文件都是 synthetic」的
   合法场景（无 uuid 的第三方转录）下**过度停折**。改为在头注登记为已知形态。
3. **负控用例钉住（取）**：R-22 的 N3/N4 两条，其中 N4 就是 B 的反例逐字夹具，
   v1 下必红（实测 v1 吃掉 `user-resend`）、v2 下必绿（实测保留）。

**注意 A 自认的因果串联**：A 的 M3 说 P-1 与洞 B 串联（replacement fold 只发生在带附件消息上），
这条我复核成立（`isReplacementFoldable :175-178` 要求 `attachments.length > 0`）。
它的推论正是本仲裁的支点：**锚点前认领这件事，只有「上一轮自己挖的空洞」需要它**——
既然如此，就不该用「id ∉ candidateIds」这种**全称谓词**去换它，而应当用**定位证明**精确认领。

### 2.2 D2/D3 — 附件身份坍缩（必裁点 2）

**A 的证明确实隐含前提，但不是「anchor≠null」，而是「命中的行是真副本」。**
A 的 V2 定理只证明了「准入集是今天下界的超集」和「超集增量与 bucket 副本一一配对」；
它**从未证明**「附件档命中的行是发起该回声的那一回合」。A 在 §7.1 用
「附件档 ⇒ 必走 replacement fold ⇒ 只换元素不改数组长度 ⇒ 结构上不可能删泡」补这一步——
**这一步是错的**：`mergedHistory` 长度确实不变，但被折的运行时消息**不进 `kept`**，
最终输出是 `|history| + |kept|`。命中错行时，两个真实回合 ⇒ 一个气泡。

**逐步推演 §2.2/§2.3 字面规则下 B 的两个反例（v1 台架实跑，非纸面）**：

| 反例 | 入参 | v0（今天） | v1（规格字面） | 判定 |
|---|---|---|---|---|
| **B 反例一** | `history=[h:A(image/png, 无 name)]`，`bucket=[E_B(空文本, image/png, name=b.png)]`，`snap({E_B}, null)` | `h:A \| user-B`（2 泡） | **`user-B`（1 泡）** | **真丢失**：turn A 被 `historyReplacements.set(0, E_B)` 覆盖，E_B 又不入 kept |
| **B 反例二**（= 规格 §3.4 读法②） | `history=[h:A, h:B]`（h:B 才是真副本） | `h:A \| h:B \| user-B`（3 泡） | **`user-B \| h:B`（2 泡）** | **真丢失**：A 消失、B 重复。规格「顺序不变、唯一差异是 name 挂到前一泡」**证伪** |
| **变体 CE1b**（锚点非空、诱饵行在锚点之后） | `history=[h:anchor, h:A]`，`bucket=[h:anchor, E_B]`，`snap({h:anchor,E_B}, 'h:anchor')` | 3 泡 | **2 泡** | **真丢失**，且**与洞 A 无关**——该行本来就在今天游标的扫描区内，是洞 B 单独造成的 |

**规格里有没有 B 没注意到的守卫？——没有。** 逐条查过：guard 1（`candidateIds.has(message.id)`）
只约束**候选**不约束**历史行**；guard 2（match-required）只在**找不到**匹配时生效；
`isReplacementFoldable` 只看候选自身；**规格全文没有任何候选唯一性条款**。
B 的判断「候选唯一也不足以修复反例一」我复核成立：唯一的可匹配行仍可能是另一张图。

**处置裁定：image-only 歧义 fail-open 保留重复——必要，但要精确切分，不是一刀切。**
`(kind, mediaType)` 这个身份对「本 app 自己发的截图」是**全坍缩**的（都是 `image/png`），
所以任何**无法归因**的命中都必须让路。三条切分（R-8/R-10/R-11）：

- **锚点为 null 的 replay，附件档一律不折**（实测：v2 在 B 反例一/二上退回 v0 的输出）。
  代价：全新会话内首次 resume 的 image-only 消息仍重复——**与今天完全一致，不是回归**。
- **锚点非空时，附件档只在「锚点之后的新尾区」或「本回声自己的定位空洞」里折**
  （实测：FIX-1/2/3 三轮全部折成单例且幂等，即 RCA 报告的实况路径）。
- **历史行带 `name` 时不参与附件档匹配**：`name` 只可能来自 Carrier B（`extractControlAttachment :685-687`
  从 `name/filename/path` 取），而本 app 自己写的 image 行走 Carrier A、**结构上无 name**
  （`:635-638` 注释 + `:641-645` push）。⇒「无 name」是「本 app 写的」的签名，
  用它挡住外来命名图片行是零成本的暴露面收缩。

### 2.3 残留的不可裁边界（必须写进规格，不得再声称「恒为重复」）

上面三条切完之后，**仍有一个丢失口**：锚点之后新落盘的、同 `(kind, mediaType)` 的、
**无 name 且无对应回声**的 image-only 行（外来写入方、或 Carrier-B 泄漏造出的空文本行）
会吸收我们的回声（实测：v2 在 CE1b 上仍是 2 泡）。裁定：

- **登记为 R7（丢失方向残留），不得再用「chip 名归属漂移」这种定级**；
- 其暴露面与今天文本档的同类暴露**同级**（今天一条锚点后同文本的外来行同样会吃掉文本回声），
  ⇒ 满足「不新增今天没有的丢失类别」这条准入线；
- 根治属 F11-b（canonical uuid 等值）。**F11-b 的立票理由由此从「增益」升级为「残留收口」。**

另外实测发现一条**今天就已存在、两轨都没提**的丢失（v0 与 v1 输出相同）：
`anchor=null` 且历史行不在 candidateIds 时，文本档回声会被更早的同文本行吃掉
（台架 B-CE4：`bucket=[user-resend('继续')]`、`history=[h:old('继续'), h:oldA]` ⇒ v0/v1 都输出
`h:old|h:oldA`，重发气泡消失）。这条**不是本批引入**，但它证伪了模块头注
`:48-49`「residual fail direction is a duplicated bubble, never a lost one」这句合同正文。
裁定：**登记为 R6 + 一条 incident 层回归用例**，头注措辞同步订正（R-21/R-23）。

### 2.4 D4 — 旗舰场景与 T2（必裁点 3）

**核实 A 的两条证伪**：

1. **前缀性质**：`§3.1` 的 `history=[h:u1,h:a1,h:a2,h:a3]` 不是 `§3.2` 的
   `[h:u1,h:a1,h:u2,h:a2,h:u3,h:a3,h:u4,h:a4]` 的前缀，也不是它的任何后缀。追加写的 JSONL
   不可能先有 `h:a2`（对 `h:u2` 的回复）后有 `h:u2`。读侧也堵死了「`h:u2` 被吞」这条出路：
   `historyReader.ts:901` 的 `if (text || attachments.length > 0)` 对图片行**必然为真**
   （Carrier A `extractContentAttachments` 抓 image 块）。**A 对。**
2. **淘汰方向**：`pushMessage` 的 `messages.shift()`（`:750-755`）与 `openTailLines`（`:390-410`）
   都只从**头部**去行；对固定文件前缀，处理更多行只会淘汰更多，窗口起点**单调右移**。
   ⇒ 行不会在中段「变新」。**A 对。**

**亲测 A 的替代场景（P-1 犯罪现场）**，三路对跑：

```
bucket   = [h:u1, h:a1, E1003, h:a2, E1005, h:a3, h:u4, h:a4]   // 上一轮 fold 的产物
history  = [h:u1, h:a1, h:u2 , h:a2, h:u3 , h:a3, h:u4, h:a4]
snapshot = { candidateIds: 上面 8 个 bucket id, anchorHistoryId: 'h:a4' }
v0 → h:u1|h:a1|h:u2|h:a2|h:u3|h:a3|h:u4|h:a4|E1003|E1005   （10 泡，两条回声垫在最尾）
v1 → h:u1|h:a1|E1003|h:a2|E1005|h:a3|h:u4|h:a4             （8 泡）
v2 → 同 v1，且再跑一轮不动点                                （8 泡，幂等）
```

v0 的输出与 RCA §1 用户原述（「历史输入 a（图）→ 历史输入 b（图）→ 我的输入 n」、

## §5 总判

**修订后开工。不判推倒。**

两条 blocker 在合取后都有安全出路，且出路已在本轮台架上实测取证，不是纸面推演：

| blocker | 合取后的出路 | 实测 |
|---|---|---|
| **B-Blocker 1**（附件身份坍缩致丢失） | R-8 附件档锚点前置 + R-11 无 name 要求 + R-5 定位认领 | B 反例一/二在 v2 下**退回 v0 的输出**（2 泡 / 3 泡），同时 FIX-1/2/3 的实况路径仍折成单例且幂等 |
| **B-Blocker 2**（新鲜度谓词被 id 漂移欺骗） | R-2 下界回退 + R-4 对齐探针 + R-5 定位认领 | B 的漂移反例在 v2 下**保留 `user-resend`**（3 泡），同时 A 的 P-1 犯罪现场仍从 10 泡修到 8 泡 |

**为什么不判推倒**：B 的两条 blocker 打掉的是**规格的两条论证**（计数守恒、新鲜度谓词），
不是**修法的目标**（把上一轮自己挖的空洞填回去、让 image-only 有身份可比）。
目标本身在 v2 上被实测证明可达，且**不需要动 `chatSessions.ts`**（`orderedIds` 的生产者
`snapshotResumeCandidates` 就在本文件内，`chatSessions.ts:515-519` 今天已按序传参）
⇒ F2 红线仍然不撞，§0.2 的 D-3 降级理由继续成立，b 票（F11-b）维持另立。

**为什么不判「照原稿开工」**：A 轨的「0 blocker」建立在两条它自己也承认未证明的信念上
（bucket 只增不删、行 id 永远稳定），而 B 轨用两个反例把这两条信念各打掉一半；
A 的补充直证（附件档结构上不可删泡）经实测为假。**照原稿施工会引入今天不存在的丢失类别。**

**施工序不变**（先落会红的用例 → 洞 A → 洞 B → 头注 → 六门 + 15 对变异），
但第 1 步的红灯集合改为 N1/N2/N6/N7/N14/N16，并**增加一次「按原稿跑 N8/N9 让它们变红」的
反向发射证据**（见 §4.2 脚注）。
