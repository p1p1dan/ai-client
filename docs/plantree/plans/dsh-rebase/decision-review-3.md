### 1. 决策 113：`/goal` 命令带附件时怎么处理；命令记录要不要进历史

- **带附件的 `/goal …`（第 18 条）**：现在，如果你发 `/goal 目标内容` 的同时带了附件，系统不会把它当命令处理，而是整段（包括 `/goal` 三个字）当作普通对话发给模型——不会真的建立目标。要支持"带附件也能建目标"，图片这条路能单独打通，文字附件因为缺一个专门的上传通道仍要拒绝，约 0.5 人日。
  **我方建议**：先接受现状，需要时再单独排期。
- **命令与回答只在直播里出现，重开对话后没有（第 19 条）**：现在，你发的 `/goal`、`/compact` 这类命令和 DSH 给的回答，只在当时的对话过程中可见；重新打开这个对话后，这几行就不在了（不算聊天记录）。要让它们也进历史，约 1 人日，外加要重新生成一批内部测试基准。
  **我方建议**：先不做，需要时再排期。

### 2. 决策 114：模型"反问用户"的工具，没有关闭开关

- 现在：这个工具（模型觉得信息不够时会弹出问题让你回答）默认装上、无法关闭，这与 1.0.x 的行为一致（1.0.x 也关不掉）。如果要能关，两个办法都要额外做：A）设置里加一个开关直接屏蔽它，约 0.5 人日；B）走正式的插件审查流程再登记进白名单，约 1～1.5 人日，但设置页会显示完整的审查信息。
- **我方建议**：暂不加开关，与 1.0.x 现状一致，不算倒退；需要的话选 A 更省事。

### 3. 决策 115：试点插件（Office 文档读写）的已知风险与写入放行

- **审查结论"有条件通过"，请确认接受三项已知风险（第 6 条）**：这是一个第三方社区插件（不是 DSH 官方的），能在对话里创建/读取 Word、Excel、PPT 文件。代理人工审查后认为可以有条件接受，但有三点风险：①处理特殊构造的文件时可能让整个对话引擎卡顿几秒、占用几百 MB 内存（默认关闭、只处理你工作区内的文件、单文件上限 50 MiB，可以缓解）；②插件依赖了一个自己没有声明的 DSH 内部包，靠系统自动找到，以后 DSH 升级需要重新核实；③往 Excel 写入以 `=` 开头的内容会被当公式写入（每次写入都会先弹卡预览完整内容）。
- **放宽写入类工具的审批规则（第 10 条）**：现在，这个插件的写入操作（创建/修改文档）按"接受编辑（accept-edits）"档位（即你已同意模型自主编辑工作区内文件）下，和内置的"写文件/编辑"工具一样不用每次单独弹卡；"每次都问（ask）"档位下仍照常弹卡。
- **我方建议**：都同意，默认保持关闭，你可以在设置里手动打开；如果希望这个插件的写入始终单独确认，告诉我们去掉这一条即可。

### 5. 决策 123：旧会话分叉后续聊，生成的新会话要不要加标题后缀

- 现在：一个从旧版（1.0.x）会话"分叉"出来的支线，一旦在 DSH 版里继续聊，会被迁移成一个新的 DSH 会话；这个新会话和原会话显示**同一个标题**，原本用来区分"这是 1.0.x 遗留"的小徽标也随之消失，两条记录在侧栏看起来像重名。
- 备选：自动在标题后加一个"（1.0.x）"之类的后缀加以区分。
- **我方建议**：这个场景不常见（要先分叉、再用旧版续聊、再回新版继续），可以先不处理，遇到再说；如果您现在就想要后缀，请告诉我们。

### 6. 决策 128：右列终端的三处细节

- **远程工作区可以开终端（第 4 条）**：现在的判断规则把"远程（SSH）工作区"也当成"有绑定目录"，所以远程会话一样能打开终端（连到远端机器执行命令）。如果您认为远程场景不该开终端，改一行代码即可置灰。
- **默认列宽是 558 / 520 像素，不是原型标注的 460 像素（第 7 条）**：原型截图上终端列宽是写死的 460px（说明"约等于中栏对半分"）。实现时改为直接复用文件编辑器列现成的"拖拽比例"机制（更省代码、行为更统一），按这套机制算出来的默认宽度是：1440×900 窗口下 558px、1280×720 下 520px，不是 460px。
- **worktree 初始化脚本要不要挪到右列（第 17 条）**：现在新建工作区后自动跑的初始化脚本，仍显示在"左栏"的旧终端面板里（这是此前遗留的入口，理论上应被右列终端取代）。挪过去并删掉左栏这一整套终端代码（约 1.5 千行 + 测试），是一项独立小任务。
- **我方建议**：远程终端维持现状（可开）；列宽按拖拽机制（更统一），如果您在意 460px 这个数字请明确说明；初始化脚本迁移另开任务处理，不影响当前功能。

原文：[128](decisions/128-p1-11-right-column-terminal-choices.md)

### 7. 决策 129：Windows PowerShell 命令权限分析的从严选择

- **含变量 / 脚本块 / 执行字符串的命令一律不能被"记住"（第 4 条）**：Linux 下（bash）像 `npm test $FLAGS` 这种带变量的命令，权限系统能记住命令本身、以后不用每次确认。但 Windows（PowerShell）下，只要命令里出现变量、脚本块，或者"把字符串当代码执行"这类写法，这次实现一律不允许被记住——每次都要重新确认，哪怕之前点过"本会话允许"。理由：PowerShell 的脚本块几乎能藏在任何地方，记住一条外围命令等于连带记住了脚本块里可能做的任何事。
- **`sc`、`curl`、`wget` 不做别名归并（第 7 条）**：旧版 PowerShell（5.1）里 `sc` 是 `Set-Content`（写文件）的别名，但新版（PowerShell 7）里 `sc` 是完全不同的"服务控制器"命令；`curl`、`wget` 同理。为避免张冠李戴，这三个名字不自动关联，各自按独立命令处理。
- **1.0.x 自有引擎的 bash 审批卡也会多一行提示（第 13 条）**：这次给 PowerShell 命令加的"为什么需要你确认"提示，顺带也加到了仍在用的 1.0.x 旧引擎的 bash 审批卡上，会让老用户多看到一行解释文字。
- **两种终端在"已允许"记录里的显示不统一（第 16 条）**：你批准过的命令会在活动记录里留痕，PowerShell 命令写"已允许 PowerShell"，bash 命令写"已允许 bash"（全小写，沿用 1.0.x 的老写法），两者风格不统一。
- **我方建议**：都同意——从严处理更安全，两处小提示对用户只有好处，显示不统一影响很小，后续如需要可以单独统一。

原文：[129](decisions/129-p1-6d-pwsh-analysis-choices.md)

## 四、需要你授权的动作（不是决策，是等你点头才能做的事）

1. **推送分支并跑 Windows CI**（`.github/workflows/dsh-p1-6d-windows.yml`；P1-10d 的打包冒烟 L1 已带上试点插件）
   - **做什么**：把分支推到 `ci/dsh-p1-6d-windows`（或手动触发 workflow_dispatch），在真实 Windows 上跑 admin / 标准用户两路的 PowerShell 权限探针（S18），以及同一份打包冒烟顺带验证试点插件（Office 工具）在 Windows 上的装载、过闸、读写。
   - **为什么**：pwsh 词法分析和插件在 Windows 上的实际行为，目前只在本机用 bash 做「干跑对照」验证过，没有真正跑过 Windows。
   - **风险**：仓库是公开的，推送分支/触发 CI 会让代码在 GitHub Actions 上公开跑一遍；消耗 CI 分钟数；不涉及破坏性操作。

2. **P1-7d：在开发机上启动 Electron 做 GUI 点验**
   - **做什么**：实际打开应用界面，核对 P1-7a/b/c（目标条、待办卡、后台任务与子代理浮窗、工具行文案图标等）以及 P1-11 右列终端的真实视觉效果——这些目前只有挂载测试覆盖，没有人眼看过。
   - **为什么**：挂载测试只能证明"行为对"，不能证明"看起来对"（容器查询断点、标签栏对齐、深浅主题对比度等都还没人看过）。
   - **风险**：本机是 2 核 / 3.3GB 的开发机，此前做大操作（如整包构建）崩溃过两次；需要谨慎控制点验方式和范围，避免再次把系统弄崩。

3. **P1-4e：把录制门禁接入 CI**（改 `build.yml`、新增 `dsh-bridge-gate.yml`）
   - **做什么**：把本地在跑的 `bridge-record --check` 金样本回归检查，正式接入 CI 流水线，让每次推送自动核对 DSH bridge 的行为有没有漂移。
   - **为什么**：目前这项检查只在本机手动跑，接入 CI 能自动兜底、防止以后的改动悄悄破坏已验证的行为。
   - **风险**：改动核心 CI/构建配置文件，一旦配置有误可能影响后续所有推送和构建；决策 100 已明确要求这一步必须先问您。

4. **真实网关验证**（例如 P1-15 的 R7：三种一次性补全对真实网关跑一遍；此前决策也提到 R1～R10 系列需要授权）
   - **做什么**：用你指定的真实模型服务（而不是本机假网关 `fake-gateway.mjs`）跑一遍提交信息 / 分支名 / 代码评审等功能，核对真实的错误码、限流、超时等行为。
   - **为什么**：目前所有验证都基于本地假网关，还没有确认过真实网关的行为是否符合预期。
   - **风险**：会向真实的公司网关发出实际请求（数十次小请求量级），消耗真实配额，且请求内容会离开本机。

5. **P1-12：删除自有 runtime**（`src/runtime`、native worker 路径等）
   - **做什么**：正式删除分支里已经不再使用的自研聊天引擎（`src/runtime`）及相关代码，本分支自此完全依赖 DSH 宿主。
   - **为什么**：roadmap 记录的前置条件已全部满足——P1-9a/9g 的旧版本语料已备妥、P1-9f 导入已落地（可以删 `PiImportProcess`）、skills/模板/MCP 配置/子代理目录规则已搬进 `src/shared`（P1-16 前置搬迁已完成）。
   - **风险**：这是本分支对旧引擎的最后一次「退役」，删除量较大且不可逆（只能靠 git 历史找回）；删除之后分支不再能回退到自有引擎路径，建议在确认前面几项验证（尤其 P1-7d、Windows CI）都过了之后再做。

6. **（不需要你操作，只是在等）P1-13c Windows 读密文回退**：已派给 Windows 端的会话去做（决策 091），交回分支 `feat/dsh-p1-13c` 或 bundle 后由编排者验证合入。
