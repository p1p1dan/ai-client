# 决策 001：走 B 路线，先做 P0 探针；调研 §9 六点按建议拍板

日期：2026-09-25。来源：[DSH 二开可行性调研 §9](../../../../plans/2026-09-24-dsh-rebase-feasibility-study.md)，用户当日回复「按建议」，并追问沙箱与宿主拓扑的理由（答复记在下方各条）。

## 规则

1. **主线：B 路线。** DSH 宿主做 worker 引擎（我方 bundle 叠在 `dsh-base` 上，随包 `node.exe` 拉起），外壳、登录、额度、Git、编辑器、终端、聊天渲染层保留。先做 P0 探针（约 1.5 人周 + 1 次加密机上机），P0 退出标准任一项不过就回到本决策重议。A（fork 桌面端）与 C（自有 runtime 兼容 DSH 插件）不做，理由见调研 §0 第 4、5 条与 §4.2。
2. **兼容目标与插件来源：** 先做 L1 + L3；第三方插件走内部白名单加官方包，不开放社区自由安装；L2 等 P2 之后再议。
3. **权限：审批体验沿用我方模型**（逐次审批 + 四档 + 会话授权记忆 + bash 分析 + 拒绝清单，决策 014 / 023 / 026），移植成宿主插件，挂在 `user-approval` 的 answerer 与工具执行前拦截上。
   - 理由一：DSH 的审批只有一次性授权，没有授权记忆，用户已习惯「本会话内允许」。
   - 理由二：DSH 在 Windows 上默认用 `sandbox-windows-acl`，子进程降为低完整性令牌加能力 SID。加密驱动按进程放行明文，会不会认这类降权进程完全未知；最坏情况是沙箱里的命令全部读到密文或被拒，产品在加密机上不可用。
   - **沙箱不是否掉，而是先验证再叠加**：P0 在加密机上把 ACL 沙箱开、关各测一次（[Q002](../open-questions.md)）。通过的话，P1 / P2 把沙箱作为兜底层叠在我方审批之下；不通过就关掉。
4. **进程拓扑：P0 实测后定**（[Q001](../open-questions.md)），默认倾向所有会话共享一个宿主。
   - 现状是 ARD D4「一会话一隔离进程」，好处是一个会话崩了不影响其他会话。
   - DSH 宿主比我方 worker 重得多（Cordis + 几十个插件 + 插件管理 + 会话持久化），而且它本身就是按「一个宿主服务多个会话」设计的，官方桌面端也只起一个宿主。一会话一宿主时内存按会话数成倍涨，普通办公机开几个会话就吃紧。
   - 共享的代价是崩溃隔离：宿主一崩，所有会话一起断。缓解办法是 Main 侧自动重启宿主，会话从 DSH 事件日志恢复。
5. **pi TUI 互通：切换到 DSH 后放弃**，不再双写 pi 格式。内嵌终端改跑什么在 P2 定（[Q003](../open-questions.md)）：DSH **官方没有 TUI**（调研 §3 表格「pi 会话兼容」行），`dsh` 命令行只有 web / acp / sdk / headless 几种入口；现成的终端界面是社区的 `@deepseek-harness-tui/dsh-tui`。
6. **goal 模式：等 P1 随 DSH 引擎上**，原样使用官方 `dsh-goal`、`dsh-tool-goal`、`dsh-goal-round-driver`、`dsh-command-goal` 与 `client/ui-goal` 的交互约定；不在自有 runtime 上先做一版。runtime-hardening 的 T138 / T8 并入本计划。

## 影响

- runtime-hardening 的 D3 / D4（bash 流式与后台命令）保持暂停，由 P1 的 DSH jobs 提供；[bash 计划书](../../../../plans/2026-09-24-bash-streaming-and-background-plan.md)仅作参考。
- 1.0.x 的缺陷修复照常在自有 runtime 上做，不受本决策影响。
