# 决策 002：加密机移出 P0 门槛；P0 只看 Linux 与普通 Windows；Q001 定为共享宿主

日期：2026-09-26。来源：用户当日回复。P0-4 上机包做好后一直等加密机上机，P0-5 收口因此卡住。用户表示「先不考虑加密机，就考虑正常的 Windows / Linux 系统上能否正常使用，最后再去验证和适配加密机」，并在两个选项里选了「GitHub Actions 跑」与「共享宿主」。修订[决策 001](001-route-b-and-scope.md) 第 1、4 条。

## 规则

1. **P0 的平台门槛改为 Linux + 普通 Windows。** 加密机不再是 P0 的退出条件，挪到 P2 默认切换之前，作为最后一道验证与适配关。
   - 验证用的仍是现成的 P0-4 工具包与检查单，适配工作在那时做。
   - [Q002](../open-questions.md)（沙箱在加密机上能否叠加）跟着挪到这一关再裁决。
2. **普通 Windows 用 GitHub Actions 验证。** 在 `windows-2022` runner 上跑 P0-4 工具包与一键脚本 `run-p0-4.ps1`，不跑对照组模式。为此需要把 `feat/dsh-p0-probe` 或其派生分支推到远端，用户已随这一选项同意。
3. **Q001 定为共享宿主**：所有会话共用一个 DSH 宿主。
   - 依据是 P0-1 实测：4 个会话时，共享宿主约 181 MB，一会话一宿主约 735 MB，现状 4 个 worker 约 387 MB。
   - 代价是崩溃隔离：宿主一崩，所有会话一起断。进 P1 之前在 Linux 上补验三项（roadmap P0-6）：崩溃后自动重启并用 `agents.resume` 恢复会话；多会话同时跑回合时的事件循环延迟；带历史的会话的内存。补验中崩溃恢复这一项不成立时，回到本条重议。

## 取舍

- 放弃的保障：决策 001 原本让加密机成为 P0 的否决项，失败就在投入 P1 之前止损。现在 P1（6～8 人周）有可能在加密机不过时部分白做。最大的未知是随包 `node.exe` 加载原生 DLL、koffi 命名信号量、ACL 沙箱降权进程能否拿到明文。
- 缓解：上机包已就绪（[检查单](../topics/p0-4-encrypted-machine-checklist.md)），任何时候有上机机会都可以提前跑，不必等到 P2。结果不好就立即回到决策点，不必等排期。

## 影响

- roadmap：P0-4 改为「普通 Windows CI 实测」；新增 P0-6 共享宿主补验；P0-5 的输入改为 P0-1～P0-4 与 P0-6；加密机上机写进 P2 的前置项。
- README 硬约束第 1 条（加密机）保留为最终约束，但检验时点从 P0 改到 P2 前。
- open-questions：Q001 移出；Q002 改为挂在 P2 前的加密机关。
