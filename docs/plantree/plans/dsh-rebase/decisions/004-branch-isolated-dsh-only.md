# 决策 004：分支内直接整体替换为 DSH，不做双引擎；合入 main 即切换

日期：2026-09-26。来源：用户当日回复：「在当前分支完全可以重头开启，不需要保留两个引擎并存，因为这个分支就是拿来实验开发的，测试完毕后直接合入 main 进行无痛更新迭代」。修订[决策 001](001-route-b-and-scope.md) 第 1 条的分期与 README 硬约束第 2 条（渐进）。

## 规则

1. **不做双引擎。** 在 `feat/dsh-p0-probe` 上直接把 agent 引擎整体换成 DSH 宿主。不做「按会话选引擎」的接缝和设置开关，也不做 P2 的「默认切换」。
2. **渐进靠分支隔离实现。** main 继续维护 1.0.x，缺陷修复照常在 main 上做；本分支定期合入 main，避免漂移。测试完毕后合入 main，合入即切换。
3. **「无痛」是合入的硬门槛：**
   - 已装用户的旧会话首次打开时复制一份转为 DSH 格式，原文件不动。这样回退到 1.0.x 仍能读到旧会话。
   - 设置迁移：模型选择、权限档位、会话授权记忆。
   - CC / Codex 导入直接产出 DSH 格式。
4. **原 P2 的各项并入 P1，都在合入 main 之前完成：**
   - 加密机上机与适配，是合入前的否决关（[决策 002](002-defer-encrypted-machine-and-shared-host.md) 的「P2 前」改为「合入 main 前」）；
   - 内嵌终端去留（Q003）。
5. **自有 runtime 在分支内退役。** 先停用，把还要用的部分（权限模型等）抽出来；合入 main 前删掉 `src/runtime` 与 native worker 路径，合入后的 main 只有一个引擎。
6. **回退方式：** 合入并发版后若出问题，用户回装上一个 1.0.x 版本。旧会话因为只复制不改，仍能读到；新建的 DSH 会话在 1.0.x 里看不到。

## 取舍

- **省掉的**：引擎切换接缝、设置开关、双引擎并存期的维护与测试，以及 P2 单独一轮的切换工作。原 P1 + P2 约 9～12 人周，估计降到约 8～11 人周（粗估）。
- **放弃的**：已装用户在同一个版本里「先试 DSH、不行再切回」的能力；切换变成整版升级。
- **风险集中到合入那一刻**：加密机或迁移任何一项不过，整个分支都不能合入。缓解：加密机上机包现成，可以提前跑；迁移做成可重复的离线测试。

## 影响

- roadmap：P1 重排为「分支内 DSH 替换」；原 P2 取消，其内容并入 P1；原 P1 草案里的 P1-1（按会话选引擎）作废。
- README：硬约束第 2 条改写。
- 分支约定：本分支需尽快合入 main 的 v1.0.3 提交（分叉点 `b64f577f` 早于 1.0.3），此后定期同步。
