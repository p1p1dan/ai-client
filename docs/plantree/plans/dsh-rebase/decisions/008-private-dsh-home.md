# 决策 008：`DSH_HOME` 用应用私有目录，不与官方 DSH 共用 `~/.dsh`

日期：2026-09-26。**状态：用户 2026-09-28 批准（[决策 090](090-user-rulings-2026-09-28.md)）。** 依据：[P1-1 方案 §5 D4](../topics/p1-1-engine-cutover.md#5-需要拍板的决策点)、[决策 001](001-route-b-and-scope.md) 第 2 条、[可行性调研](../../../../plans/2026-09-24-dsh-rebase-feasibility-study.md)第 108、216 行（B 路线的 L3 验收口径是「会话格式」）。

## 规则

1. 产品的 `DSH_HOME` 是 `~/.pilab/<profile>/dsh-home`，以 0700 创建，与现有 `pi-agent` 同放在应用状态根下（`appStatePaths.ts` 注明新状态都放这里）。
2. 宿主继续拒绝使用 `~/.dsh`。
3. `AICLIENT_DSH_HOME` 覆盖项只在未打包时生效，用于开发与测试。
4. L3 按调研的 B 路线口径理解：会话格式（v4）和 profile 布局与官方一致，插件兼容。不共用目录。

## 取舍

- 不选「与官方共用 `~/.dsh`」，三个原因：
  - 版本不一致时两边会互相迁移格式，而 DSH 不支持降级。我方钉 `0.1.7-rc.2`，写 v4；官方 `latest` 仍是 `0.1.5-rc.3`，它写哪一代格式没有核实。
  - 用户层的 `cordis.patch.yml` 和 `.env` 会叠加进我方宿主，可能把我方关掉的上报行重新打开。
  - 同一个会话两边同时打开会撞内核锁。
- 不选 `<userData>/dsh-home`：与「会话数据放应用状态根」的现有约定不一致。
- 代价：用户在官方 DSH Desktop 里看不到我方会话。如果以后要互相打开，走导出 / 导入，或者合入前另议共用目录。
- 如果用户要的是字面意义上的共用目录，只需改这一个路径，外加处理上述三个风险。本决策不锁死这个方向。

## 影响

- P1-1：`DshHostProcess` 的 home 解析与权限。
- P1-3：宿主环境策略、`.env` 隔离、日志清理都以这个目录为根。
- P1-9：迁移与回装策略按这个目录写。
