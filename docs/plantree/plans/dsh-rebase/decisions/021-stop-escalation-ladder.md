# 决策 021：Stop 升级阶梯：先关这一个会话，失败才重启宿主

日期：2026-09-26。**状态：用户 2026-09-28 批准（[决策 090](090-user-rulings-2026-09-28.md)）。** 依据：[P1-3 方案 §4 D5](../topics/p1-3-shared-host.md#4-需要拍板的决策点)、T144「Stop 一定在有限时间内收尾」。

## 规则

1. t0 发 `worker.stop`。到 t0 + 10 s，界面收尾照旧：发 `stopped(forced)` 和 idle。T144 的承诺不变。
2. 与此同时走阶梯 A：对这个会话做会话级 dispose，限时 3 s。
   - DSH 会把已经流出的正文作为 interrupted 落盘，并释放会话锁。
   - 成功就在同一个宿主上重开这个会话，其他会话不受影响。
3. A 失败就走阶梯 B：立即优雅重启宿主。
   - 先优雅关停 3 s，其他会话在飞的正文同样落盘为 interrupted；不退再 SIGKILL。
   - 然后按宿主崩溃流程恢复所有会话，被牵连的会话收到 `engine_restarted`。
4. P1-4 落地后，评估改用「种子分叉续聊，不动宿主」（方案里的 C）。

## 取舍

- 不选「等其他会话空闲再重启，最多等 60 s」：升级到 B 只在 DSH 自身有缺陷时发生，很罕见；而且那段时间里卡住的会话不能用。
- 代价：
  - 其他会话在飞的回合会被中断，需要用户手动继续。
  - 取消收不了尾时，会话级 dispose 可能同样等不到（两者都等 `whenIdle`），这时 A 大多会超时，直接落到 B。这一点还没验证，由 P1-3e 实测。

## 补记（2026-10-07，决策 155，实现取舍待审批）

- P1-3e 实测（[决策 151](151-p1-3e-stuck-switch-choices.md) 第 5 节第 1、2 条）：
  - 「取舍」第 2 点成立：取消收不了尾时，阶梯 A 的会话级 dispose 也等不到。
  - 第 3 条在卡点位于 DSH 内部时不成立：宿主的优雅关停也在等卡住的会话，3.5 s 收不了尾，宿主被 SIGKILL，其他会话已流出的正文全部丢失。
- 按用户裁决（[决策 149](149-user-rulings-2026-10-07.md) 第 6 条），由 [决策 155](155-ladder-b-dispose-others-first.md) 修：
  - Main 重启宿主之前，先对其他在忙的会话并发发 `worker.dispose`，总共最多等 3 s，再走第 3 条的优雅关停；
  - 被提前关闭的会话照旧收到 `engine_restarted`，与其他会话同一批恢复；
  - 第 1、2 条和界面 10 s 收尾不变；阶梯 B 最坏多 3 s。
