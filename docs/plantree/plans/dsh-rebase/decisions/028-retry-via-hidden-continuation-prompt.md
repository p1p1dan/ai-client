# 决策 028：DSH 下「重试上一轮」追加一条用户看不到的续跑提示（偏离决策 045 字面，请重点审批）

日期：2026-09-26。**状态：自主决定，待用户审批。** 依据：[P1-4 方案 §5 D3](../topics/p1-4-bridge-parity.md#5-需要拍板的决策点)、[runtime-hardening 决策 045](../../runtime-hardening/decisions/045-failure-card-continue-retries-last-turn.md)、[分片 04](../topics/p1-4-bridge-parity/04-turn-semantics.md)。

## 规则

1. 只有同时满足以下条件才受理：会话空闲，且最后一个 `turn/end` 是 `error`、`interrupted` 或 `aborted`。否则在发出任何事件之前抛 `WORKER_RETRY_UNAVAILABLE`，渲染层沿用 045 的处理：把提示放回输入框，由用户确认。
2. 受理后，以 followup 追加一条续跑提示，`source.kind` 为 `aiclient-retry`。这条提示模型看得到、用户看不到：历史投影把它隐藏，也不回显气泡。然后发 `running`。
3. 不分叉。DSH 把失败的尝试记为 `assistant/attempt`，本来就不进模型上下文，这一轮已完成的工具轮也都还在。

## 与决策 045 的对照

- **做到的**：
  - 不重复发送用户那条提示；
  - 已完成的工具轮保留，不会重做写文件、跑命令；
  - 失败的回复不进模型上下文，但仍留在日志里可以查看；
  - 用户界面上的行为与 v1.0.3 一致。
- **偏离的**：
  - 045 写的是「不追加新的 user 消息」「模型拿到的正是失败那次请求的上下文」。DSH 开新回合，首批至少要有一条消息；首批为空时直接判回合完成（`dsh-agent-loop` `:963-965`）。所以模型会多看到一条很短的续跑提示。

## 取舍

- 备选 B：用 `agent/request-error` 把失败的请求挂起，等用户点「继续」。好处是不加消息；问题是挂起期间回合一直算在跑，占着忙锁，崩溃后也续不上。
- 备选 C：分叉到失败回合之前，重发原消息。这会丢掉已完成的工具轮，违反 045 的核心理由。
- **如果用户要求严格不加消息，改用 B，并接受它的脆弱性**，在 P1-4c 开工前定。
