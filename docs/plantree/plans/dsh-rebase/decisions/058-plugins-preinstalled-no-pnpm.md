# 决策 058：白名单插件在构建期预装进安装包；去掉 pnpm，关掉插件管理两行（收口决策 016）

日期：2026-09-27。**状态：自主决定，待用户审批。** 依据：[P1-10 / P1-16 方案 §5 D2、D3](../topics/p1-10-p1-16-extensions.md#5-需要拍板的决策点)。

## 规则

1. 白名单插件写成宿主子包的精确版本依赖，构建期按锁文件的 `integrity`，由 `npm ci` 装进 `resources/dsh-host/node_modules/`，与 `@aiclient/dsh-app` 同路。用户机上不跑任何包管理器，也没有安装入口。
2. `DSH_HOME` 里只记启用了哪几个。宿主每次启动，按「产品 bundle +（已启用 ∩ 白名单）」重写 profile 清单，这是决策 025 第 5 条 bundles 重申的扩展。
3. 去掉 pnpm（约 −16 MiB，Q007 少一项）；关掉 `plugin-manager`、`tool-plugin-manager` 两行；profile 用户层不参与组合。**[决策 016](016-pnpm-ships-for-now.md) 由本决策收口。**
4. 插件随应用版本整体升级；peer 兼容在构建期对钉住的 DSH 核一次。插件与宿主同样做 B 档裁剪，一起计入 128 MiB 的硬上限。单个插件默认上限 5 MiB / 500 个文件，超出需单独批准。

## 取舍

- 不选「随包 tarball，首启用 pnpm 离线装」：多一个首启失败面，还要随包带 pnpm。
- 不选「运行期从内部源装」：用户机要联网并写用户目录（P0-2 的问题）。
- 代价：上新插件要发版；插件字节全部计入安装包；以后若要运行期安装，得另立决策。
- 开工前做实验 E1：关掉插件管理两行、profile 用户层不参与组合后，宿主照常启动。
- 实验 E2：插件作为宿主依赖时，npm 的 peer 解析会不会报 `ERESOLVE`。E2 需要联网，在构建流程里做。
