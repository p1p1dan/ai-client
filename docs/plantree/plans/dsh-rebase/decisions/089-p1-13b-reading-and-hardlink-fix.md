# 决策 089：P1-13b 判读，DSH 新建文件改为不走硬链接

日期：2026-09-28。**状态：自主决定，待用户审批。** 依据：[P1-13b 摘要](../evidence/p1-13b-encryption-matrix-2026-09-28.md)、[决策 084](084-p1-13-round1-reading.md) 第 2、3 条。

## 结论

1. **新建文件不加密，主要是 DSH 引入的回退，由我们在宿主里修。**
   - DSH write 新建文件时，先写临时文件，再用硬链接发布到目标名：51 个类型**全部不加密**；
   - 1.0.x 的写法（node.exe 直接按目标名新建）和「先写临时文件再改名」都是 22 个加密、29 个不加密；
   - 所以 DSH 的写法比 1.0.x 多出 22 类不加密。按决策 084 第 2 条，这是回退，**合入前必须修掉**。
2. **修法：新建时改为直接按目标名、以排他方式创建（`wx`），不再用硬链接。**
   - 位置：`@deepseek-ai/dsh-fs-local` 的 `writeFileAtomic` 在 `createIfAbsent` 分支调用 `internals.linkFile(tempPath, absolutePath)`（DSH 0.1.7-rc.2，`lib/index.js` 约第 551 行）。
   - 做法：由宿主给这个钩子换一个实现：用 `wx` 打开目标名，把临时文件的内容写进去再关闭。
     - DSH 原本的「不覆盖并发创建者」语义不变：目标已存在时 `wx` 报 `EEXIST`，照样走 DSH 的 `throwGuardedCreateFailure`；
     - 代价：写的过程中，别的进程可能看到一个只写了一半的文件；
     - 1.0.x 一直是直接写，没有原子性，所以这不比 1.0.x 差。
   - 首选宿主插件在启动时设置 fs 服务的 `internals.linkFile`，不改 DSH 的包文件；做不到时，退回构建期补丁。两种做法都要加一条静态守卫：DSH 升级时，调用点或参数一变，就构建失败。
   - 只在 Windows 上换；Linux、macOS 保持 DSH 原样。
   - 登记为 roadmap 的 **P1-13c**，下一轮上机时验证：新建文件的加密结果要与 1.0.x 一致（22 类）。
3. **node.exe 读不出 9 类文件，不是 DSH 的问题，交给用户和 IT。**
   - 这 9 类是 yml、rb、php、ps1、cmd、sql、scss、docx、pptx。Node 与 Electron 读到的都是密文，1.0.x 用的是同一个 node.exe，所以现在就有同样的问题。
   - 产品侧没法绕：换 PowerShell 读也不行，它读 md、java 等反而是密文。
   - 这不否决 DSH 路线，因为 DSH 没有让它变差。但它说明「读写全部明文」这个目标在这台机器的现行策略下达不到，需要 IT 给 node.exe 补上这些扩展名。见 [Q009](../open-questions.md)。
4. **载体继续叫 `node.exe`（维持决策 084 第 3 条）。**
   - 读取的解密与进程名无关；
   - 新建 `.js` 是否加密与进程名有关，而且 node.exe 这个名字恰恰让 `.js` 不加密；
   - 改名会改变写入时的行为，而且测不全，所以不改名。
5. **会话日志不加密的问题维持现状。** `.jsonl.zstd` 由 DSH 新建，修掉硬链接以后会不会加密，下一轮一起看；1.0.x 的会话日志也是 node.exe 新建的。

## 取舍

- 另一种修法是整个关掉原子写，但 DSH 改已有文件走的是 `ReplaceFileW`，第一轮实测改完仍加密，没必要动。这次只换新建的路径。
- 不采用「新文件先复制一份已加密文件再覆盖」这类绕法：复制与覆盖的结果和直接新建差不多（22～27 类），却要多维护一个模板文件。
