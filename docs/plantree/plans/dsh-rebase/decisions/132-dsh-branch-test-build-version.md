# 决策 132：DSH 分支 CI 测试包的版本号用 `1.1.0-dsh.N`

日期：2026-09-29。**状态：自主决定，待用户审批。**

依据：[决策 130](130-user-rulings-2026-09-29-batch3.md) 补充裁决（推送分支并跑 Windows CI 已授权）；用户 2026-09-20 的要求「手动推送（随后要打包）前先升版本号，单独一个 chore 提交」。

## 背景

本机不能整包构建（2 核 / 3.3 GB，`pnpm build` 两次弄崩系统），所以推送后手动触发 `build.yml`，在 CI 上整包构建并跑打包冒烟 L1。`workflow_dispatch` 只上传构建产物，不建 Release。

分支的 `package.json` 版本还是 `1.0.3`，与已发布的 1.0.3 同名。产物文件名和版本串都来自这里；同名的两个安装包只能靠 SHA256 区分，09-18 已经踩过一次。

## 决定

1. 推送前把版本升到 `1.1.0-dsh.1`，单独一个 `chore` 提交；以后本分支每次要打包的推送递进 `N`。
2. 选 `1.1.0-dsh.N` 的理由：
   - 按 semver，它比 `1.0.3` 新，装在 1.0.3 上是正常升级；
   - 比以后 main 发的 1.0.x 修复版都新，测试机上的自动更新不会把 DSH 测试包换回 1.0.x 引擎；
   - 用 `1.0.3-*` 或 `1.0.4-*` 都不行：前者比 1.0.3 旧，后者等 1.0.4 发布后会被自动更新替换掉；
   - `dsh` 标签让文件名一眼看出是本分支的包，不和 main 的 `-test.N` 混。
3. 这只是测试包的版本号，不是发版决定。正式合入 main 后发什么版本号，由用户在 P1-14 定。

## 待用户确认

- 如果你想用别的版本号（例如 `2.0.0-dsh.N`，或沿用 `-test.N`），告诉我，下一次打包前改。
