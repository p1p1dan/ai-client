## 规则

### 问题 1：回退后被回退的提示回到输入框

1. **递给这个对话，而不是递给屏幕上的输入框。** bridge 给出的 `editorText` 由会话分支对话框放进 `composerDrafts` 的 `offered[sessionId]`。输入框只在这个对话正显示在里面时取走它；回退结果返回前用户已经切到别的对话的，文字等那个对话回到输入框时再放进去，不会进到别的对话。
2. **输入框里已有内容时：接在后面，中间空一行，不覆盖。** 输入框为空（或只有空白）时直接放入；已有文字时变成「原有文字（去掉末尾空白）+ 空行 + 被回退的提示」。用户打的字一个不少，被回退的提示也不丢，用户删掉不要的那段即可。代价：若用户不看就按 Enter，两段会一起发出。没有选「保持原样、提示用户」，是因为那需要新的提示界面，而且被回退的提示就此找不回来；没有选「覆盖」，是任务要求不覆盖。
3. **只递文字。** bridge 的 `editorText` 只有文字；被回退的那条提示当初带的图片或附件不会回来，要用户重新添加。
4. 对话框回退后仍然开着（维持原行为），关掉后就能看到输入框里的文字。回退到回答（不是提示）时 bridge 不给 `editorText`，输入框不变。

### 问题 2：新建分叉打开时时间线为空

5. **根因**：Main 建分叉时依次发出 `session.created`、同一请求号的 `session.history`（`initial`，分叉点之前的内容）和 `idle`。渲染层的 `initial` 页只认「恢复」登记过的水位（`session.resumed`），`session.created` 从不登记，于是这一页被当作过期页整页丢掉，要等下次冷启动走 `readPage` 才看得到。
6. **改法**：`session.created` 带请求号时也登记水位，分叉自带的这一页就按原有的历史页路径合并进来。没有另起一套，也不多一次 IPC。普通的首次发送也会登记，但它不带历史页，下一次恢复会覆盖这个水位，行为不变；别的请求号的 `initial` 页照旧被拒。
7. **没选的方案**：分叉物化后再走一次侧栏的激活路径（对宿主里的分叉做一次温恢复，让它重发历史）。多一次往返，空态会闪一下，而且温恢复要求渲染层给的目录与宿主记的逐字相同，多一个失败点。
8. 分叉的历史事件可能先于 `materializeForkedChatSession` 到达（行还没建）。消息按对话 id 存，不依赖行，两种先后顺序结果相同，已有单测。

### 问题 16：回收后再点开，回合的「已工作 N 秒」与「完成于」消失

9. **根因**：直播消息本身没有日期（红线 store 不存时间），回合时钟只在 `useMessageMetadata` 的组件状态里，而且只收当前对话的事件。点「新建」时中栏显示开始界面，时间线整个卸载，再点回来时登记表是空的。所以不只是容量回收：只要中间经过一次开始界面就会丢；在别的对话里时结束的回合，也从来没被记下。
10. **改法**：登记表移到 `stores/messageMetadataRegistry.ts`，按对话分开，一个监听器收所有对话的事件；`ChatWorkspace` 在整个运行期持有监听（引用计数，单独挂载的时间线也会持有一份）。回退时清掉该对话的时间戳（分支换了）；对话从列表消失时一并清掉。
11. **重启后**：重开的对话走 `readPage`，历史行带日志写下的日期（`timestamp` / `settledAt`），原有的 `replayedSpanMetadata` 兜底照旧生效，用时与完成时间都在（第 1 批 A1 已验证）。**优先用历史数据**的含义在这里：凡是历史行，一律用历史日期；只有从未经过历史回放的直播消息才用运行期登记表。
12. **仍取不到的（写清楚，不修）**：
    - 回合行里的「思考 N 秒」来自另一个按挂载保存的登记表（`useTurnTiming`），本次没改，时间线重新挂载后直播回合的思考时长仍会消失；历史回放本来就不带思考时长，所以重启后也没有。见遗留问题。
    - 窗口打开时回合已在进行（没收到用户消息的 `message.started`），这一轮没有起点，只能显示「已工作」而没有秒数，与改动前相同。
    - 窗口重载（不重启应用）后，直播登记表清空；重开对话时走预览或温恢复，拿到的是带日期的历史行，所以仍然有。

### 问题 25：迁移中提示与迁移失败卡画在时间线顶部

13. **挪到时间线末尾**：在所有回合和「待送达」回合头之后、「会话失败」卡之前，也就是与失败卡同一处，紧挨输入框。这两样通常是用户刚做的事的结果（在旧对话里发送会触发迁移；迁移或打开失败会在这里说明原因），而用户做这件事时就在底部。空对话里顶部与底部是同一个位置，不变。
14. **不另加自动滚动**：时间线原有的「贴底跟随」会把末尾新出现的卡带进视野（发送时本来就会滚到底）。用户自己往上翻着看时不会被拉下来，这与「会话失败」卡一致。
15. **代价**：这张卡也用于「加载更早的消息」读取失败（`read_failed`），那种情况下按钮在顶部、卡在底部，用户若停在顶部要往下看才看到。这种失败少见，统一放底部换来的是发送类失败一定看得见。

### 问题 33：输入框草稿不分对话

16. **草稿按对话保存与恢复**：切换对话时，把输入框里的文字与附件停放在离开的对话名下，取回要去的对话停放的草稿（没有就是空的）。只有空白的不停放。没有选中对话的开始界面也有自己的一份。用布局副作用做切换，新对话不会有一帧显示旧对话的文字。
17. **只在内存里**：草稿不跨重启保存，与没发送过的对话一样；附件（含图片的 base64）也只在内存里。对话从列表消失（删除、归档、工作区同步剔除）时它的草稿一并丢弃。
18. **分叉带草稿不变**（T-27）：目标条上换工作区触发的分叉，草稿整份跟到新对话，原对话不留一份。会话分支对话框里的「从这里分叉」不带草稿：原对话的草稿留在原对话，分叉是空的。
19. **失败回填按所属对话走**：发送失败把消息退回输入框（D1 与 D15 的回填、T135「没有可重试的回合」的回填），如果用户已经切到别的对话，就放进原对话停放的草稿，规则仍是「只放进空的」；不会放进屏幕上别的对话的输入框。
20. **Retry 快照带上所属对话**：`retryable` 记下失败发生在哪个对话，只在那个对话显示在输入框时才出现 Retry。之前发送在用户切走后才失败时，Retry 会出现在另一个对话，点了就把原对话的消息发到那里。现在这种 Retry 留给原对话，用户切回去时出现；在原对话里已经显示的 Retry，离开时照旧清掉。
21. **两处「清空输入框」只清自己对话的**：插话（Ctrl+Enter）的 IPC 期间用户切走了，只从原对话停放的草稿里拿掉已发出的文字与附件；`/archive`、慢的 `/compact` 结束时输入框已经换成别的对话，就不去清屏幕上那个对话的草稿，改为丢掉原对话停放的命令文字。
22. **已知边界**：粘贴或选文件的附件还在读取中时切换对话，读完的附件会落到切换后的对话里（读取流程只认当前列表）。这个窗口很短，没有处理。

### 问题 28：缺 `piLeaf` 的 1.0.x 行文件被删后发送

23. **选「走正常的 `source_missing` 失败卡」，删掉修复路径。** 以前 Main 把「没有 `piLeaf` 且文件不在」当作「1.0.x 只预留了文件名、从没写过」，把行改成一个新的空 DSH 会话（`recordCreated` + `createSession`）。
24. **理由**：
    - 这个判断不可靠：`piLeaf` 这个字段出现之前的版本留下的行，确实写过对话，也没有 `piLeaf`。对这种行，「修复」等于悄悄换成一个空会话，模型丢掉全部上文，用户却不知道。任务点验里的 L5 正是用户刚看过完整预览、文件随后被删的情形。
    - 与 `ChatComposer` 已有的原则一致：已知的会话文件是权威，文件缺失、损坏时不能悄悄换成新会话。
    - 与带 `piLeaf` 的行（L7）一致：同样的「保存这个对话的文件已经不在磁盘上」卡，消息退回输入框，提示新建对话。
    - 修通的做法（让恢复接受以「创建」作答）要改渲染层的恢复等待和 Main 的返回值，改完之后上面第一条的问题依然在。
25. **代价**：真正「只预留、从没写过」的行（很早的开发版才会留下）现在打开或发送时显示 `source_missing` 卡，用户要新建对话，而不是像以前设计的那样无感地变成新会话。这类行没有任何内容可丢，卡上的说法（文件不在、请新建对话）对它们也成立。
26. `SessionIndexService.clearUnwrittenRuntimeIdentity` 只被这条路径使用，一并删除，免得留一个能抹掉行身份的无人调用的写入口。
