## 2. 自主决定（待用户审批）

### #10 检查更新报代理连接失败

1. **保持跟随系统代理，遇代理类错误改直连重试一次**。`updaterSession` 在「更新也走代理」未勾选时用 `{ mode: 'system' }`（`ProxyConfig.applyProxy`），系统里残留失效代理（代理软件已退出但系统代理未清）就直接失败且不回退。
2. 新增 `useDirectForUpdater()`（把更新会话切 `direct`）与 `isProxyConnectionError()`（识别 `ERR_PROXY_CONNECTION_FAILED` / `ERR_SOCKS_CONNECTION_FAILED` / `ERR_TUNNEL_CONNECTION_FAILED`，大小写不敏感——错误文本是 electron-updater 包装过的，不是我们的类型）。
3. **只对「检查更新」重试，不对下载与安装重试**。下载/安装是用户在检查已经证明可达之后按下的按钮，中途换掉会话是意外而不是补救。
4. 重试只做一次：`proxyRetryAt` 在重试前置位、成功后清空、失败后才报错，所以一个持续坏掉的代理是「每次检查一次重试」，不是「每次检查一次重试再加每次错误事件一次」。
5. 两条失败路径（`autoUpdater` 的 `error` 事件与 `checkForUpdates()` 的 promise rejection）都走同一个 `handleFailure`，避免两处各决定一次要不要重试。

### #11 模型目录只在启动时同步一次

6. **每小时同步一次**（`CATALOG_SYNC_INTERVAL_MS`），**窗口重新获得焦点且距上次尝试超过 15 分钟时再同步一次**（`CATALOG_SYNC_FOCUS_MIN_INTERVAL_MS`）。数值照搬更新检查的形态（那里是 4 小时 / 30 分钟），差异理由是模型目录这个问题更便宜、过时得更快。
7. 焦点间隔（15 分钟）**短于**服务自身的 10 分钟新鲜度窗口是有意的：那个窗口管「不重复拉取」，这个管「连问都不问」，一次会被缓存吞掉的询问也是一次多余的 IPC 往返。
8. 新增 `src/main/services/piModelConfig/syncScheduler.ts`（`CatalogSyncScheduler`），**从 `main/index.ts` 启动时挂到主窗口**。非 forced 同步，所以服务自己的 TTL 仍然生效；重叠触发去重（慢同步期间的下一次直接返回，不排队）。
9. **单独一个模块**的理由与 `managedCredentialsStartup.ts` 相同：`main/index.ts` 有模块加载期的 electron 副作用，vitest node 环境里导入会挂死；这个模块只把 `BrowserWindow` 当类型用，所以「焦点事件值不值得同步」这些判断可以在 node 环境里测。

### #12 模型目录同步失败静默回落旧缓存

10. **这条与 #10 不是同一个原因，因此不采纳 issue 里「代理失败时直连重试」的建议**。模型同步走的 `net.fetch` 在应用内代理开关关闭时本来就是直连，不受系统代理影响；issue 描述里的「系统代理残留」在这里基本不会触发。
11. **新增「有目录但回退了」这一档失败记录**：`PiModelSyncFailure.withCatalog`。`rememberSyncOutcome` 过去只记「没拿到目录」与账号类错误，瞬时的 wire 失败被有意丢弃——理由是「红卡压在能用的应用上」正是 `chatEmptyState.ts` 存在要避免的东西。**这条理由仍然成立**，所以 `withCatalog` 为真的失败**不弹恢复卡片**（`piModelSyncNoticeView` 加了对应守卫，账号类失败照旧弹），但**必须被记住**，否则就回到了 issue 抱怨的「静默」。
12. 记忆下来的这一档在**两处**露出：**模型菜单的状态行**加「上次成功同步：<时间>」（`CatalogStaleness.since`，`bundled` 没有这个时间——它从未被本机拉取过，编一个出来是撒谎）；**设置 → 模型管理**在状态块上方显示一句黄色告警加原始诊断。
13. **模型按钮上加一个小黄点**（`catalogStaleness` 返回非空时为真）。菜单里的那句话只有打开菜单的人才读得到，而从没打开过菜单的人正是提出这条 issue 的人。`aria-hidden`，因为触发器的可访问名已经带上了同一句话。

### #13 临时对话位置与命名

14. **「临时对话」从置顶改为列表最底**（在所有仓库与临时工作区之后），推翻决策 183 §1.2 的置顶裁决。理由：没有仓库的对话是列表上最不具体的一组，而一个永久占用的首位会在每次新建临时对话时把仓库推下去。
15. **「临时对话」与「临时工作区」不合并**：前者是不属于任何仓库的对话，后者是旧功能建的临时目录，两者是不同东西。
16. **设置里的「临时会话」区块改名为「临时工作区」**（`i18n.ts` 里该区块的全部词条：标题、说明、默认目录、自动创建、重命名 / 删除对话框等）。这个开关实际只控制临时工作区，命名与实际行为改到一致。代码标识符（`temporaryWorkspaceEnabled` 等）**不改**——它们本来就叫 workspace，这次只是把中文文案对齐过来。

### #14 折叠 / 展开按钮字号

17. **新增 `--text-group-label` 13px 档**，只给侧栏分组标签（仓库名与「临时对话」）用；`text-group-label` 同时注册进 tailwind-merge 的 `font-size` 组。
18. **放宽 D25 的 CJK 下限，只对侧栏分组标签这一级生效**。对话行、辅助行、按钮仍是 14px。理由是分组标签短、它管的对话行才是要读的正文，降一档正是让它退到后面去。
19. **不采用「保持 14px、从颜色和字重上减轻」**：用户在两轮预览里看过 14px 的灰字标签，判断它压在自己管的对话标题上偏重——分组标签的颜色已经是 `muted-foreground`（最轻的一档），再轻只能动字号。

### #15 归档模式（第一期）

20. **模式一（按工作目录，默认）按仓库的添加时间排序，新的在上**，取代决策 170 的活动时间排序。活动排序会在任何地方的对话结束一个回合时重排列表——文件夹可能从指针下面移走，而几周没碰过的仓库无论用户怎么想它都会沉到底。
21. `Repository` 新增 `addedAt?: number`。**旧的仓库在加载时按它当前在数组里的位置补时间戳**（`Date.now() - (length - index)`），所以列表不会在开始按这个字段排序的那一刻重排。`handleAddRepository` 写入 `Date.now()`。
22. **没有时间戳的仓库按它在数组里的位置排序**（`orderFoldersByAddedAt` 里用负值位置当兜底），而不是排到最前或最后——数组里靠后 = 添加得晚（新增是追加），这正是这个顺序要的事实。
23. **模式二（按分组）第一期只有一个固定的「未分组」组**，所有对话（含临时对话与临时工作区里的）都在里面，组内按最近运行时间排。这与 issue 里写的「有一个默认分组，所有新对话默认丢在里面」一致。`buildUnassignedFolder` 与未来的用户自建分组共用同一个形状（同一套标题、折叠、8 条上限、搜索行为），第二期替换成用户分组时不必换一种东西。
24. **模式开关是工具行的一个图标按钮**，不是两个中文标签的分段控件：280px 的面板里已经有搜索框和两个按钮，「按工作目录」/「按分组」的中文标签会占掉大半。当前模式在提示与可访问名里，图标说明将要得到的是哪个列表。
25. **渲染分支互斥**：`groupingByGroup` 时仓库树整体不渲染（`renderUnassignedGroup()` 取代 `visibleFolders.map(...) + renderTemporaryGroup()`）；`showAddRepositoryEmptyState` 的「添加仓库」空态照旧优先——一个仓库都没有时没有东西可分。
26. **给会话行加右键「跳转到工作目录」**（`onJumpToWorkspace`，走 `shell.openPath` 打开目录本身，与仓库行的「在资源管理器中打开」同一实现）。**没有本地目录的行不显示这一项**：临时对话没有，远程仓库的虚拟路径 `openPath` 会直接 reject。
27. **删除了 `deriveFolderLastActivity` 与 `orderFoldersByActivity`**。它们是决策 170 的产物，本次改动把生产调用点全部换掉后成了孤儿，按工程规范一并删除（测试同步改写成按添加时间的语义）。

### 其他

28. **`applyHeldFolderOrder` 保留**。它的原目的是「指针在列表里时不重排」，在稳定的添加时间顺序下几乎不再触发；但「**全部折叠 / 全部展开**」的组集合也跟着它走，且它是决策 170 已批准的行为，本次不顺手删（删它会让「指针在列表里时顺序被冻结」这个已批准的行为消失）。
29. **本轮不推送、不发版**。按分支规则，推送前需用户确认。

## 3. 第二期与已知难点（待讨论）

1. **拖动归类比看起来麻烦**，至少四处要一起解决：
   - 列表现在是「一行一个 `role="button"`，单击即打开对话」；拖动要引入拖拽层与放置目标，并且要和「点击打开」区分开（按下即拖还是移动阈值后拖），否则误拖会被读成误点。
   - 列表在一个 `ScrollArea` 里，拖动到视口外需要自动滚动，跨滚动容器的原生 DnD 在 Electron 里行为不一致，用指针事件自绘更可控但工作量更大。
   - 折叠的分组是有效的放置目标吗？折叠状态下看不见落点，要么拖动时自动展开，要么只认标题行。
   - 「未分组」组是所有对话的默认去处，把它当普通分组还是当「移出分组」的语义，影响右键菜单与拖出的行为（拖出分组 = 回到未分组的可能性）。
2. 备选做法（第二期开工前与用户确认）：**先做右键「移到分组 ▸」菜单**，它不需要拖动层、能覆盖全部归类需求，拖动作为后续增强；或者拖动只支持「拖到另一个分组的标题上」这一种手势，不做组内排序。
