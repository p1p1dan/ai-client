# 决策 204：SDK 宿主铸的消息 id 带宿主标记，对话重开后回复不再画进旧行

日期：2026-10-19（北京时间）。**状态：自主决定，待用户审批。** 小修，只动路线 B（Agent SDK 引擎）的宿主，DSH 不变。

分支：`claude/nostalgic-panini-61c8bb`，从 `main`（`19f6f5ef`）开出。编号 204 已在决策编号登记表登记。

修订关系：

- 路线 B [S-6 反馈 13](../../claude-sdk-engine/topics/s6-feedback.md)（Ctrl+Enter 插话后回合错位、「只有已工作没有正文」）：症状相同，**原因不同**。那次是回合错位，这次是 id 撞车；回合逻辑本次不动。
- [决策 145](145-p1-7e-e6-choices.md)（空闲回收发 `released`，渲染层只解绑、保留屏幕上的消息）：不变。本决策正是在它保留旧行的前提下，让新宿主不再与旧行撞 id。

## 1 现象

用户 2026-10-19 报告（Windows，1.1.1-test.1，claude-opus-5-5）：一个 SDK 对话 11:48 回复完，14:05 在同一对话发新消息。进度先是「工作中 xx 秒 ↑xx token」，然后变成「工作中 xx 秒」，最后只剩「已工作」，没有正文。重启应用后这段回复正常显示。

## 2 证据（用户机器上的转写与日志，原件不入库）

- CLI 每个新进程的第一条请求，转写里 `api-request` 行的 `base` 为空。这个会话共有三处：01:53Z（09:53 新建）、03:23Z（11:23）、06:12Z（14:12，用户重启应用之后）。14:05 那条（06:05:45Z）的 `base` 不为空，说明它和 11:23 起的是同一个 CLI 进程，即第二个宿主。
- 转写里唯一一条 `cost-state`（CLI 退出时写）：`startTime` 是 09:53:33.85，`totalDuration` 5,051,031 ms，即 11:17:45 退出；最后一次活动是 11:01:49，相差约 16 分钟，与 Main 的 15 分钟空闲回收加 1 分钟巡检间隔吻合。
- 应用日志 11:13:39 有一行「new chat on the Claude Agent SDK engine」：用户新建了另一个对话。窗口的占用（`claimEntry`）随之转走，这个对话成了无人占用，于是被空闲回收。
- 第一个宿主跑过 3 个回合（t1 6 步、t2 2 步、t3 17 步）。第二个宿主的回合编号又从 1 开始：11:23 是 t1，11:38 是 t2，14:05 是 t3，共 3 步，id 为 `cc-<会话前8位>-t3-s1..s3`，全部落在第一个宿主 t3 已经用过的 id 上。

## 3 原因

1. 宿主的计数器（`turnCount`、`userMessageCount`）在每个宿主进程里从 0 开始，消息 id 由会话 id 前 8 位加计数器拼成：`cc-user-<n>`、`cc-<sid8>-t<回合>-s<步>`，后台唤醒回合的 requestId 是 `cc-turn-<sid8>-<n>`。同一个对话重开后，新宿主铸出的 id 与旧宿主的完全相同。
2. 渲染层在空闲回收（`released`）时故意保留屏幕上的消息（决策 145）。重开时 `session.history` 的合并（`historyReplayMerge.ts`）只能按文本折叠纯文本行；带工具的行折不掉，原样留在时间线里，仍用旧 id。SDK 的历史行不带 `liveMessageId`，所以 DSH 那条按 id 精确折叠的路走不到。
3. 新回合的 `message.started` 碰到已存在的 id，`upsertMessage` 就地替换那条旧行，随后的思考、正文、工具都画进时间线上方的旧位置。新用户消息下面没有任何助手行，回合结束只剩「已工作」。重启后时间线全部按 CLI 转写重新投影（`h:` id），所以恢复。
4. 11:23、11:38 两个回合的前几步应该也被吞了（第一个宿主的 t1、t2 各有 6、2 步带工具的行），只是后面还有新步骤，不容易看出来。14:05 这一回合只有 3 步，全部撞上，所以正文整段不见。

不是 CLI 空闲期间自己退出或重连，也不是后台任务唤醒打开了引擎回合：转写里 11:48 到 14:05 之间没有任何行，CLI 进程也没换。

## 4 规则

1. 每个 `ClaudeSdkSessionRuntime`（即每个宿主进程）启动时取一个 6 位十六进制标记（`randomUUID()` 前 6 位），写进它铸的每个 id：
   - 用户回显：`cc-user-<标记>-<n>`（块 id 仍是消息 id 加 `-text`）；
   - 模型步骤与本地命令回复：`cc-<sid8>-<标记>-t<回合>-s<步>`；
   - 后台唤醒回合的 requestId：`cc-turn-<sid8>-<标记>-<n>`。
2. 计数器的含义与步骤号解析（`-s(\d+)$`）不变；问题卡 id（`cc-question-<toolUseId>`）本来就唯一，不动。
3. 录制规整（`tools/event-normalize.ts`）的两条 id 规则接受可选的标记，已入库的录制样本不用重录。

## 5 取舍

- 不选「重开时按转写把计数器续上」：要从转写数出宿主曾经算过的回合与步骤（本地命令回复、引擎回合、插话合并都会让两边数法不同），数错一个就又撞。随机标记不依赖任何对齐。
- 不选「渲染层遇到已存在的 id 时另起一行」：`message.started` 就地替换是其他路径（DSH 的重放、本地命令）依赖的语义，改它影响面大；问题出在宿主铸的 id 不唯一，就在宿主修。
- 没做「SDK 历史行带 `liveMessageId`，重开时按 id 精确折叠」：那样重开后带工具的旧行也能换成历史行、不再重复显示，但要让实时 id 与转写身份一一对应（用 API 消息 id、用户消息 uuid），改动大，列为后续。本决策之后，这些旧行仍留在原位（与修改前相同），只是不再被新回合覆盖。
