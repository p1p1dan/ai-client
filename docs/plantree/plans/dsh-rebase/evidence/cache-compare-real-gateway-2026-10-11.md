## 5 结论：第 2 步重写从哪里来

1. **触发点在我们的请求字节**：
   - pi-ai 的 Anthropic 转换把最后一条用户消息改成带 `cache_control` 的文本块（`@earendil-works/pi-ai/dist/api/anthropic-messages.js:1066-1085`），较早的用户消息照常以纯字符串发出（`:935-940`）。
   - 于是同一条消息在相邻两个请求里写法不同。每个回合的第 2 步，正是上一请求的最后一条（本回合的用户输入）第一次「不再是最后一条」的时候。
   - 受控对比（同一网关会话、同一上游）：B 原样发送，在这 5 个位置丢缓存；Bn 只改一处，把用户消息固定成块，就一个都不丢；C1（Claude Code 写法）也一个都不丢。Claude Code 的网关文档也明确要求不要把块形式的内容转成字符串。
2. **丢多少由网关选中的上游决定**：X 类容忍这种切换（A 本轮丢 4 token）；Y 类每轮退回一个断点（数百到一千多 token）；Z 类（dsh.11）每轮退回到约 32k 的 system 级前缀（1～2.4 万 token），同时还多出 1.2 万～2.7 万 token 的未知提示。Z 类的放大与那段多出的提示都在客户端之外，本轮复现不了，也就无法进一步归因。
3. **为什么官方 CLI / SDK 看不到**：Claude Code 在每个请求里都保持消息内容为块形式，只移动断点（C1 复现了这一点）。直接用 SDK 的人通常也是整段块数组追加。只有「最后一条转成块、其余是字符串」这种 pi-ai 写法才会撞上。
4. **客户端侧的盲点**：宿主的前缀监视（决策 173 / #9）按设计把字符串和单个文本块视为相同，所以一直报「纯追加」。在 Y / Z 类上游上，这个假设不成立。

建议（待决策，本次没有改代码）：

- 让发出的每条用户消息在所有请求里保持同一种写法，最简单是一律块形式。可以在宿主的请求钩子里规范化（它已经在改写请求体加 `metadata.user_id`），或给 pi-ai 打补丁。
- 前缀监视把「写法变化」单独标出来。
- 把 Z 类现象（首步多出的提示、退回到 32k）连同运行面板的诊断转给网关管理员。
