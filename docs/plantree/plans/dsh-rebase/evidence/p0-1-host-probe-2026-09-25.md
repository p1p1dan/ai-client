# P0-1 宿主骨架与资源探针（2026-09-25，Linux 开发机）

Role: evidence。对应 [roadmap P0-1](../roadmap.md)，为 [Q001](../open-questions.md) 提供数据；B 路线依据见[决策 001](../decisions/001-route-b-and-scope.md)。原始数据（去掉本机路径）在同目录 [p0-1-host-probe-2026-09-25.data.json](p0-1-host-probe-2026-09-25.data.json)，由 `src/dsh-host/measure.ts` 生成。

## 结论先行

1. **能走，没有硬阻塞。** 在纯 Node 上用 `dsh-app-boot` 启动「`dsh-base` + `@aiclient/dsh-app`」。Node 用的是 v24.18.0，与随包 `node-runtime` 同版本，没用 Electron。
   - 94 行组合出来，85 行全部激活，9 行按配置关闭，0 行失败或挂起。
   - 能建会话，也能正常停：退出码 0，不残留进程。
   - 启动和建会话阶段不派生任何子进程，没有 DNS 查询，没有出站连接。
2. **数字（中位数，页缓存热）：**

   | | DSH 宿主 | 我方 native worker |
   |---|---|---|
   | 启动到可用 | 0.74 s（ready 后再建第一个会话约 10 ms） | 0.21 s（bootstrap 本身就建好会话） |
   | 空载内存 | RSS 177 MB / PSS 149 MB | RSS 94 MB / PSS 71 MB |
   | 1 / 2 / 4 个会话 | 在空载基础上 +2.9 / +4.5 / +4.7 MB RSS | 一个进程只装一个会话 |

3. **Q001 建议选共享宿主：一个应用实例只起一个 DSH 宿主，由 Main 负责崩溃后自动重启。**
   - 同一宿主里再开一个空会话几乎不花内存，成本几乎全在宿主本身的约 180 MB。
   - 一会话一宿主时，4 个会话实测 RSS 735 MB，是共享宿主（约 181 MB）的 4 倍，也是我方现有架构（4 个 worker 共 387 MB）的 1.9 倍。
   - 详见[§Q001 建议](#q001-建议)。
4. **加密机新增两项待测（写进 P0-4 检查单）：**
   - **启动依赖原生 addon。** `dsh-app-boot` 用 `node-addon-require-builtin` 访问 Node 内部加载器，默认先把 `.node` 复制到缓存目录再加载，Windows 上缓存目录是 `%LOCALAPPDATA%`。
   - **会话写锁依赖原生模块。** Linux 走 `node-addon-system` 的 flock。Windows 按 DSH README 的说法走 koffi（FFI）命名信号量，本次在 Linux 上没法实测。

## 方法

- **机器与纪律**
  - 开发机 2 核 / 3.3 GB，内核 7.0.0-31。
  - 每次测量前，脚本扫 `/proc`，确认没有 vitest 进程才开始，测量串行跑。
  - 没起 Electron 和 GUI，没调任何模型或 provider。网络只用过 npm registry，而且只在安装时用。
- **载体**
  - 版本：随包 Node 钉在 `scripts/node-runtime-pin.mjs` 的 `NODE_RUNTIME_VERSION = '24.18.0'`（CI `build.yml` 打包用的也是这个 pin）。
  - 本次二进制：工作树的 `out-node-runtime/node` 是一个软链，指向主检出里已经下载好的 linux-x64 v24.18.0，来源是 nodejs.org 的 tarball，见 `PIN.json`。
  - 系统 Node 是 v22.23.2，只用于 `npm install` 和 diskcold 模式的驱动进程。diskcold 要驱逐 v24 二进制的页缓存，驱动进程就不能跑在同一个二进制上。
- **对照组**
  - 用本工作树的 `node scripts/build-agent-host.mjs` 构建 `out-agent-host/worker.js`，产物 84.1 MiB。工作树没装依赖，构建时临时软链了主检出的三份 node_modules（与 lockfile 逐项一致），构建完即删。
  - 启动方式与 `PiWorkerProcess.ts` 的 Windows 打包分支一致：`spawn(node, [worker.js], stdio 带 ipc)`。
  - 请求沿用 `scripts/packaged-worker-smoke.cjs` 的 `worker.bootstrap` 载荷。模型指向 `127.0.0.1:9` 的假 provider，只 bootstrap，不发 prompt。
- **隔离**
  - 每次运行新建 `/var/tmp/aiclient-dsh-probe-*/<label>/{home,tmp,dsh-home,workspace}`，权限 0700。
  - 用 `/var/tmp` 而不是 `/tmp`：本机 `/tmp` 是 tmpfs，写进去会占内存。
  - 环境变量走白名单：只放 `PATH`、`LANG`、`HOME`、`USER`、`LOGNAME`、`SHELL`、`TMPDIR`，再加引擎自己需要的变量。开发机 shell 里的任何密钥都进不来。
  - 另设 `DSH_TELEMETRY_DISABLED=1`。
  - `host.ts` 拒绝未设置的 `DSH_HOME`，也拒绝指向真实 `~/.dsh` 的 `DSH_HOME`（用账户数据库里的 home 判断，不看 `HOME` 变量）。
- **插桩：** 两边都加 `--import lib/probe-hooks.mjs`，做三件事。
  - 非回环的出站连接：先记录，再直接断开。
  - 记录每次 `dns.lookup`。
  - 记录所有 `child_process` 调用（异步和同步都算）和 `worker_threads`。

  另外两路补充：
  - `/proc` 每 250 ms 采一次进程树，并存下 `ps -o pid,ppid,etime,rss,cmd` 快照。
  - 单独跑一轮 `strace -f`，抓 `execve` 和各种写文件的系统调用。这一轮的计时不采用。
- **口径**
  - **ready**
    - DSH：从 spawn 算到 `host.ts` 在 `boot()` 返回后经 IPC 发出 `ready`。此时插件树已全部结算，启动审计也已通过。
    - worker：从 spawn 算到 `worker.bootstrap` 成功返回。worker 一个进程一个会话，所以这个时间已包含建会话。
  - **启动的几种「冷」**
    - 冷启动：用空的 `DSH_HOME`，首次初始化 profile 和目录。
    - 热启动：复用冷启动第 1 轮的 `DSH_HOME`，里面已有 4 个会话落盘。
    - 以上两种情况下，引擎文件都在页缓存里。
    - 磁盘冷：先用 `posix_fadvise(DONTNEED)` 驱逐引擎全部文件和 node 二进制的页缓存再启动，每次驱逐掉 100～156 MB 页缓存。
  - **内存**
    - ready 后静置 8 s，每秒采一次、共 10 次，取中位数。指标是 `VmRSS`，同时记下 `smaps_rollup` 的 `Pss` 和 `VmSwap`。全程 swap 为 0。
    - 会话按 1 → 2 → 4 递增，每一档静置 4 s 后采 5 次。
  - **会话：** 由 bundle 里的 `aiclient-probe` 插件调用 `ctx.agents.create()`，路由取 `agentDefaultModel.currentSelection()`。不发 prompt。

复现命令（仓库根目录起）：

```bash
(cd src/dsh-host && npm install)          # 依赖与 package-lock.json；Node 用系统 v22 即可
pnpm build:agent-host                      # 对照组 worker（需根 / src/agent-host / src/runtime 依赖）
cd src/dsh-host
../../out-node-runtime/node measure.ts run --cold 3 --warm 5 --worker 5 --out /var/tmp/p0-run-final.json
../../out-node-runtime/node measure.ts parallel --n 4 --out /var/tmp/p0-parallel.json
../../out-node-runtime/node measure.ts trace --settle 3000 --samples 3 --out /var/tmp/p0-trace-final.json
/path/to/other/node measure.ts diskcold --n 3 --settle 2000 --samples 2 --out /var/tmp/p0-diskcold.json
../../out-node-runtime/node measure.ts smoke --no-expose-internals --host-env NARB_DISABLE_NATIVE_CACHE=1
# 单独起一个宿主（stdout 打 ready JSON，Ctrl+C 停）：
DSH_HOME=$(mktemp -d) DSH_TELEMETRY_DISABLED=1 ../../out-node-runtime/node --expose-internals host.ts
```

## 宿主怎么接起来

- **子包 `src/dsh-host/`（`@aiclient/dsh-host`，private）**
  - 仿照 `src/runtime/` 的独立 npm 子包形态，有自己的 `package.json`、`package-lock.json`、`tsconfig.json`。
  - 它的 `package.json` 就是 app-boot 的 installation anchor。
  - 直接依赖：`dsh-base`、`dsh-app-boot` 以及 app-boot 的几个 peer（cordis 系列、`dsh-home-paths`、`dsh-launch-environment`、`dsh-system-prompt`），另加本地的 `@aiclient/dsh-app`（`file:./bundle`）。
- **bundle `src/dsh-host/bundle/`（`@aiclient/dsh-app`）**
  - 与官方 `sdk-app` 同一形态：`dsh.bundle.patch` 指向 `cordis.patch.yml`，`lib/index.js` 是插件，peer 依赖 `@deepseek-ai/cordis ~4.0.4`。
  - patch 关掉四行：
    - `session-telemetry-otel`：launcher 另外设了 `DSH_TELEMETRY_DISABLED=1`，`readProfilePatches` 会再追加一次同样的 disable，等于双保险。
    - `deepseek-account`（`dsh-deepseek-account-platform`，DeepSeek 平台浏览器登录）。
    - `llm-deepseek-account`：账号路由的 LLM 适配器，没有账号提供方就是空壳。这一行是任务单之外多关的。
    - `hmr`：worker 引擎靠重启拿配置，与 sdk-app 的取舍一致。
  - patch 插入一行 `aiclient-probe`。它在 Node IPC 上提供 `create-session` / `close-session` / `stats` 三个请求，是将来 `aiclient-bridge` 的占位。
  - **`host/webserver` 和 `host/frontend-static` 是 `dsh-web-app` 里的行，`dsh-base` 里根本没有。** 我们的 profile 不叠 web-app，所以这两行本来就不存在，谈不上关掉。`host.ts` 在任何插件导入之前，会在组合结果上断言这两行（按 id 和包名都查）确实不在，并断言上面四行都是 `disabled: true`。
- **launcher `src/dsh-host/host.ts`**
  - 以 `@deepseek-ai/dsh/profile-boot` 的 `runProfile` 为蓝本，也就是官方 Desktop 宿主走的那条路。去掉了代理、命令行和 bin 相关的部分，只用 `dsh-app-boot` 的公开导出。步骤：
    1. `resolveProfileDir('aiclient', DSH_HOME)`
    2. `initProfile(dir, ['@deepseek-ai/dsh-base', '@aiclient/dsh-app'])`
    3. `loadProfileDirectory`，有 bundle 被跳过就直接失败
    4. 写空根配置 `cordis.yml`，内容为 `[]`
    5. `createRuntimeResolution`
    6. `readProfilePatches`（依次叠 bundle 层、profile 层、home 层和遥测开关）
    7. 静态审计
    8. `installFailLoud`
    9. `boot(bin, root, patches, prepare)`：`prepare` 里挂 logger exporter，把 warn/error 打到 stderr（`dsh-base` 没有控制台日志行）；`provide('profileContext')`；`provide('launchEnvironment', loadLayeredEnv())`；`plugin(PluginPackages, { resolution })`
    10. 激活普查
    11. IPC 发 `ready`
  - 停止有三个触发：IPC `shutdown`、SIGTERM/SIGINT、父进程断开（防止留下孤儿引擎）。停止时 `ctx.fiber.dispose()` 后自然退出。如果 3 s 后还有句柄没释放，就打印句柄清单并强制退出。本次全部运行都没走到强制退出这一步。
  - `profileContext` 必须提供，否则 `dsh-base` 里 `plugin-manager`、`config-editor`、`settings` 三行的 `disabled` 表达式会把它们关掉，而 P0-2 的 `llm-pi-ai` 需要 `settings`。
  - 不提供 `cmdlineArgs`：`dsh-base` 里没有哪一行注入它，只有各模式 bundle 的 startup 行才要。
- **组合结果（Linux）**
  - 94 行，其中 85 行 active，9 行 disabled，0 行 inactive。
  - Loader 普查报 86 个 active，多出的一个是 app-boot 自己挂的根 `cordis:include` 条目（id `include`）。
  - 字面值关闭的 7 行：`tool-plugin-manager`、`hmr`、`deepseek-account`、`session-telemetry-otel`、`skill-badge`、`tool-ralph`、`llm-deepseek-account`。
  - 按平台表达式关闭的 2 行：`pwsh-sandbox`、`tool-pwsh`。
  - Windows 上则反过来，关的是 `bash-sandbox` 和 `tool-bash`。

## 子进程清单

**启动加 4 次建会话的整个过程中，DSH 宿主没有派生任何子进程。** 三种方法结论一致：

- `/proc` 每 250 ms 采一次进程树：宿主进程之下没有任何进程。`ps` 快照里只有 `node --expose-internals --import …/probe-hooks.mjs …/host.ts` 这一行。
- 进程内钩子：`spawn`、`spawnSync`、`execSync`、`execFileSync`、`worker_threads` 的记录都为空。
- `strace -f` 抓到的 `execve` 只有 node 自己一次。native worker 对照组同样只有这一次。

也就是说，启动阶段没有 pnpm、git、python、shell，也没有别的 node 进程。plugin-manager 虽然处于激活状态，启动时并不调 pnpm。

**要注意，本次没有覆盖工具执行。** bash / pwsh（走 node-pty，Windows 上是 conpty）、搜索、git 等要等 P0-2 真跑回合时才会出现，届时要用同一套插桩再抓一次子进程。

## 宿主写到 DSH_HOME 之外的文件

来源是 strace 抓到的写类系统调用，包括 `openat`（带写标志）、`mkdir`、`rename`、`link`、`unlink`。

| 位置 | 写了什么 |
|---|---|
| `$DSH_HOME`（39 项） | `profiles/aiclient/{package.json, cordis.patch.yml, cordis.yml, pnpm-workspace.yaml}`；`sessions/<按 cwd 生成的目录名>/<sessionId>/{session.lock, session.v4.jsonl.zstd}`，先写 tmp 再 `link` 成正式文件；`storages/session_projcache/sessions/<id>.json` |
| `$TMPDIR` | ① `node-addon-native-custom-loader-<uid>/native-cache/node-addon-require-builtin-linux-x64-gnu/0.1.6/…/linux-x64-gnu-napi-v9.node`，是原生 addon 的副本，随后从这里加载；② `dsh-spill-XXXXXX/`，spill-local 放大段工具输出的根目录 |
| `$HOME`（沙盒） | 无 |
| 其他任何位置 | 无 |
| 我方 worker | 只写 agentDir 下的 `sessions/*.jsonl` 和 `*.writer.lock`，另建了 trace 目录 |

读取方面值得注意的有四处：

- `<cwd>/.env` 和 `$DSH_HOME/.env`：`loadLayeredEnv` 会把项目目录下的 `.env` 当作环境层读进来，见风险第 3 条。
- 宿主自己的可执行文件：native loader 读它来判断 libc。
- `/etc/resolv.conf` 和 `/etc/nsswitch.conf`：DNS 模块初始化时读的，并没有真正发起解析。
- 本轮没有读取任何 `$HOME` 下的点文件，也没有从子包之外的 `node_modules` 加载过模块。唯一例外是 `ws` 找可选依赖 `bufferutil` 时，逐级向上探到了主检出的 `node_modules`，结果是 ENOENT。

本轮实际加载的原生模块（Linux）：`node-addon-require-builtin`（启动时，从缓存副本加载）和 `@deepseek-ai/node-addon-system`（会话首次落盘时的 flock）。worker 没加载原生模块。

## 意外与风险

1. **启动离不开原生 addon，`--expose-internals` 反倒不是必需的。**
   - `dsh-app-boot` 的 profile 运行时解析（`internalModules()`）固定通过 `node-addon-require-builtin` 拿到 Node 内部的 ESM/CJS 加载器，不走 `--expose-internals`。
   - 去掉 `--expose-internals` 实测照常启动：85 行全部激活，约 750 ms。这个参数只影响 vendored loader 的优先路径和 HMR，而 HMR 我们已关。
   - 这个 addon 默认先复制到缓存目录再加载，以免 DLL 被锁住。Linux 上缓存目录是 `$TMPDIR/node-addon-native-custom-loader-<uid>`，**Windows 上是 `%LOCALAPPDATA%\node-addon-native-custom-loader\native-cache`，落在 `DSH_HOME` 之外**。
   - 在加密机上，「node.exe 写出 DLL，再 LoadLibrary 加载它」这条链路是否可行，目前未知。
   - 可控开关：设 `NARB_DISABLE_NATIVE_CACHE=1` 就原地加载，本次已实测，Linux 上照常启动且不再写缓存目录；也可以用 `NARB_NATIVE_CACHE_DIR` 改缓存位置。
   - **P0-4 必须加一项**：宿主在加密机上经 node.exe 启动，缓存开、关各测一次。
2. **写会话和执行工具要用到更多原生模块。**
   - DSH README（`packages/session/session-persistence-jsonl/README.md`）写明，Windows 上会话写锁是命名内核信号量，由 koffi（FFI 原生模块）实现。Linux 上用的是 `node-addon-system`，本次已实测加载。
   - `fs-local`、`subprocess-local` 也依赖 koffi；bash / pwsh 工具走 node-pty。npm 包里附带 win32-x64 的 `conpty.node`。
   - 这些原生模块在加密机上都要经 node.exe 实际加载一遍。本次只能在 Linux 上验证 Linux 那一套。
3. **项目 `.env` 会被读进宿主环境。** `loadLayeredEnv` 读 `<cwd>/.env`。在我方产品里，cwd 就是用户的仓库，而 DSH 的凭据链路会用环境层里的 `DEEPSEEK_API_KEY` 这类变量。P1 要决定是不读项目层，还是由 Main 传入显式的环境快照。
4. **安装体积大。**
   - 340 个包、248 MB（du）、21.7k 个文件；对照组 `out-agent-host` 是 84 MiB、12.5k 个文件。
   - 大头：`@opentelemetry` 36 MB（遥测虽已关，但它是 `dsh-base` 的依赖，照样装上）、`@img/sharp-*` 28 MB、`node-pty` 26 MB（带全平台 prebuilds）、`@deepseek-ai` 20 MB、`openai` 17 MB、`@google` 14 MB、`@anthropic-ai` 14 MB。
   - 打包时需要按平台裁剪 prebuilds。如果加密机需要对落盘文件做 TSD 处理，文件数量是个成本。
5. **`plugin-package-inventory-deepseek` 会把已装插件清单附在 DeepSeek 官方 API 请求里**，只对 `deepseek-official` 路由生效。P1 的 bundle 建议关掉。
6. **默认路由是 `deepseek-official/deepseek-flash`。**
   - 这来自 `agent-default-model` 行。`agents.create()` 不校验凭据，所以没有 key 也能建会话。
   - P0-2 必须在 `llm-pi-ai` 的 settings 里配置我方网关，并改默认路由，否则第一个回合就会打到官方。本次没有发任何请求。
7. **spill-local 会检查 spill 根目录是否安全。**
   - 起因：本机 umask 是 002，最初建的沙盒目录是 0775，组可写，spill-local 报 `skipped unsafe root …` 并停用 spill。改成 0700 后正常。
   - Windows `%TEMP%` 的 ACL 能否通过这项检查，要放进 P0-4 一起看。否则大段工具输出没有落盘位置。
8. **多个宿主共用一个 `DSH_HOME` 不是 DSH 公开支持的形态。**
   - 本次 4 个宿主共用时，空会话没有出错。
   - 但 DSH 的 `storage-domain` README 写明，变更通知只在单进程内可见（Single-process change visibility）。
   - 会话写锁是跨进程的（flock 或命名信号量），能防止两个宿主同时写同一个会话。但 plugin-manager、config-editor、settings 的写入没有跨进程协调。
   - 这是一会话一宿主方案额外要付的代价。
9. **没接 WorkerSlot。** 约束要求不改 `src/main`，所以本次由测量脚本当 supervisor。它的拉起方式与 `PiWorkerProcess` 的 Windows 分支同形：node 加 `ipc` stdio，IPC 用 Node 自带的 `process.send`，与 `createNodeProcessWorkerTransport` 同一通道。真正接进 WorkerSlot 是 P0-3 的事。
10. **Node 模块解析会越出子包目录。** 这次看到的是 `bufferutil` 向上探到了主检出。打包后宿主应放在独立目录，例如 `resources/dsh-host/`，避免意外解析到应用自身的 `node_modules`。

## Q001 建议

实测值与外推值对照如下。外推一律按实测斜率计算，并标明「外推」。

| 会话数 | 共享 DSH 宿主 | 一会话一 DSH 宿主 | 现状：一会话一个 native worker |
|---|---|---|---|
| 1 | RSS 约 179 MB | 约 179 MB | 约 94 MB |
| 4 | **约 181 MB（实测）** | **735 MB RSS / 533 MB PSS（实测，4 个并行）** | **387 MB RSS / 229 MB PSS（实测）** |
| 8 | 约 185 MB（外推，按每会话约 1 MB） | 约 1.47 GB RSS / 约 1.07 GB PSS（外推） | 约 770 MB RSS（外推） |
| 第 N 个会话就绪要多久 | 第一个约 0.75 s（宿主启动）加 10 ms，之后每个 3～15 ms | 每个 0.73～0.95 s；4 个同时起要 2.0 s（2 核） | 每个约 0.2 s；4 个同时起要 0.43 s |

**建议：共享宿主。** 一个应用实例起一个 DSH 宿主，所有会话都挂在上面。这与决策 001 第 4 条的默认倾向一致。理由：

- **成本在宿主，不在会话。** 宿主基线约 177 MB，每多一个空会话约 1～3 MB。一会话一宿主相当于每个会话都重复付一次基线；4 个会话就比现状多出 350 MB 左右，8 个会话接近 1.5 GB，放在普通办公机（以及这台 3.3 GB 的开发机）上吃不消。
- **启动时间同样如此。** 共享宿主只在第一个会话时付一次约 0.75 s（磁盘冷时约 0.95 s），之后新会话基本瞬时完成。一会话一宿主则每个新会话都要等将近 1 s，恢复多个会话时在 2 核机器上会排队。
- **DSH 本身就是按「一个宿主服务多个会话」设计的**，官方 Desktop 也只起一个宿主。多宿主共用 `DSH_HOME` 反而踩到它没有承诺的区域（风险第 8 条）。
- **代价是失去崩溃隔离。** 缓解办法：Main 侧 supervisor 在宿主退出后自动重启（本次测得重启本身约 0.75 s，停止约 45 ms），会话再通过 `ctx.agents.resume()` 从事件日志恢复。

需要在 P0-2 或 P1 补验证的条件：

1. 宿主崩溃后自动重启，并用 `agents.resume` 恢复多个会话，要能可靠恢复到正确状态。本次只测了起和停，没有测 resume。
2. **事件循环争用。** 宿主是单线程 Node，一个会话的重 CPU 工作（压缩、大结果处理、JS 实现的搜索）会拖慢其他会话的流式输出。P0-2 跑两个会话并发回合时，要测事件循环延迟。
3. 带历史的会话占多少内存。本次只测了空会话，长会话的增量两种拓扑都要付，但共享宿主下没有基线的倍增。

不建议把「一会话一宿主」作为默认。可以保留为逃生口，例如需要不同 profile 或不同 `DSH_HOME` 的特殊会话，等 P1 按需要再议。

## 局限

- 只测了 Linux 开发机。Windows 的冷启动还会叠加 Defender 实时扫描，这部分要在 P0-4 上机时顺带记录。
- 只测了空会话，没有发回合，也没有执行工具，所以子进程清单只覆盖「启动加建会话」。
- 磁盘冷启动用 `posix_fadvise` 驱逐页缓存来模拟，不等同于重启后的完全冷态。
- 页缓存热时，冷启动和热启动差别不大。这说明 `DSH_HOME` 的首次初始化很便宜，不代表首次安装后的首次启动也很快。
