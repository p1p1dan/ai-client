# P0-3 最小 bridge：DSH 会话接进现有 worker RPC（2026-09-25，Linux 开发机）

Role: evidence。对应 [roadmap P0-3](../roadmap.md)。事件来源沿用 [P0-2 的事件表](p0-2-goal-and-plugins-2026-09-25.md#宿主发出的事件p0-3-映射的输入)。截图、GUI 结果和无界面 smoke 的原始输出都在 [p0-3-gui-2026-09-25/](p0-3-gui-2026-09-25/)。

## 结论先行

1. **三件事在开发机 GUI 里都走通了，渲染层一行没改。** 打开开发开关 `AICLIENT_DEV_ENGINE=dsh` 后，一个聊天会话改由 DSH 宿主来跑：
   - 助手正文是真流式：12 次采样里，已画出的正文长度从 10 个字逐步涨到 85 个字；
   - 一个 bash 工具行先显示「运行中」，5 秒后变为「已完成」；
   - 审批卡在我方的 PendingPermissionDock 里弹出，点「直接允许」后文件写成功；另一次点「直接拒绝」，文件没有写，工具行标「已拒绝」。
   - 两次的模型请求都只打到本地假网关，共 9 次，全部来自 DSH 宿主，全部带假 key。
2. **接缝选的是 (a)。** 开发开关打开时，Main 在 `createPiWorkerSlot` 里改拉 DSH 宿主进程（随包 node），不拉 native worker。宿主里新增的 `aiclient-bridge` 行加载**原封不动的** `PiWorkerRpcServer`，再用一个实现同一接口的 `DshSessionRuntime` 顶替 `NativeWorkerRuntime`。
   - Main 看到的仍然是同一套 worker RPC 和 RuntimeEvent。
   - 产品代码只改了 `src/main` 的两处：新增 `devDshEngine.ts`，`createPiWorkerSlot.ts` 加一个受开关保护的分支。
   - 开关不开时，走的是与原来完全相同的调用。
3. **DSH 事件 → RuntimeEvent 的映射表、缺口和有损点**见下文，供 P1 使用。P0 的主路径全部够用：文本、工具、审批、回合结束、停止。缺口集中在五块：
   - 历史 / 树 / 分叉 / 回滚；
   - 用量；
   - 思考块的起止；
   - goal / todo / 后台任务通知这类 DSH 独有的事件；
   - 权限档位。
4. **审批方面：** DSH 只在模型申请越出沙箱时才发 `approval/request`，这条路已经接进我方的权限卡。P1 要做逐次审批，必须在 DSH 的 `tools/pre-execute`（执行前拦截点）上挂我方的权限插件，复用本次同一条 permission RPC 通道（见「审批与 P1」）。

## 接缝选择

| | (a) 宿主里的 bridge 插件讲 worker RPC（**采用**） | (b) 在现有 worker 里以进程内方式起 DSH |
|---|---|---|
| 进程 | 宿主**替代** worker：Main → DSH 宿主（随包 node），只有一跳 | Main → worker（开发态是 Electron utilityProcess）→ DSH 在 worker 进程内 |
| 能不能跑在白名单载体上 | 能。任何平台上宿主都跑在随包 node 上，和 P0-1 / P0-2 的测量条件一致 | 开发态和 macOS / Linux 打包态跑在 Electron 上。DSH 的运行时解析要改写 Node 内部的模块解析器（`--expose-internals` 或原生 addon），DSH 桌面端在 Electron 上为此专门加了参数；而且解析器是**进程级**的，会影响同进程里我方 runtime 自带的 cordis、pi-ai 这些同名包 |
| 翻译层 | 在宿主进程内直接订阅 DSH 服务：`session/event`、`agent/assistant-stream`、`approval/request`。不需要第二套私有协议 | 同样是进程内，但 worker 里要同时装两套引擎 |
| 对 `src/agent-host` / `src/runtime` 的改动 | 无。`PiWorkerRpcServer` 被原样 import | 要改 `worker.ts` 的分派逻辑，还要处理两套依赖并存 |
| 对 Main 的改动 | 在 `createPiWorkerSlot` 里多一个拉起分支 | 无，但打包时 worker 会带上 DSH |

选 (a) 的理由：只有这一种形态能在所有平台上都让 DSH 跑在随包 node 上，这是加密机的硬约束；同时引擎、翻译层和 RPC 服务端都在同一个进程里，链路最短。代价是 Main 多了一个开发开关分支，由单元测试覆盖。

**落地形态：**
- `src/main/services/agent-host/devDshEngine.ts`：
  - `isDevDshEngineSelected()` 只在 `AICLIENT_DEV_ENGINE=dsh` **且** app 未打包时为真；读不到 `app` 时一律当作关闭。
  - `buildDevDshHostLaunch()` 负责组装启动参数：
    - 命令：用随包 `out-node-runtime/node`，可用 `AICLIENT_DSH_NODE` 覆盖；参数是 `--expose-internals src/dsh-host/host.ts`。
    - 工作目录：`DSH_HOME`（默认 `<userData>/dsh-home-dev`，可用 `AICLIENT_DSH_HOME` 覆盖）。这是 P0-2 的结论：宿主启动目录下的 `.env` 会流进工具环境，所以不能用用户仓库当启动目录。
    - 环境变量：白名单，不继承任何 `ANTHROPIC_*` 或其他密钥。
- `src/dsh-host/host.ts` 的桥接模式（`AICLIENT_DSH_BRIDGE=1`）：
  - 从文件第一行起缓冲所有 IPC 消息，因为 Main 拉起进程后立刻就发 `worker.bootstrap`，而 Node IPC 在还没有监听者时会直接丢消息。
  - 这个模式下只有 worker RPC 走 IPC，ready 信息改写到 stderr。
- `@aiclient/dsh-app` 的 `aiclient-bridge` 行（`bundle/lib/bridge.js`）：
  - 开关打开时，这一行启用，P0 测量用的 `aiclient-probe` 行关闭。
  - 它认领缓冲区，并用原样的 `PiWorkerRpcServer`（`src/agent-host/piWorkerRpcServer.ts`）加 `DshSessionRuntime`（`src/dsh-host/bridge/dshSessionRuntime.ts`）来服务这条通道。
  - 收到 `worker.dispose` 后宿主退出；父进程断开时宿主自行退出。
- 会话身份：`bootstrap` 返回的 `sessionFile` 是 `$DSH_HOME/aiclient-sessions/<dsh 会话 id>.dsh.json` 这个小桩文件。Main 需要一个持久文件作会话键，重新拉起时把它传回来，桥接层读桩文件后改用 `agents.resume`。**恢复这条路本次没有测。**

**对 Q001（共享宿主）在 P1 意味着什么：** 现在是一会话一宿主，因为 worker RPC 按 slot 设计，一个进程只 bootstrap 一次。改成共享宿主时有三点：
- `DshSessionRuntime` 可以原样复用：它已经按 DSH 会话 id 过滤 `session/event`、`agent/assistant-stream` 和 `approval/request`，一个宿主里并存多个实例不会串。
- 要改的是**传输层**：
  - Main 对一个宿主进程开多条虚拟通道：消息带上 slot 键，或者复用现有 generation 字段再加一个会话键；
  - 宿主侧按 slot 各起一个 `PiWorkerRpcServer` 加 `DshSessionRuntime`；
  - WorkerSlot 的「进程退出 = slot 崩溃」语义要拆开：关一个会话只 dispose 这个 runtime，宿主进程崩溃则所有 slot 一起崩，由 Main 重启宿主，再逐个 `agents.resume`。
- 翻译层不用重写，重写的是 WorkerManager 和 WorkerTransport 里「一个 slot 对应一个进程」的那一层。

## 映射表：DSH → RuntimeEvent

事件来源分两类：持久会话事件（`session/event`，可以回放）和进程内实时事件（Cordis 分发）。每条 RuntimeEvent 都带上 `sessionId`（我方的逻辑会话 id）和当前回合的 `requestId`。

| DSH 来源 | 发出的 RuntimeEvent | 说明 |
|---|---|---|
| `worker.send`，bridge 自己处理 | `session.status running` | 然后调用 `agent.followup(createUserMessage({source:{kind:'user'}}))` |
| `session/event` `user/message`，且消息 id 等于本轮 followup 的 id | `message.started`（role user，带 `attemptId`）+ `message.delta` + `message.completed` | 权威回显，renderer 靠 `attemptId` 撤掉乐观气泡。runtime context 快照、goal 续跑提示等其他 user 消息不回显 |
| `agent/assistant-stream` 的 `start {turn, step}` | `message.started`（role assistant，`model` = DSH 路由） | messageId = `dsh-<会话>-t<turn>-s<step>`，与持久事件共用同一个键 |
| 流 chunk `text-delta` | `message.delta`（blockId = `…-b<index>`） | 真流式：P0-STREAM 的 20 块到 renderer 合并成 17 条 delta |
| 流 chunk `reasoning-delta` | `thinking.delta` | 不发 `thinking.started` / `completed`（缺口） |
| 流 chunk `tool-call-delta`（首个带 name 的） | `tool.started`（input 为 `{__streaming}`） | 与 native 的流式工具行同形 |
| `session/event` `assistant/message` | 把流里缺的正文补发成 `message.delta` | 用于兜底，比如某次尝试没走流 |
| `session/event` `tool/call` | `tool.started`，已开始过则发 `tool.updated`，都带完整参数 | 另加 `path` 作为 DSH `file_path` 的别名，只加不删；否则我方工具行显示不出文件名 |
| `approval/request`（waterfall） | `permission.requested`：`decisions: ['allow','deny']`、`kind` / `action` / `detail`（file_change 或 exec）、`reason` = DSH 的升级理由 | 等 `worker.permission.respond` 返回后发 `permission.resolved`，再回给 DSH `allowed-once` / `rejected` / `cancelled`；DSH 撤回请求时自动拒绝并标 `autoReason: aborted` |
| `session/event` `tool/result` | `tool.completed`：`ok = !isError`，`output` 或 `error` 是**纯文本** | 有损，见下 |
| `session/event` `step/end` | `message.completed` | |
| `session/event` `turn/end` | `completed` → `session.completed`；`aborted` → `session.stopped`；其他 → `session.failed`（带原因）；三种情况都再发 `session.status idle` | |
| `session/event` `turn/start`，且不是 bridge 发起的回合 | 合成一个 requestId，发 `session.status running` | 用于 goal 续跑轮和后台任务完成通知开出的回合 |
| `worker.stop` | 发 `session.status stopping`，再调 `agent.cancel({kind:'user'})` | 由随后的 `turn/end aborted` 收尾 |

无界面 smoke 里的实际序列（节选）：

```text
TOOL: session.status running | message.started user | message.delta | message.completed |
      message.started assistant | tool.started bash | tool.updated | tool.completed ok=true | message.completed |
      message.started assistant | message.delta | message.completed | session.completed | session.status idle
DENY: … tool.started write | tool.updated | tool.completed ok=false (沙箱拒绝) | message.completed |
      message.started assistant | tool.started write | tool.updated | permission.requested write |
      permission.resolved deny | tool.completed ok=false | message.completed | … | session.completed | session.status idle
```

**缺口：没有映射的部分，P1 要补。**
- **会话读写**：`history` / `tree` 返回空；`commands` 返回空列表；`compact` / `rewind` / `reload` / `fork*` 直接报 `WORKER_DSH_UNSUPPORTED`。重开会话时时间线会是空的。要补就得读 DSH 会话日志，把它投影成 `SessionHistoryPage`，这对应 L3 会话格式那部分工作。
- **`usage.updated`**：没发。DSH 有 `token-meter`、`request/context` 这类数据可用。
- **`permission.activity`**：没发，所以时间线上看不到权限审计行。
- **`question.requested`**：没接。`dsh-base` 默认不挂 ask 工具，不过 `user-questions` 服务是有的。
- **`preview.requested` / `subagent.activity` / `custom.message`**：都没接。其中后台任务完成通知现在被当成一个合成回合处理，而不是一条 custom 消息。
- **DSH 独有、我方没有对应类型的事件**：`goal/change`、`todo/write`、`command/run|done`、`approval/asked|decided`（后两者只写日志）。P1 要给渲染层补 goal 条和 todo 卡时，需要新的 RuntimeEvent 类型，或者 custom 事件。
- **权限档位与模式**：`setPermissions` / `setPermissionGear` / `setPermissionTier` 目前什么都不做。我方的「执行 · 每次询问」这类档位没有映射到 DSH 的沙箱模式，也没有映射到审批策略。
- **`interject`（Ctrl+Enter 插话）**：固定返回 `false`。DSH 有 `steer`，可以对接。

**有损点：**
- 工具结果被压成纯文本。DSH 的 content 块里可能有图片，结果里也没有带结构化 `details`（例如文件改动的 review、`refused` / `stopped` 标记）。
- bash 非零退出码在 DSH 里 `isError=false`，只在正文末尾写 `[exit code: N]`，所以我方的工具行会显示为成功。
- 审批卡只有「允许 / 拒绝」：DSH 只有一次性授权，所以不提供「本会话内允许」，也没有倒计时。
- 卡片文案沿用 `write_file` 这个动作 id，渲染出来是「写入工作区文件」，而实际目标在工作区**外**（路径本身会正确显示在文件行里）。P1 需要给「申请越出沙箱」单独一个动作 id。

## 审批与 P1

- **DSH 的规则：** `workspace-write` 模式下，沙箱内的 bash 和文件操作一律不问；越界操作直接拒绝，并在结果里提示模型「可以带 `sandbox_permissions` 重试一次」；只有模型真的带着 `sandbox_permissions` 和 `justification` 重试时，才会发 `approval/request`。本次两张卡都属于这种情况：第一次 `write` 被沙箱拒绝，第二次带升级参数才出卡。
- **本次已经打通的：** `approval/request` → `permission.requested` → 我方卡片 → `worker.permission.respond` → `permission.resolved` → 回给 DSH 的应答结果。整条链路走的是现有 RPC 和 PendingPermissionDock，没有任何改动。
- **P1 要补的（决策 001 第 3 条）：**
  1. **执行前拦截。** 在 DSH 的 `tools/pre-execute` waterfall 上挂 `aiclient-permissions`（P0-2 已确认每次工具调用都会分发这个 waterfall）。按我方的四档、会话授权记忆、bash 静态分析、拒绝清单逐次判定，需要询问时调用与本次相同的 `ask()` 出卡，拒绝则直接终止这次调用。
  2. **越界升级怎么落到四档上。** 例如「全开」档是否自动放行升级、「每次询问」档照常出卡。同时要给这类卡一个专门的动作 id，改掉「写入工作区文件」的误导文案。
  3. **沙箱保留为兜底层。** 我方审批之后仍由 DSH 沙箱把关；Windows ACL 沙箱在加密机上是否可用，要等 Q002 / P0-4 的结论。
  4. **「本会话内允许」。** DSH 没有这个概念，要在我方插件里记住授权，再在 pre-execute 阶段直接放行。

## 局限与风险

- **只在开发态、Linux 上验证过。** 打包态的宿主路径（`resources/…`）和 Windows 上的 node.exe 拉起都没做，开关在打包态也是强制关闭的。
- **bridge 按路径 import 产品 TypeScript**（`src/agent-host/piWorkerRpcServer.ts`）。这只在源码检出里可行。P1 要把 worker RPC 协议拆成一个可以打包的公共模块，或者让 bridge 自带一份。
- **会话恢复没测。** 包括重启应用后重开一个 DSH 会话、worker 崩溃后重拉。这两种情况下 `history` 都是空的。
- **一会话一宿主。** 每个会话多占约 180 MB（见 P0-1）。多会话场景得等 P1 的共享宿主。
- **开发机宿主报「weaker process-tree containment」。** 原因是这台机器的 user systemd 处于 degraded 状态，与 P0-2 相同。
