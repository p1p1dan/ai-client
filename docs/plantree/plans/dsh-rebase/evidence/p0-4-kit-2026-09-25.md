# P0-4 加密机上机包：构建与 Linux 预演（2026-09-25）

Role: evidence。上位：[roadmap P0-4](../roadmap.md)。用户上机用的检查单：[topics/p0-4-encrypted-machine-checklist.md](../topics/p0-4-encrypted-machine-checklist.md)。

本文只记录上机包本身：怎么做出来、查什么、在 Linux 上预演到了哪一步。加密机的结果等用户上机后另写一份证据。

## 结论

1. **工具包可以在这台 Linux 开发机上可靠地做出来，不需要 Windows CI。**
   - 做法：以 `src/dsh-host/package-lock.json` 为准，执行 `npm ci --os=win32 --cpu=x64 --install-links --ignore-scripts`。
   - 为什么可以跳过安装脚本：用到的原生二进制都随 npm 包预编译好了。锁文件里本来就记着 win32-x64 的可选包：
     - `node-addon-require-builtin-win32-x64-msvc`
     - `@koromix/koffi-win32-x64`
     - `@vscode/ripgrep-win32-x64`
     - `@img/sharp-win32-x64`
   - node-pty 1.2.0-beta.15 自带 `prebuilds/win32-x64`。
2. **体积**：zip 40.2 MB；解压后 10,880 个文件、126 MB；最长相对路径 181 个字符。
   - 裁掉的内容：其他平台的 prebuilds、`.bin` 链接、11,226 个 `.map` / `.d.ts` 文件。
   - Linux 预演用的是同样裁剪过的树，宿主照常运行，说明这些裁剪不影响运行。
3. **原生二进制全部核对通过**：14 个 `.node` / `.dll` / `.exe` 都是 PE32+ x86-64。构建脚本读 PE 头判定，另用 `file` 复核一遍，逐个 sha256 记在 [kit-manifest-win32-x64.json](p0-4-kit-2026-09-25/kit-manifest-win32-x64.json)。清单如下：
   - `node-addon-require-builtin` 的 `win32-x64-msvc-napi-v9.node`
   - `koffi.node`
   - node-pty 的 `conpty.node`、`conpty_console_list.node`，以及 `conpty/OpenConsole.exe`、`conpty.dll` 两份
   - `rg.exe`
   - sharp 的 `.node` 与两个 libvips DLL
   - pnpm 的 `reflink.win32-x64-msvc.node`、`fastlist-0.3.0-x64.exe`
4. **Linux 预演**：检查项全部跑通，40 项通过、2 项记录、1 项跳过（本机没有 PowerShell）。对照组模式也用替身跑通了（见下文「预演」一节）。
   - 用的是随包 node v24.18.0，工具包目录结构与 Windows 版相同。
   - 脚本里 PowerShell 那一侧（读文件头、清理、合并报告）由替身代跑。
5. **没能在本机验证的**：`run-p0-4.ps1` 本身，以及所有 Windows 专属的路径，清单见文末。本机没装 pwsh，脚本连语法解析都没做过，只做了逐行人工审读。

## 检查项

每一项都拿已知的明文标记串去比对，结果分三种：明文、密文（`%TSD-Header-###%`）、其他。

| 组 | 编号 | 内容 |
|---|---|---|
| 前提 | premise、N0 | PowerShell 写标记文件并读文件头，确认是 TSD 容器；node.exe 直接读 |
| 宿主启动 | B2、B3、B1 | NARB 原生缓存：关（原地加载）/ 缓存目录放在加密区 / 默认（`%LOCALAPPDATA%`）。用 `process.report` 的 `sharedObjects` 确认实际加载的是哪个 `.node` |
| DSH 工具 | F-on-*、F-off-* | 沙箱开（workspace-write，Windows 上走 ACL 受限令牌）和沙箱关（`/permission danger-full-access`）各跑一遍，见下方工具序列 |
| 会话 | L-lock-held、L-lock-released、L-recall、S-log-plaintext | 写锁（Windows 上是 koffi 命名信号量）；恢复后的历史里仍有标记串；会话日志由 node 解码后含明文 |
| 终端 | P-pty-spawn、P-pty-read | 经 `ctx.subprocess.spawnTerminal`，在 node-pty / conpty 里起 PowerShell 读标记文件 |
| spill | SP-spill-root | `%TEMP%\dsh-spill-*` 是否可用，是否报 unsafe root；落盘的 spill 文件读回是否明文 |
| 插件 | G-pnpm-install | 先用 `pnpm view` 探测 npm 源，连不上记跳过；能连就经 plugin-manager 安装 `dsh-office-tools@1.0.4`，读回 `package.json` |
| 子进程 | D-bash、D-powershell、D-pwsh7 | node.exe 直接起 Git Bash、Windows PowerShell、PowerShell 7 读写同一个加密文件 |
| 原生模块 | K-natives | 宿主 A 实际加载过的 `.node` |
| 盘上形态 | heads | PowerShell 读上面每个产物的头 16 字节 |
| 对照组 | F-ctrl-* | `-ControlGroup` 模式，由官方 DSH Desktop 跑同一套工具序列 |

F-on / F-off / F-ctrl 共用的工具序列：read 标记文件 → read 待改文件 → edit → read 回读 → write 新文件 → read 回读 → grep → glob → pwsh 读 → pwsh 写 → pwsh 大输出 → read 回读 pwsh 写的文件。最后再用 node.exe 直接读一遍这些产物。

工具调用由假网关 `dsh-p0-2` 计划里新增的 `P0-FS` 场景按内容驱动，参数用一段 JSON 带过去。新增的 `P0-RECALL` 场景用来检查恢复后请求历史里是否还有标记串。网关日志会写下每次工具调用的完整结果，也就是模型实际看到的内容；判定就用这份结果。

## 预演（Linux，2026-09-25）

- **主模式**
  - 用 `--platform linux` 构建同构工具包，在包里跑 `host/p0-4-probe.ts --make-markers`，再用替身完成 PowerShell 那一侧：读文件头、清理、写 `ps-side.json`（带 BOM），最后跑 `p0-4-report.ts` 合并。
  - 结果：14.4 s 跑完，40 项通过、2 项记录、1 项跳过。摘要全文见 [linux-dryrun-summary.txt](p0-4-kit-2026-09-25/linux-dryrun-summary.txt)。
  - 清理：只删了本次新建的 `/tmp/dsh-spill-*`、`/tmp/dsh-subprocess-*` 和工作目录；原本就有的 NARB 缓存目录保留。
  - 摘要第一段写着「前提：不成立」，这是对的：Linux 上没有加密。
- **对照组模式**
  - 替身：用我方宿主模拟 DSH Desktop。把脚本里那份 home 级补丁原样写进替身的 `DSH_HOME/cordis.patch.yml`，把网关密钥写进 `DSH_HOME/.env`。宿主进程不带网关 URL 和密钥的环境变量，所以 bundle 里的地址默认指向丢弃端口 `:9`。
  - 结果：探针 `--control` 在固定端口 18484 等到 12 / 12 步，14 项全部通过，网关收到的请求都带了密钥。
  - 这说明两件事：home 级补丁确实覆盖了 `llm-pi-ai` 的 `baseURL`；DSH_HOME 下的 `.env` 确实进了凭据链。
- **静态检查**：`tsc -p src/dsh-host/tsconfig.json` 无错；新增和改动的文件过了 biome；`fake-gateway.mjs` 过了 `node --check`。

## 过程中查到的事实

1. **NARB 缓存失败时会静默回退。** `node-addon-native-custom-loader` 的 `materializedNativeBinaryPath` 把复制缓存的整段逻辑包在 `try` 里，任何失败都改用原地路径，不报错。因此加密机上如果复制失败，宿主照样能起来，只是没走缓存。B1 / B3 靠 `sharedObjects` 区分这两种情况，回退时记「记录」。
2. **会话日志是多帧 zstd**，每追加一次就是一帧。`zlib.zstdDecompressSync` 一次只解第一帧，只能拿到 199 字节的 header。要按帧魔数切开逐帧解码，DSH 自己的 public decoder 也是这么做的。
3. **spill 文件只保留输出尾部**，本次 64 KB，所以判定只看输出里的 token，不假设从第 1 行开始。
4. **Windows 上的执行文件与锁。**
   - `dsh-pwsh-local` 找 pwsh 的顺序：`%ProgramFiles%\PowerShell\7\pwsh.exe` → PATH 里的 `pwsh.exe` → `System32\WindowsPowerShell\v1.0\powershell.exe`。
   - 会话写锁是 `Local\dsh-session-lock-<sha256(小写路径)>` 命名信号量；第二个持有者会收到 `SessionAlreadyOwnedError`。Linux 预演走的是 flock，报错相同。
5. **对 P1 的提醒：共享 DSH_HOME 会带进用户配置。** DSH 宿主会叠加 `DSH_HOME/cordis.patch.yml`（home 级补丁）和 `DSH_HOME/.env`（用户层环境变量）。对照组正是靠这一点改道官方 DSH Desktop 的。反过来说，如果 P1 按 L3 目标和官方 DSH 共用 `~/.dsh`，用户写在那里的补丁和 `.env` 也会进入我方 worker 引擎。P1 设计凭据接缝和组合审计时要考虑这一层。

## 只能在 Windows 加密机上验证的

- `run-p0-4.ps1` 在 Windows PowerShell 5.1 下能不能跑通。已经针对以下已知坑写法：
  - StrictMode 2；
  - 原生命令的 stderr：调用时切到 `ErrorActionPreference=Continue`，且不重定向；
  - `ConvertFrom-Json`；
  - 中文与 BOM；
  - 超过 MAX_PATH 的删除：先用 node 的 `rmSync`，再用 `Remove-Item`。
- node.exe v24.18.0 在 Windows 上直接跑工具包里的 `.ts`（类型剥离）、`--import file:///C:/…` 预加载钩子。
- 加密相关的全部结论：TSD 前提、各条路径读到明文还是密文、NARB 缓存副本能不能被 LoadLibrary 加载。
- `sandbox-windows-acl` 的受限令牌 runner 在加密目录上能不能授权写入，pwsh 在沙箱里能不能起来。
- koffi 命名信号量写锁、conpty（`conpty.node`）加载、rg.exe 在加密文件上的 grep 结果、pnpm 在 Windows 上的 store 位置与安装后文件形态。
- 官方 DSH Desktop 是否接受这份 home 级补丁（它的组合与 dsh-base 不完全相同），以及它的宿主进程到底是哪个 exe。
