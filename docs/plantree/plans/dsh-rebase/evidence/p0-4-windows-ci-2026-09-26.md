## 结论

1. **一键脚本在真 Windows PowerShell 5.1 上第一次就跑通，`run-p0-4.ps1` 没改一行。**
   - 语法解析通过（`Parser::ParseFile`，5.1.20348.5622）。
   - 事先防过的坑都没出事：StrictMode 2、原生命令 stderr、`ConvertFrom-Json`、中文与 BOM、超过 MAX_PATH 的清理。
   - 三份报告的清理都成功，`cleanup.failed` 为空。
2. **管理员账户（runner 自带的 `runneradmin`）：45 通过、3 记录、0 失败。** 覆盖了 roadmap P0-4 列的全部项，逐项见下表。
3. **标准用户（新建本地账户，只在 Users 组，Medium 完整性），跑了两轮：**
   - **工作区在用户目录下**（`C:\Users\p04std\…`，Full Control）：43 通过、3 记录、1 跳过、0 失败。跳过的一项是 `D-pwsh7-read`，因为这一轮故意对该账户隐藏了 PowerShell 7。
     - DSH 的 pwsh 工具因此退回 Windows PowerShell 5.1。它在 ACL 沙箱里（Low 完整性受限令牌）读、写、大输出都正常。
   - **工作区在 `C:\` 根下新建的目录**（只继承 Authenticated Users:Modify）：37 通过、6 失败。
     - 6 项都是沙箱开时 pwsh 工具起不来：`SetNamedSecurityInfoW failed (Win32 5): grantWrite(<ws-on>)`。
     - 这是 DSH 自身的设计行为，已定位，见下文「DSH 在 Windows 上的问题」。**没有改 DSH 包。**
4. **DSH 自身的 Windows 问题 1 个：`sandbox-windows-acl` 要求工作区根目录能写 owner（WRITE_OWNER）。**
   - 目录只有 Modify 权限时，沙箱开的所有 shell 调用都被拒绝。拒绝方式是 fail-closed：不会退回无沙箱运行。
   - 管理员账户对任何目录都有 Full Control，所以只跑管理员会把这个问题完全盖住。
5. **修复清单**：
   - 工具包构建脚本 1 处：npm 11 下 `file:` 依赖留成了符号链接。
   - workflow 自身 4 处。
   - 探针加了 2 处观测，不改原有判据。
   - 逐项见「修复清单」一节。
6. **明文 / 密文**：普通目录，所有读回都是明文。摘要第一段的「前提：不成立」是预期结果。

## DSH 在 Windows 上的问题

### 1. ACL 沙箱要求工作区根目录能写 owner；只有 Modify 的目录下，沙箱开时 pwsh 工具全部失败

- **现象**（标准·根目录一轮）：
  - 沙箱开的 3 次 pwsh 调用，工具结果都是：
    ```
    Error: SetNamedSecurityInfoW failed (Win32 5): grantWrite(C:\p04enc\p0-4-20260926-172333\ws-on)
    ```
  - pwsh 进程没有起来，所以 `shell-written-*.txt` 不存在，连带 F-on-read-shell-written、F-on-node-verify 失败。
  - F-on-acl 显示工作区上没有能力 SID ACE。
  - 同一轮里，沙箱关的 pwsh、所有文件工具、rg.exe（grep / glob）都正常。
- **日志**：
  - [standard/report-20260926-172333/p0-4-summary.txt](p0-4-windows-ci-2026-09-26/standard/report-20260926-172333/p0-4-summary.txt)
  - [p0-4-report.json](p0-4-windows-ci-2026-09-26/standard/report-20260926-172333/p0-4-report.json)：`checks[id=F-on-*]`，以及 icacls 原文 `checks[id=F-on-acl].detail`。
- **定位**：
  1. `dsh-sandbox-windows-acl` 的 `grantWrite` 用一次 `SetNamedSecurityInfoW` 同时写三样东西：DACL 里的能力 SID ACE、Everyone 拒绝 `FILE_DELETE_CHILD`，以及 SACL 里的 Low 完整性标签。
  2. 写标签需要 WRITE_OWNER。目录的所有者只隐含 READ_CONTROL 与 WRITE_DAC 两项权限。
  3. DSH 源码注释与 README 对此有明文说明：「Granted directories must be caller-owned and grant `WRITE_OWNER` … A directory whose DACL grants only Modify now fails the grant loudly instead of silently skipping the confinement.」
- **复核**：[acl-probe-standard.txt](p0-4-windows-ci-2026-09-26/standard/acl-probe-standard.txt)。同一个标准账户，各在两处新建一个自己拥有的目录做对比：

  | 位置 | 继承到的权限 | `icacls /grant`（改 DACL，需要 WRITE_DAC） | `icacls /setintegritylevel (OI)(CI)L`（改标签，需要 WRITE_OWNER） |
  |---|---|---|---|
  | `C:\p04enc\…` | `p04std:(M)`、`Authenticated Users:(M)` | 成功 | **Access is denied，exit 5** |
  | `C:\Users\p04std\…` | `p04std:(F)` | 成功 | 成功 |

  用户目录那一轮的沙箱开全部通过，工作区上也有 ACE 与 Low 标签。
- **影响面**：
  - **不受影响**：
    - 用户目录（桌面、文档、`C:\Users\<用户>\…`）是 Full Control；
    - 管理员账户。
  - **受影响**：只有 Modify 权限的目录。典型例子：
    - 普通用户在 `C:\` 根下自建的 `C:\work`、`C:\code`：它们只继承到 Authenticated Users:Modify，继承项里也没有 CREATOR OWNER。这是在 runner 上观察到的；客户端版 Windows 的 `C:\` 默认 ACL 一般相同，但本次没验证；
    - IT 预先建好、再给用户 Modify 的共享或数据目录；
    - 数据盘根下的目录，取决于分区根的 ACL，本次没测。
  - 加密机上的受策略目录（如 `D:\Encrypted`）是哪种 ACL 还不知道，到 P2 前上机时要一并看 F-on-acl。
- **失败形态**：fail-closed，不会退回无沙箱运行。模型拿到的工具结果就是上面那行英文错误。read / write / edit / grep / glob 不经过 shell 沙箱，不受影响；切到 `danger-full-access` 后也不受影响。
- **处理**：按约束没有在 DSH 包里打补丁。workflow 的闸门把这 6 项登记为已定位的失败：出现时记 warning；哪天变成通过会出 notice；其他任何失败都会让 job 失败。

### 其他观察（都不算失败）

- 宿主 A 的 stderr 里有一条警告：`subprocess-local is using weaker process-tree containment because Windows ConPTY remains outside Job containment`。意思是 Windows 上终端进程不在 Job 里，逃出直接父子树的子孙进程不保证随之结束。
- 宿主 dispose 后还挂着 `PipeWrap` / `MessagePort` / `Timeout` 这些句柄，由 `host.ts` 的 3 秒兜底退出。所有宿主都在 20 秒内正常停下（`graceful: true`）。
- NARB 缓存三种启动方式都真的生效了：B3 / B1 从缓存副本加载，B2 原地加载，没有出现静默回退。
- `%TEMP%` 是 8.3 短名（`RUNNER~1`）时，spill-local 没报 unsafe root。

## 没能覆盖的

- **加密相关的全部结论**：TSD 前提、明文 / 密文、NARB 缓存副本放在加密区能不能被 LoadLibrary 加载、ACL 沙箱在加密目录上能不能授权。按决策 002 挪到 P2 前的加密机上机。
- **对照组**（官方 DSH Desktop，`-ControlGroup`）：按决策不跑。
- **交互式登录**：标准用户走的是计划任务的批处理登录，不是桌面交互登录。没有资源管理器，也没有可见的控制台窗口。ConPTY 与 ACL runner 在交互会话里的表现没有单独验证。
- **Windows 10 / 11 客户端版**：runner 是 Windows Server 2022。
- **杀毒、AppLocker、组策略**：没测 Defender 或第三方杀软拦截 `rg.exe`、`OpenConsole.exe`、`node.exe`，也没测组策略锁死执行策略。
- **非 ASCII 路径**：中文用户名，工作区或用户目录路径里带中文。标记串与工具输出也都是 ASCII，pwsh 5.1 的中文输出编码没测。
- **数据盘**：runner 的 D: 是临时盘，数据盘根下工作区的 ACL 没测。
- **真实安装目录**：没用 `%LOCALAPPDATA%\Programs\PiLab Ai`，换成了同结构、同样带空格的 `C:\p04app\PiLab Ai`。
- **两个组合没单独跑**：「管理员 + 没有 PowerShell 7」「标准用户 + 有 PowerShell 7」。
- **pnpm 离线跳过路径**：runner 能连 npm 源，所以没走到。
- **P0-6 的内容**：长时间运行、多会话、崩溃恢复。

## 对 P0-5 / P1 的提醒

1. **Windows 默认权限预设与 ACL 沙箱的前提冲突。** 工作区只有 Modify 权限时，workspace-write 下的 shell 工具完全不可用，模型看到的只有一行 Win32 错误。P1 需要定：
   - 在打开工作区时预检 WRITE_OWNER；
   - 不满足时怎么办：提示用户、改用 `danger-full-access` 加我方审批，或拒绝。
2. **ACL 沙箱会永久改动工作区 ACL。** 它写的是常驻的 ACE、Low 标签和 Everyone 拒绝 DC，并沿目录树继承。按 DSH README：
   - 大目录首次授权要全树重新传播，可能要几分钟；
   - 手工 `icacls` 撤不掉（`ERROR_NONE_MAPPED`）。

   用户或 IT 会看到这些改动，P1 默认开不开要有决定。
3. **CI 与验收都必须带标准用户这一路**，管理员账户会掩盖第 1 条。
4. **办公机大多只有 Windows PowerShell 5.1**，DSH 会退回它。本次 5.1 在沙箱开、关两种模式下都正常，但中文输出与编码没测。
5. **DSH 在 Windows 上只有 `pwsh` 工具，没有 `bash`**。提示词、审批文案、UI 里按 bash 写的假设在 Windows 上都要换。
6. **ConPTY 不在 Job 里**，Windows 上终端进程树的回收弱于 Linux。P0-6 的崩溃恢复补验要考虑残留进程。
7. **工具包构建对 npm 版本敏感**（本次已修）。P1 打包不要依赖 `npm ci --install-links` 的行为。
