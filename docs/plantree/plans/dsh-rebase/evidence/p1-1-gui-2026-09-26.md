# P1-1 引擎直替：开发机 GUI 点验（2026-09-26～27，Linux 开发机）

Role: evidence。对应 [roadmap P1-1](../roadmap.md) 的退出判据「开发机上新建会话走 DSH」，以及[决策 005](../decisions/005-legacy-pi-sessions-read-only-until-p1-9.md)（旧 pi 会话只读）、[决策 010](../decisions/010-p1-1-scope-boundary.md)（fork / 重试 / 附件明确拒绝）在界面上的表现。实现与无界面回归见 [p1-1-engine-cutover-2026-09-26.md](p1-1-engine-cutover-2026-09-26.md)。截图、结果 JSON、驱动脚本都在 [p1-1-gui-2026-09-26/](p1-1-gui-2026-09-26/)。本次只取证，没有改 `src/`。

## 结论先行

1. **退出判据成立。** 新建会话由 Electron 主进程拉起 DSH 宿主（随包 node + `--expose-internals` + `src/dsh-host/host.ts`），三次启动全程没有出现任何 native worker。索引行 `agent: "dsh"`，身份是预期路径下的桩文件。会话日志在首条回复画出之前约 0.8 s 就已落盘，而且早于桩文件。流式正文、工具行都正常。
2. **恢复与崩溃重启成立。** 应用完全退出再启动后，点开会话能继续跑工具回合，模型也能看到重启前三轮的内容。时间线为空，这是 P1-4 之前的预期。回合中按确切 pid `SIGKILL` 宿主后，0.8 s 内自动拉起新宿主并恢复会话。状态停在 `failed`（不是 `error`），下一轮正常跑完。
3. **旧 pi 会话：预览 ✅、只读卡片 ✅，但消息没有退回输入框 ❌。** 输入框被清空，挂上「重试上一条消息」，而这个重试只会再被拒一次。卡片下方还多出一条原始英文报错。
4. **拒绝路径都「拒绝了」，但附件的体验同样有缺陷。**
   - fork：API 明确报 `WORKER_DSH_UNSUPPORTED`，但界面上根本没有分叉入口。
   - 重试：`retry_unavailable` 处理正确，提示出现，原提示词留在输入框。
   - 附件：请求没有发给模型，但文字和图片一起从输入框消失，报错是原始英文。
   - TUI：明确拒绝，有中文提示，没有拉起任何进程。
5. **没有发现阻断 P1-2 / P1-3 的问题。** 建议在两者开工前先修 D1、D2（见「缺陷」）。两项都是 P1-1 自己的范围，只改渲染层的小改动，而且每个升级用户第一次打开旧对话就会碰到 D1。

## 缺陷（按严重度）

**D1 中：旧 pi 会话里发送被拒后，消息没有退回输入框，而是挂成一个永远会失败的「重试」。**
- 现象：
  - 输入框被清空，出现「重试上一条消息」（`composerButtons` 里有这一项）。点它只会再次触发 resume，再被 `legacy_session_readonly` 拒绝。用户打的字在界面上看不到了。
  - 「迁移前只能查看」卡片下方同时出现原始英文红框：`Error: Error invoking remote method 'chat:resumeSession': Error: legacy_session_readonly: Session <id> was written by the previous chat engine and is read-only until it is migrated`。
  - 另外，打开旧会话时、发送之前没有任何只读提示，输入框看起来完全可用。
- 复现：
  1. 应用停止时，往 `session-index.json` 追加一行 `agent: "pi"`，`runtimeIdentity` 指向真实的 pi 会话文件。
  2. 启动应用，在侧栏点开这一行。
  3. 输入任意文字并点发送。
- 证据：[10-legacy-send-refused.png](p1-1-gui-2026-09-26/10-legacy-send-refused.png)；`p1-1-run3-result.json` 的 `legacy.composerAfter`（`value: ""`）、`legacy.factsAfter.errorBox`、`legacy.factsAfter.composerButtons`。
- 分析（推断，未改代码验证）：`ChatComposer` 的 `decideFailureAffordance` 对这类「resume 被拒、从未发出」的结果选了 `resend`，没有选 `restore-draft`。原始报错框就是 `lastError` 里存的 IPC 原文。

**D2 中：带图发送被拒后，文字和图片都丢出了输入框，报错是原始英文。**
- 现象：
  - 红框内容是 `Error: Error invoking remote method 'chat:send': WorkerSlotError: WORKER_DSH_UNSUPPORTED: Sending attachments is not bridged to the DSH engine yet`，没有翻译。
  - 输入框清空，草稿列表清空，只留一个圆形「重试」。重试会带着同一张图再发一次，必然再被拒；用户也没办法去掉图片、只发文字。
  - 粘贴图片时没有任何预先拦截，所以只有发出去才知道不支持。
- 复现：在 DSH 会话的输入框粘贴一张图片，输入文字，点发送。
- 证据：[05-attachment-draft.png](p1-1-gui-2026-09-26/05-attachment-draft.png)、[05-attachment-refused.png](p1-1-gui-2026-09-26/05-attachment-refused.png)；`p1-1-item4-result.json` 的 `attachment.trace`（点发送后 0.1 s 内已是 `composer: ""`、`drafts: []`，约 0.4 s 后 `lastError` 出现上述原文）。

**D3 中低：DSH 回合的失败原因一律落到「本应用不认识这一轮的结束原因」，并直接显示原始 JSON。**
- 现象：
  - 网关不可达时，卡片正文是 `DSH turn ended: {"kind":"error","error":{"message":"Connection error.","code":"TRANSPORT"}}`。bridge 发出的 `session.failed` 只有 `error`、没有 `errorCode`，所以 `sessionFailure.ts` 只能落到 `unknown`，网络类失败拿不到对应的卡片文案。
  - 点「继续」收起卡片后，输入框上方仍留着同一段原始红字。
  - 宿主被杀时的「Worker exited (code=null signal=SIGKILL)」落到同一张 unknown 卡。这个事件由 WorkerManager 发出，同样不带 `errorCode`，与引擎无关，应是既有行为。
- 复现：
  1. DSH 会话里停掉网关，然后发送。
  2. 或者回合进行中杀掉宿主。
- 证据：[07-failed-card.png](p1-1-gui-2026-09-26/07-failed-card.png)、[07-continue-toast.png](p1-1-gui-2026-09-26/07-continue-toast.png)、[09-crash-after-kill.png](p1-1-gui-2026-09-26/09-crash-after-kill.png)。

**D4 低：fork 在界面上既没有入口，也没有说明。**
- 现象：「会话分支」对话框显示「共 0 个节点 / 这个会话还没有落盘的树节点。」，但这个会话已经有 6 轮以上落盘。用户会以为数据丢了，也看不到「暂不支持」的提示。回退同理。
- 复现：在 DSH 会话点顶栏的「会话分支」。
- 证据：[04-fork-branch-dialog.png](p1-1-gui-2026-09-26/04-fork-branch-dialog.png)。
- 归属：P1-4b。

**D5 低：「继续」走 `retry_unavailable` 后，提示文案与 DSH 的真实原因不符。**
- 现象：提示说「上一轮没有留下可以重跑的记录 —— 可能根本没被记录下来，或者历史已被压缩」，实际原因是 DSH 的重试还没有桥接（决策 010）。
- 证据：[07-continue-toast.png](p1-1-gui-2026-09-26/07-continue-toast.png)。

**D6 低：重启后点开 DSH 会话，空时间线显示新会话的英文空态。**
- 现象：时间线显示「No messages yet. Send a prompt to stream from the Agent Host.」。时间线为空本身是 P1-4 之前的预期，但这句英文、新会话口吻的文案会让人以为历史丢了。
- 证据：[08-restart-click-resumed.png](p1-1-gui-2026-09-26/08-restart-click-resumed.png)。
- 归属：P1-4a（投影历史），或先换一句「历史将在后续版本显示」的过渡文案。

## 没能取证的项

- **`session_locked` 与「强制接管」：** 没有制造出来。
  - 应用内每个会话只对应一个宿主，渲染层也按窗口认领会话。要撞锁，就得另起一个宿主进程持有同一个 DSH 会话，属于脱离界面的造数据。
  - 无界面回归里已有 `lockedWhileOwned`，覆盖的是「锁冲突映射为 `session_locked`、`forceTakeover` 被忽略」。
  - [实现证据](p1-1-engine-cutover-2026-09-26.md)已登记：「强制接管」在 DSH 下无效，归 P1-3。
- **P0-TOOL 的「运行中」截图：** 这段运行只持续 141 ms，截图没赶上。运行中状态在 store 采样里有记录，画面由 P0-SLOWTOOL 的截图补齐，两者都在上表。
- **从界面点「从这里分叉」：** 树为空，界面上没有这个按钮，只能在 API 层取证，见 D4。

## 其他观察（不算 P1-1 缺陷）

- **退出：** `app.quit()` 会先弹渲染层的「确认退出」。及时点「退出」时，三次都在 0.54 / 1.09 / 1.08 s 内全部进程退出，宿主一并退出，没有孤儿。
  - 如果确认框放着超过 30 s，Main 就不再等回应（`CLOSE_RESPONSE_IPC_TIMEOUT_MS`），这时再点「退出」没有任何效果。这是既有行为，本次撞到过一次。
- **同一 slot 上重复 resume：** 发送被拒之后、以及点「继续」时，WorkerManager 会在**同一个**活着的 slot 上再发一次 `session.resumed` 和 `session.history(mode initial, 空页)`，宿主 pid 不变，渲染层保留原时间线。等 P1-4 让历史非空以后，这种重复 resume 会不会覆盖时间线，P1-3 / P1-4 要留意。
- **宿主 stderr：** 宿主的 stderr（ready JSON、「weaker process-tree containment」告警）以 `session.stderr` 事件送到渲染层。
- **目录权限：** `dsh-home` 本身是 0700，但 DSH 自建的 `profiles/` 是 0775。归 P1-3 的 home 策略。
- **文案遗留：** 开始页输入框占位仍是「给 Pi 发消息…」；旧会话的模型徽标是「p0fake/fake-1 · unverified」。
- **console.error 分类：**
  - 临时环境噪声：`[workspace-tree]`，因为临时工作区不是 git 仓库；`legacy-import:listProjects`，因为临时 HOME 下没有系统密钥环。
  - 预期拒绝的 IPC 日志：`chat:forkSession`、`chat:send`（附件）、`chat:retryLastTurn`、`chat:resumeSession`（`legacy_session_readonly`），以及点开 DSH 会话时的 `chat:readSessionPage`（`session_replay_unavailable`，这是设计上回退到 resume 的信号）。
  - 故意 SIGKILL 的崩溃日志。
  - 没有未捕获异常。
