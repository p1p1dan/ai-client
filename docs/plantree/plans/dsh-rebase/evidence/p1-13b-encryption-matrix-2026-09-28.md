# P1-13b 加密矩阵（2026-09-28，脱敏摘要）

- **上机包**：`c3eb0068` 构建，sha256 `4a5ea708…b652`。现场对上机包的哈希做过校验，没有改动原版代码。
- **环境**：用户的加密测试机，管理员权限（EnableLUA=0）。应用 1.0.3，随包 Node v24.18.0，Electron 39.2.7（内嵌 Node v22.21.1）。
- **原始报告与证据包**只留在开发机本地（主检出的 `contextFX/linshide/P1-13b-现场结果/`），不入库。原因：仓库是公开的，原始报告里有机器与路径信息。
- **判读**：见[决策 089](../decisions/089-p1-13b-reading-and-hardlink-fix.md)。

## 规模

- 输入：51 个文件，覆盖 51 种扩展名和文件名。用户逐个确认：28 个已加密、23 个未加密（后者推测是加密策略没覆盖这些类型，原因未确认）。
- 读者 6 个、写者 8 个；408 条写入结果、102 个读取批次，没有读写错误。
- 改名副本那一组在正式矩阵里被跳过，原因是脚本里的 `Get-FileHash` 报错；现场另起进程补测完成。

## 一、随包 node.exe 能读出哪些类型的明文

Node 与 Electron（以 node 模式运行）结果完全一致：

| 类型 | node.exe / Electron 读到的 |
|---|---|
| md、java、hpp、xlsx、pdf | 明文（PowerShell 5.1 读这几类反而是密文） |
| txt、ts、js、py、c、cpp、h、cs、sh、bat、xml、html、vue、csv | 明文（输入经用户确认已加密） |
| **yml、rb、php、ps1、cmd、sql、scss、docx、pptx** | **密文**：产品读不到内容 |

- 改名的 node 副本读这 51 个输入，结果与 node.exe 逐字节相同：42 个明文、9 个密文。**读取时的解密与进程名无关**。
- 这张表只代表这台机器上的这套策略，不能当成通用白名单。

## 二、各种写法新建的文件会不会被加密

| 写法 | 加密 | 未加密或未确认 | 说明 |
|---|---:|---:|---|
| node.exe 直接新建（**1.0.x 的写法**） | 22 | 29 | 用户逐个确认 |
| 先写临时文件再改名 | 22 | 29 | 与直接新建一致 |
| **先写临时文件再硬链接（DSH write 的写法）** | **0** | **51** | 用户确认全部未加密 |
| 只复制已加密的输入 | 27 | 24 | 用户逐个确认 |
| 复制后覆盖 | 22 | 29 | 2 个人工确认加密，其余按文件大小推断 |
| 复制后原地编辑 | 27 | 24 | 同上 |
| Electron 直接新建 | 23 | 28 | 3 个人工确认加密，其余按文件大小推断 |
| PowerShell 5.1 新建 | 28 | 23 | 用户确认目录总数 |

- 延迟复读确实有变化，比如 PowerShell 读 md、java 从明文变成了密文。实际的延迟约 260 秒，不是 60 秒。
- 文件太小时不能凭大小判断是否加密：不同进程看到的大小不一样（有的是 8192 字节，有的是明文长度）。

## 三、策略是否按进程名匹配

- **读**：与进程名无关，见第一节。
- **写**：做了三组对照，分别是安装目录的 node.exe、临时目录的 node.exe、同一临时目录里改了名的副本，三者 SHA256 相同，各新建 51 个文件。
  - 用 cmd 读其中的 `.js`：两个 node.exe 写出的是明文，改名副本写出的是密文。
  - 说明新建 `.js` 是否加密与可执行文件名有关，而且 node.exe 这个名字恰恰让 `.js` 不加密。
  - 只跑了一轮，其他类型没有对照。

## 上机包的缺陷（下一轮修）

- 正式脚本里 `Get-FileHash` 找不到，导致改名那一组被跳过；独立进程里可以正常执行。
- `certutil -dump` 对大量类型给出 OTHER，解析规则要核对。
