## 2 首步探测：同样内容，不同网关会话

3 个新对话各发同一句不调工具的短问（每个 1 个请求）。请求体都是 23,931 字符，与 Ap3 首个请求的 23,965 只差提示语那几个字。

|---|---|---|---|
| P1 | 37,596 | 0 | 37,594 |
| P2 | 37,598 | **33,520** | 4,076 |
| P3 | 37,601 | **33,520** | 4,079 |
| C1（官方 SDK，Claude Code 写法，默认 UA，新会话） | 37,620 | **32,216** | 5,402 |

- 本轮出现了三类首步提示量：约 8.5k、约 10.4k、约 37.6k。即便网关会话标识相同（Ap3 与 S3 / N3），首步也落在不同的类别。
- 37.6k 这一类比 10.4k 多约 27.2k，而客户端发出的字节数相同。按计数推断：
  - 约 24.3k 落在可跨会话、跨请求共享的前缀里：P 组读到 33,520；系统块不同的 C1 读到 32,216，dsh.11 里也反复回退到 32,216；
  - 约 2.9k 落在各会话各自写入的部分：每个会话写入约 4.08k，不多出时同样内容约 1.2k。
- C1 的请求没有写 TTL（按 Claude Code 写法只写 `{type:"ephemeral"}`，默认是 5 分钟），但用量把它的 5,402 写入记为 1 小时 TTL。应用请求的写入同样都记为 1 小时。

最后一个探测对话（P3）接着用修复后的应用做 3 轮带工具的工作，然后闲置约 6.9 分钟，再发一句短问。

| 请求 | 时间（UTC） | 提示总量 | 缓存读 | 缓存写 | 丢失 | 说明 |

| 31（第 1 轮第 1 步） | 01:39:19 | 37,671 | **33,520** | 4,149 | **4,081** | 距上一请求 5.7 分钟 |
| 32（第 2 步） | 01:39:30 | 38,160 | 37,669 | 489 | 2 | |

- 回合内各步、间隔约 30～40 秒的回合开始，都只丢 2：修复后的应用在这一类上没有每轮第 2 步的重写。
- 两次超过 5 分钟的闲置之后都丢了缓存，而且都是退回到较早的、仍有效的前缀。可这些写入在用量里都标为 1 小时 TTL。
  - 推断：这一类上游对消息部分的缓存实际只保留约 5 分钟，或者在闲置后有别的变化，第 39 个请求的提示量减少了 175 就是一个迹象。客户端无法判断是哪一种。
  - 本机的缓存链折叠按 5 分钟 TTL 把这两次判为「过期」。应用自己用 1 小时 TTL，会把它们算作没有本地原因的损失。

## 4 写法切换的对照

| 组 | 写法 | 网关会话 | 首步 | 回合第 2 步 / 其他步的丢失 |
|---|---|---|---|---|
| S3 | 修复前 | Ap3 的 | 8,546 | 第 2、4、8 个请求都是 2；其余也都是 2 |
| N3 | 修复后 | Ap3 的 | 8,545 | 全部 2 |
| S4 | 修复前 | Pz 的（多出的一类） | 37,696 | 27 / 234 / 27 / **1,904** / **2,249** / 27 / **1,286** |
| N4 | 修复后 | Pz 的 | 37,693 | **与 S4 逐字相同**（27 / 234 / 27 / 1,904 / 2,249 / 27 / 1,286） |

- S3 / N3 分到了 8.5k 的一类，旧写法也不丢，所以这一类对写法切换不敏感。
- S4 / N4 两组的损失完全相同，与写法无关。规律是：以 `tool_result` 结尾的那次写入，下一个请求读不到，回退到上一个以用户文本结尾的写入。每步还有约 25 token 读不到，在供应商 B 上是 2。
- 这些现象只出现在 SDK 重放里（历史思考块已去掉，系统提示前加了标记）。同一会话里修复后的应用本身（Pz，保留思考块）没有出现。所以它反映的是重放请求的构造在这一类上游上的表现，与应用无关，也与写法无关。
- 有一点值得注意：S4 / N4 的系统提示前有自己的标记，第 2 步读到的量却仍然和应用请求写下的量几乎一样（37,669 / 37,666）。按计数推断，这一类上游上，我们的系统提示可能不在缓存前缀的最前面。这只是推断，无法验证。

## 5 回答编排者的问题

- **供应商 A 的额外提示**：存在。首步多出约 2.72 万 token，其中约 2.43 万在可共享的前缀里，所以它会被缓存、也能跨会话复用。它不是每个会话都出现：本轮 6 个新会话里，Ap3 和 S3 / N3 没有，P1～P3、C1 有。它与客户端无关：官方 SDK、Claude Code 结构、默认 UA 也有。dsh.11 里看到的 32,216 正是 C1 读到的共享前缀大小。
- **修复后的应用在供应商 A 上还丢不丢缓存**：每轮第 2 步回退到约 32k 的问题没有再出现，在多出和不多出两类上游上都是这样。剩下的损失只出现在多出的那一类上、闲置超过 5 分钟后的回合开始；而用量声称写入的是 1 小时缓存。这一点在客户端之外，客户端改不了：继续发请求就会写入，但闲置超过 5 分钟后那部分就读不回来了。
- **是否与写法切换有关**：本轮在供应商 A 上没有观察到写法切换造成的差异。修复对供应商 B 那一类有效（见 [DA-3 修复复测](da3-fix-real-gateway-2026-10-11.md)），在供应商 A 上无害。
- **供应商额外加了什么**：只能给出计数。共享部分约 2.43 万 token；每个会话约 2.9k；每次请求末尾约 25 token 不进缓存（只在 SDK 重放里看到）。不能断定内容。
