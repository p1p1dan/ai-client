# 压缩相关真实网关取证：执行计划

建立：2026-10-11。上位：[roadmap](../roadmap.md) P1-5 R8/R9 的延伸、决策 [177](../decisions/177-auto-compaction-policy-per-model.md)、[178](../decisions/178-compaction-progress-and-send-during-compact.md)、[179](../decisions/179-compact-instructions.md) 第 11/9/9 节「真实网关上还需取证的点」。

状态：只读调研 + 计划，尚未执行。本文只规划怎么做，不包含任何执行结果；执行后的结果写一份新证据文件（建议 `evidence/compaction-real-gateway-<日期>.md`，脱敏摘要，格式仿 [p1-5 真实网关证据](../evidence/p1-5-real-gateway-2026-09-30.md)）。

## 1 目的与范围

决策 177（按模型的自动压缩策略）、178（压缩进行中可见）、179（`/compact` 附加说明）都只在本地假网关（`tools/fake-gateway.mjs`）上验证过，各自留了「真实网关上还需取证的点」：

- 177 §11-1、11-2：没写输出上限的模型摘要被截断到 8192 是否够用；`summaryMaxTokens` 65536 是否会被严格校验 `max_tokens` 的服务拒绝（历史上 Claude Opus 5.5 真的因为这个 400 过，见决策 141 背景）。
- 178 §9-6：录制样本依赖 177 的宿主策略，真实网关上自动压缩触发的位置、时间线显示是否符合设计。
- 179 §9-2：`/compact <说明>` 对真实模型的遵从程度完全没测（本地只有假网关）。

本计划只覆盖这三份决策标记的取证点，不重测 P1-5 已经验过的登录/菜单/档位/工具/图片等（那些已有结论，见 [p1-5-real-gateway-2026-09-30.md](../evidence/p1-5-real-gateway-2026-09-30.md)）。

## 2 前提

1. **登录**：由用户在开发版应用里亲自登录公司网关账号（公司登录模式，`AICLIENT_MANAGED_CREDENTIALS=1`）。执行代理不触碰登录表单、不读取邮箱以外的任何凭据字段，只在用户确认已登录后经 CDP 接管。
2. **隔离**：新建独立的 `HOME` 与工作区，与 P1-5 的 `/tmp/aiclient-real-gw` 分开，避免互相污染会话文件：建议 `/tmp/aiclient-compaction-gw/{home,workspace}`。CDP 端口沿用 9222（同一时间只有一个开发版实例）。
3. **开发版**：`node scripts/dev.js --remote-debugging-port=9222`，公司登录模式。驱动只经应用界面（输入框、斜杠命令、「设置 · 模型」页、运行面板），不直接调网关、不起假网关、不用其他渠道。
4. **一次一个应用实例、期间不跑测试**：按 [dev-box-is-memory-starved] 与 [gui-cdp-pointcheck-recipe]，这台机器 2 核 / 3.3 GB。执行前 `free -m` 确认 available 不低于约 500 MB；执行期间不跑 `vitest`、不起第二个 Electron、不跑构建；跑之前确认没有残留的旧 Electron 进程（`ps -ef` 按 `utility-sub-type=node.mojom.NodeService` 或 cmdline 含 `ai-client` 精确核对，不要用裸 `grep` 关键词）。
5. **预算与中止**：所有请求（每发一条消息、每跑一次 `/compact`、每次重试都算 1 次）记入本地台账，仿 [p1-5-gw.mjs](../evidence/p1-5-real-gateway-2026-09-30/tools/p1-5-gw.mjs) 的 `requests.jsonl` 与硬预算（超过拒绝再发）。建议新驱动脚本直接复用该文件的 `scrub()`、CDP 连接与台账逻辑（同一仓库内，`import` 或照抄约定），不重新发明脱敏规则。
6. **执行者**：建议由执行代理（而不是编排者）持有 CDP 会话、读日志、写本地结果；编排者只看脱敏后的汇总,不经手任何请求体或凭据。

## 3 模型选择与理由

从 [p1-5 的目录](../evidence/p1-5-real-gateway-2026-09-30.md#r1-目录与计划)（13 个模型、4 个 provider、3 种协议）里选 4 个：

| 模型 | 协议 | 选它的理由 |
|---|---|---|
| `claude/claude-sonnet-5-5` | anthropic-messages，adaptive 思考 | 覆盖「Claude adaptive 思考」这条要求；R2/R3/R4/R5 里表现稳定、耗时短，适合反复填充对话做取证点 1、4 |
| `claude/claude-opus-5-5` | anthropic-messages，adaptive 思考 | **就是决策 141 背景里那个真的被上游 400 过的模型**（1.0.4 手动压缩，`thinking.type.disabled` 不被接受）；它的输出上限大概率比 Sonnet 更低，是取证点 2「摘要上限会不会被拒绝」的最佳回归对象 |
| `gpt/gpt-6.1-sol` | openai-responses | 覆盖「GPT」；R2/R4/R7 里零传输错误，比 `gpt-6-luna`（R2/R4 都出现过间歇性 `Connection error`，GW-3）更可控，减少取证时的噪音重试 |
| `china/glm-5.2` | openai-completions | 覆盖「一个国产模型」；China 组里 **唯一**在 2026-09-30 网关上可用的模型（GLM 5.3、DeepSeek V4 Flash/Pro 两次都是 503 `no_available_providers`，GW-1，归为网关侧配置问题，不是本次要测的东西）；通常定价低于旗舰模型，适合作取证点 3（自动压缩触发）的首选，减少消耗 |

不用的模型：Grok（不是「国产」，且 GW-16/GW-17 显示该账号近期在 Grok 组遇到过 503/`cache_limit`，噪音大）；China 组另外三个模型（直接 503，测不出压缩相关的东西，归 GW-1）。

**执行前先确认目录仍一致**：读一次 `piModels.getStatus` / 模型菜单（只取枚举与计数，不取地址），确认这 4 个模型仍在、协议未变；变了就在当次执行记录里改用等价替代（同协议、同类别）并说明理由。

## 4 取证步骤

### 4.0 通用操作（每个模型开始前）

1. 新建一个会话，选定模型，默认档位。
2. 打开「设置 · 模型」页的「自动压缩」一节（决策 177 §6.2，已随本分支代码上线），读出该模型的策略句子（「约在 X token 时触发」或「不会自动压缩：原因」）与窗口/输出上限——**不要预设具体数字**，按决策 146 的教训（GW-4：目录把 `maxTokens` 写成等于窗口），真实管理目录给这几个模型的尺寸可能和公开文档不同，一切以这个页面读到的为准。
3. 记录读到的：`contextWindow`、`maxTokens`、阈值句子、摘要上限句子（如有）。

### 4.1 取证点 1：摘要实际用多少 token

- **模型**：Claude Sonnet 5.5、GPT 6.1 Sol、GLM 5.2（3 个，覆盖三种协议）。
- **操作**：每个模型各开一个新会话，发 3～4 轮有实质内容的消息把上下文填到几千 token 量级（例如让它读一个仓库里中等大小的文件并复述要点，或连续追问几个问题），再输入 `/compact`（不带说明）。
- **要读的数据**：
  - DSH 会话日志（`.jsonl.zstd`，由应用自己的工具解码，不要用外部工具直接读原始压缩字节）里的 `compaction/summary` 事件：取 `maxTokens`（请求的输出上限）、用量字段（实际输出 token 数）；`compaction/start` 与 `compaction/end` 的时间戳差即耗时。
  - 输入框状态行：是否出现「正在压缩上下文…」（决策 176/178 的状态行），多久变成「上下文摘要」行。
  - 宿主 stderr 日志（`[dsh-host] auto compaction, plan …`，决策 177 §7）：对照该模型当次启动时预测的 `summary` 值，核对与会话日志里实际发出的 `maxTokens` 是否一致。
- **判定标准**：
  - 实际输出 token 数 < 请求的 `maxTokens`（没有被截断报错）；
  - 耗时 < 45 秒（bridge 的 `worker.compact` 超时上限，决策 179 §2.3）；
  - 结果为成功（摘要行正常出现，不是失败备注）。
- **用来回答**：决策 177 §11-1 的风险——摘要预留能不能从 64k 降到 1.6 万～3.2 万量级（即实测的输出 token 数是否远小于当前 8192/65536 的上限，从而支持把中等窗口模型的自动压缩阈值提到窗口 50% 以上）。

### 4.2 取证点 2：摘要输出上限会不会被服务拒绝

- **模型**：Claude Opus 5.5（主）；Claude Sonnet 5.5 作对照（4.1 已经验证过，若 4.1 成功即视为「新行为（177 的 min(65536, 模型上限)）不报错」的一个样本，不必重复跑）。
- **操作**：
  1. 新建会话，Claude Opus 5.5，填充到有一定长度（同 4.1 的量级即可），执行 `/compact`。
  2. 读 4.0 记录的「自动压缩」策略句子，确认它给 Opus 5.5 的 `summaryMaxTokens` 是多少（如果低于 65536，这就是决策 177 生效的直接证据）。
  3. 看这次 `/compact` 是否成功：
     - **成功**：验证了「新行为（min(65536, 模型上限)）不报错」，这是本次的主要目标，到此为止。
     - **失败且是 400 / 输出上限相关的错误**：说明目录给 Opus 5.5 声明的 `maxTokens` 本身不准（类似 GW-4 的 Grok），记为新发现，不要在本计划内深挖目录配置问题，转交网关管理员核对（仿 P1-5 R9 的做法）。
  4. **可选、谨慎**：若想额外复现「旧行为（固定 65536）会被拒绝」作对比，可以在「AI 服务」里新增一个自定义服务行，指向**同一个已登录的公司网关**、同一模型，但手工把「输出上限」填得比目录声明的真实值更大（例如改成 65536），让决策 177 的 `min()` 算不出更小的值，从而模拟旧行为。**这一步只有在不需要额外输入任何 key / endpoint（即自定义服务能复用当前登录态，不需要再填凭据）时才做**；如果新增自定义服务行必须手工填写公司网关的地址或密钥，就跳过这一步，只保留「验证新行为成功」这一半结论，将「旧行为确实会 400」列为仍是推断（与决策 177 §11-2 现状一致）。
- **要读的数据**：同 4.1，另外加「AI 服务」设置页的输出上限字段（如果做了 4 的可选步骤）。
- **判定标准**：新行为下 `/compact` 成功、无 400；可选步骤如果做了，旧行为模拟下出现 400 才算复现了风险。
- **中止条件**：如果新增自定义服务行的流程提示需要输入 API key 或网关内部地址，立即放弃可选步骤，不让执行代理看到或填写这些字段。

### 4.3 取证点 3：自动压缩能否在真实网关上按预期触发

- **模型**：优先 GLM 5.2（单价较低，4.0 读到的阈值如果也较小则更省）；如果 4.0 读出 GLM 5.2 的阈值异常大（例如窗口被目录错误地写成很大），改用 4 个模型里 4.0 阈值最小的那个。
- **操作**：
  1. 新建会话，4.0 记录该模型的阈值句子（例如「约在 34k token 时触发」）。
  2. 用「读一个较大的仓库文件 + 复述」或「连续发几段较长的文本」的方式把上下文推高，每发一次都看一眼运行面板「逐步缓存」（决策 173 落地的面板，显示每步的提示词 / 缓存读 / 缓存写）累计量，接近但别精确对齐阈值估算（阈值是约 4 字符一个 token 的估算，允许有误差）。
  3. 继续发一条消息，触发下一步 `agent/pre-step` 的压力检查。
- **要读的数据**：
  - 时间线：是否出现「正在压缩上下文…」轻量行（决策 178 §4.1），随后原地变成「上下文摘要」行；
  - 宿主 stderr 日志：该模型本次启动时的阈值预测，与实际触发时的运行面板累计量级是否大致吻合；
  - 会话日志：`compaction/start`（`turn` 为数字，说明是自动压缩）、`compaction/summary`、`compaction/end`；
  - 回合是否正常继续（压缩完成后那条用户消息的回复正常出现，不是失败卡）。
- **判定标准**：时间线按决策 178 的设计显示进行中 → 完成；阈值与估算同量级（允许 ±30% 误差，因为是字符估算不是真实 tokenizer）；回合不失败。
- **用来回答**：178 §9-6 的风险——真实网关上压缩触发的位置、时间线显示是否符合设计；177 §11-3 的风险——调小余量后阈值偏保守，真实会话里压缩间隔是否合理。

### 4.4 取证点 4：`/compact <说明>` 的遵从

- **模型**：Claude Sonnet 5.5、GLM 5.2（覆盖两种协议/两个不同体量的模型）。
- **操作**：
  1. 新建会话，做一个「有未完成任务和一次失败再修复」的小任务（例如先让它执行一个会报错的命令、再改正），制造出有「未完成任务」「失败经验」可言的对话。
  2. 输入 `/compact 保留未完成的任务和失败经验，摘要用中文写`（或拆成两次分别测「保留什么」「语言要求」）。
- **要读的数据**：
  - 摘要行正文 + 其下「本次压缩的附加说明：…」那一行（决策 179 §3.2）；
  - bridge 答复里的 `instructionsApplied` 字段（`true` 才算说明被真正带到了模型那里，不是 fail-safe 的 `false`）；
  - 会话桩里的 `compactInstructions`（只读结构，不读原文到仓库里，现场核对用）。
- **判定标准**：`instructionsApplied: true`；摘要正文里能看出确实保留了未完成任务/失败经验相关的内容，且按要求用中文写（如果原回合本身用英文思考/工具输出，看摘要是否仍转写成中文）。
- **用来回答**：决策 179 §9-2——「说明与模板的规则冲突时模型怎么权衡」「真实模型对说明的遵从程度」，本地假网关测不出来。

### 4.5 可选取证点：超窗恢复路径（评估结论：不测，跳过）

- **原因**：
  1. 要触发超窗（`CONTEXT_WINDOW_EXCEEDED`）需要把对话推过整个上下文窗口（远超取证点 3 的「0.8 × 窗口」自动压缩阈值），消耗的 token 比取证点 3 大得多，且一旦真超窗，DSH 会先尝试压缩再重试，失败路径不止一层，难以在预算内可控地复现；
  2. 该路径的基本功能性已经在本地假网关的 `overflow-compact` 录制场景里验证过（决策 178 §7.2），真实网关上唯一还不确定的是「服务端的超窗错误格式是否仍被 pi-ai 识别为 `CONTEXT_WINDOW_EXCEEDED`」（决策 178 §9-5），但这件事本身就有可能因为网关改写错误体而测不出有效结论，白白消耗预算；
  3. 这张账号近期在别的协议上出现过 `cache_limit`（GW-16）、503（GW-1/GW-17）等不稳定表现，长对话场景更容易撞上这些噪音，进一步降低单次尝试的信息量。
- **结论**：本轮不测。如果用户坚持要验，建议等前 4 项都成功、预算有富余时再做，且只在取证点 3 已验证成功的那个模型上追加填充到刚好超过其窗口（不是 0.8 × 窗口），单独记一次账，预算另算，一旦看到非预期的错误（如 503/400 而不是超窗提示）立即停止,不追加重试。

## 5 请求数与费用估算

计数口径沿用 P1-5：**每发一条消息、每跑一次 `/compact`、每次客户端自动重试都算 1 次**，记入本地台账（见前提 5）。

| 取证点 | 模型数 | 每模型预估请求数 | 小计 |
|---|---|---|---|
| 4.1 摘要 token 用量 | 3 | 填充 3～4 + `/compact` 1 + 少量重试余量 1～2 | 15～21 |
| 4.2 摘要上限是否被拒 | 1（主）+ 对照复用 4.1 | 填充 3～4 + `/compact` 1；可选自定义服务步骤再 +3～4 | 4～9（不做可选步骤）/ 7～13（做） |
| 4.3 自动压缩触发 | 1 | 填充 5～15（取决于该模型阈值大小）+ 验证继续 1～2 | 6～17 |
| 4.4 `/compact` 说明遵从 | 2 | 构建任务对话 3～5 + 带说明的 `/compact` 2 | 10～14 |
| **合计（不含可选 4.2 步骤、不含 4.5）** | | | **约 45～65** |
| 可选：4.2 自定义服务对照 | | | +3～4 |
| 可选：4.5 超窗（默认不做） | | | +10～30（若执行） |

**费用估算**：仓库里没有任何模型的真实单价数据——P1-4/P1-5 的既有结论是「DSH 不算费用，1.0.x 原生也恒为 0」（`costUsd` 从未实现，见 `topics/p1-5-models-and-credentials/02-dsh-facts.md`），公司网关这几个模型的真实计费口径不在本分支的调研范围内。因此费用只能用请求数 / token 量级表示，不能给出货币区间：

- 请求数：约 45～65 次（不含可选项），与 P1-5 的 60 次预算同量级，建议仍按「硬预算、超预算拒绝发送」执行；
- 输入 token 量级：每次填充 1k～10k token，取证点 3 的填充阶段可能到数万 token（取决于选中模型的阈值），**总输入量级估计在 15 万～40 万 token**；
- 输出（含摘要）token 量级估计在 **5 万～15 万 token**；
- 若需要折算成货币，需要用户提供这几个模型在公司网关的内部单价；没有这个数字之前，只能把「请求数/token 量级」当作预算口径，和 P1-5 一样。

## 6 证据怎么存

- **原始数据只留本地**：请求体、响应原文、`requests.jsonl` 台账、`.jsonl.zstd` 会话日志、宿主完整 stderr，一律写到仓库外的目录（如 `P15_RESULTS_DIR` 同类做法指到 `/tmp` 或本机 `contextFX`），不入库。
- **入库只放脱敏摘要**：新证据文件 `evidence/compaction-real-gateway-<日期>.md`，格式仿 p1-5 的证据文件——结论表在前，逐项取证的关键数字（token 数、耗时、阈值、是否成功）可以入库，但：
  - 不抄账号邮箱、key、原始错误体、网关会话 id（`sess_…`）、请求 id；
  - 复用 `p1-5-gw.mjs` 的 `scrub()` 规则清洗一遍再落盘；
  - 不截图（同 P1-5 的理由：登录后侧栏显示邮箱，登出后注册页列出邮箱域名）。
- **驱动脚本**：如果新写了脚本，放在 `evidence/compaction-real-gateway-<日期>/tools/`，和 p1-5 的组织方式一致，脚本本身能过 `biome check`、不含任何真实密钥或地址。

## 7 风险与中止条件

立即停止并原样汇报的情形：

- 网关返回 503 / `no_available_providers` 连续出现（类似 GW-1），同一模型重试 2 次仍失败——换模型或换时段，不要在失败路径上反复加预算；
- 出现 `cache_limit`（GW-16）或其他看起来和「账号当天已经积累了大量测试请求」有关的错误——停止当前模型的测试,记录现象,不猜测归因;
- 需要为了测试而手工输入任何 key / 内部地址（取证点 2 的可选步骤最容易撞到这个）——跳过该步骤;
- 页面上出现非预期的账号信息（邮箱、余额、内部域名）且需要截图取证时——不截图，改用文字描述或 CDP 读 DOM 文本后脱敏;
- 执行期间 `free -m` available 掉到 500 MB 以下,或页面明显卡顿——停下来,不要叠加第二个应用实例或测试进程;
- 单次取证点消耗的请求数远超本计划估算（例如 4.3 填充超过 30 次还没触发阈值）——停止这一项,记录「阈值预测与实际不符」为发现,不要无限加码。
