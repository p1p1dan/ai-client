## ① pi 上「想了多久」从来没显示过

**探针结论**：`piRuntime.ts` 里 `thinking.completed` 出现 **0 次**。它只发
`thinking.started`。

而 `reduceTurnTiming` 是用 `completed.timestamp - started.timestamp` 算时长的 ⇒
`durationMs` 恒为 null ⇒ `formatThoughtRow` 落到它的「历史消息」分支，
返回一个**光秃秃的 `Thought`**。**pi 后端上的每一次思考都是这样。**

⚠️ 那条分支本身不是 bug（恢复的历史确实没有计时数据，硬编一个数字更糟）——
它只是在回答一个当时还没人问的问题。

**为什么 pi 不发这个事件**：pi 根本没有「思考结束」这种事件，thinking 只是
content block 停止增长而已。**边界得由 Host 自己定**，然后说出来。

**取的两个边界**（`completeThinking`）：

- **模型开始作答**（`emitTextDelta`）—— 这是思考真正结束的时刻，也是两者中更紧的那个测量；
- **消息先结束了**（`closeProseStream`）—— 覆盖「想完直接去调工具、一个字没写」的回合。

**必须幂等**：同一个块两条路都可能触发，而第二次 `thinking.completed` 会用**更晚的
时间戳覆盖** `durationMs` —— 7 秒的思考会因为消息恰好一分钟后才结束而被报成 60 秒。
已用 `thinkingCompleted` 标志挡住，并且**这条有专门的断言**（渲染侧那份测试里直接
演示了「发两次会变成 60s」）。

发射点在 `openProseMessage` 换容器**之前**：换容器会把 thinking 块的 id 一起换掉，
刚结束的那次思考属于此刻还开着的那个容器。

## ② markdown 分段：实测对比后保留我们的 —— **但这是取舍，不是对方有缺陷**

> ⚠️ **本节是订正过的。** 初版我写的是「pi-app 会把前缀切在未闭合的 fence 里，
> 提交的那半渲染成一个未闭合的 fence」，并据此说我们的更好。**用户当场追问「差异
> 在哪、凭什么说我们的更好」，追问是对的**：我只测了 pi-app 那个**函数**，
> 没看它的调用方，也没验证 CommonMark 对未闭合 fence 的实际行为，
> 就把一个 trade-off 说成了缺陷。下面是补测后的真实情况。

**先纠正事实**：**未闭合的 fence 不是错误。** CommonMark 会在文档末尾自动闭合它。
用本应用真正在用的解析器（`mdast-util-from-markdown`）实测：

```
'…\n```ts\nfunction a() {\n  return 1;\n'
→ [{type:'paragraph'}, {type:'code', lang:'ts', value:'function a() {\n  return 1;'}]
```

⇒ pi-app 提交的那半渲染出来是一个**完整合法、语法高亮正常、只是短一点**的代码块，
不是坏掉的渲染。

**再看差异有多大**：拿一段含空行的 13 行代码块逐行流式喂进两边，统计每一步各自
提交了多少字符：

| 流到第几行 | 结果 |
|---|---|
| 3–9 | **两边完全相同** —— 整个 fence 都在纯文本尾巴里 |
| **10–13** | pi-app 领先：它在**代码块内的空行**处切了一刀，提交了一个部分的、已高亮的代码块 |
| 之后 | fence 闭合，两边都提交完整块 |

⚠️ **10–13 这个区间是实测出来的，不是我预测的**：我以为会停在 12（fence 闭合那步），
实际到 13 —— 因为我们的分段器是在块**后面的空行**上才结算，而不是在 fence 行上。

**另一条实测**：代码块里**没有空行**时，pi-app 提交的字符数与我们**完全相等**
（它三条规则里只有 `\n\n` 那条能在代码里触发；另两条要么需要换行后还剩 56 字符，
要么需要句末标点）。

⇒ 真实的取舍是 **「早出但会重排」（他们）vs「晚出但稳定」（我们）**：

- **我们的优势**：已提交的段落**语义永不被重新解释**，而且这个保证在
  `chatMarkdownPolicy.ts` 头注里有 CommonMark 层面的论证（所有 inline 构造都死在
  空行上；能跨空行的只有 fence / `$$` / HTML block，前两者显式跟踪，后者是已登记偏离）。
- **他们的优势**：长代码块流式时更早出现语法高亮。我们的代价是**整个代码块在闭合前
  一直是无高亮纯文本** —— 对长代码块这个体验其实更差。
- **他们的代价**：fence 闭合时块边界会跳（几行从纯文本移进代码块，整块重渲一次）。

**所以「保留我们的」= 没有足够理由换，不等于对方是坏的。**

### ⇒ 用户拍板（2026-08-30）：「可以按照 pi-app 的来」

于是本批**改了行为**：流式中的代码块不再是纯文本，交给解析器渲染成真代码块。

**但没有照抄它的机制**，因为那会撤掉一个实测过的 39× 性能优化（pi-app 把整个已提交
前缀当**一份文档**每帧重解析；我们是**分段 + memo**，100KB/40 帧实测 6379ms vs 165ms）。

落地形态：`ClosedPrefixSplit` 新增 **`openFence`** —— 尾巴里那个**尚未闭合**的代码块
单独拿出来交给 `<ChatMarkdown>`，其余尾巴照旧是纯文本。

**为什么安全（和空行规则是两套论证）**：**fence 内部的内容是字面量**，追加行不可能
重新解释已有的行，能变的只有块在哪里结束；而 CommonMark 会在文档末尾自动闭合未终止的
fence。⇒ 渲染「目前为止的 fence」显示的就是它已有的那些行，闭合时只是**继续追加**。

⚠️ **这一点上我们的结果比 pi-app 更好**：他们的已提交前缀在真正的闭合 fence 到达时
要重新切一次，几行会从纯文本**跳进**代码块；我们的块只增不改。

**刻意的边界**：只处理**未闭合**的 fence。已经闭合的 fence 后面跟的散文仍是在途文本，
交给解析器就会重新引入空行规则要防的那种「中途被重新解释」。

**`closedLength` 不包含 `openFence`** —— 它没有 settle，高水位线不许越过它；它也不是
`segment`，所以已 settle 段落的 append-only 与 memo 命中不受影响，只有这一个块每帧重解析
（代价被**当前代码块**的大小限住，而不是整篇回答）。

## ③ 刻意没取的两样

- **`stream-text-reveal` 的 2 字符淡出尾巴**：纯视觉修饰（读了源码，它明确写了
  "no buffer delay behind real stream speed"），不是性能机制。T12 的视觉基线用户
  2026-08-29 刚看图确认过，往里加一个没人要的动效不合适。
- **`ThinkingChainBlock` 的随机 live 文案**：它按文本 hash 从
  `thinking`/`briefly`/`working`/`reasoning` 四选一。我们的 `formatThoughtRow` 输出
  稳定的 `Thinking` / `Thought briefly` / `Thought for Xs` —— 信息量相同，而稳定的
  标签比 hash 随机的更好，不是更差。

## 方法论教训（本批最该带走的一条）

**只测一个函数，不看它的调用方，就给整套方案下优劣结论 —— 这是越界。**

具体错在三步：① 只 grep 了 pi-app 那个文件里有没有 fence 关键词，没查
`splitStreamingMarkdown` 被谁调用、调用方怎么用那两半；② 没验证「未闭合 fence 会
怎样被渲染」这个**决定性前提**，凭直觉当成了坏结果；③ 把结论写进了测试头注和
roadmap，让一个未经验证的判断获得了证据的外观。

**判据**：说「A 比 B 好」之前，至少要能回答「B 那样做，用户实际看到的是什么」。
答不上来就只能说「我们没有理由换」。
