# Open Questions — pi 资源接入与斜杠命令

> 只放**未解决的问题**，不放任务。解决后移出本文件，把结论写进 decisions 或对应 topic。

## Q-R1 — 非托管模式下要不要做磁盘预览目录？

R02-b 整片跳过了 pi-app 的 `scanStaticSlashCommands(cwd)`，理由是托管模式下它会
**列出实际不会加载的命令**（项目那部分被信任开关挡掉），比没有补全更糟。

但**非托管模式下项目级技能和模板是真的加载的**，而补全菜单不会列出它们——
界面与实际不一致，方向和托管模式相反：那边是「列了但不生效」，
这边是「生效但不列」。后者危害小（用户仍能手打），但仍是一处不一致。

**要拍板的是**：非托管模式要不要单独走一条按 cwd 查的路径。
代价是命令目录从「全局一份」变回「每个工作目录一份」，缓存与失效都要跟着改。

**建议**：等有非托管模式的真实用户反馈再说。现在托管是默认路径。

## Q-R2 — 要不要借用用户已装的插件？

技术上是同一个口子（`additionalExtensionPaths`，我们加载随包权限插件就是用它）。
[D01](./decisions/001-borrow-user-pi-resources-not-symlink.md) 决定 R01 只借技能与模板。

**借插件多出两件事**：

1. 插件是可执行代码，不是纯文本资源
2. `@gotgenes/pi-permission-system` 必须按包名排除——我们随包的 27.0.1 打了补丁，
   加载用户那份（31.0.0）会让 `bundled` 策略作用域静默失效

**建议**：等 R01 用起来之后看有没有人真的要。若要做，形态是设置里列出检测到的插件、
默认全不勾、权限系统那个直接不列。

## Q-R4 — TUI 模式下借用不生效，要不要补？

R01 落地后，**GUI 会话能看到用户 `~/.pi` 里的技能与模板，TUI 会话看不到**。

原因是机制不同：GUI 侧我们自己调 SDK，可以传 `additionalSkillPaths`；
TUI 侧跑的是真的 pi 命令行（`PiTuiPty` 用 node-pty 起进程），
它只认自己的 agent dir，不读我们的环境变量。
`resolveManagedPiPtyEnv()` 因此显式剔除了那个变量——留着会宣称一个没发生的借用。

**后果**：同一台机器上同一个用户，切到 TUI 就少了一批技能，而界面不会说为什么。

**可能的补法**（都没验证）：

1. pi CLI 有没有指定额外资源路径的命令行参数或配置字段
2. 在托管 agent dir 里对用户的 `skills` / `prompts` 建目录级符号链接——
   比 [D01](./decisions/001-borrow-user-pi-resources-not-symlink.md) 否决的
   「链整个配置目录」窄得多，凭据和 settings 都不在范围内，
   但仍有 Windows 权限问题，且需要处理用户后来删除源目录的情况
3. 接受差异，在 TUI 入口处说明

**建议**：先看 R01 在 GUI 里用起来的效果。如果用户主要在 GUI 里工作，这条可以一直搁着。

## Q-R5 — `pi-workspace-history` 卡在一个「声明的」而非「真实的」版本冲突上

R03 原定随包三个插件，实际只落地两个。`pi-workspace-history` 装不进去：

```text
npm error Could not resolve dependency:
npm error peer @earendil-works/pi-coding-agent@"^0.84.4" from pi-workspace-history@0.4.1
```

它**每一个**发布过 `@earendil-works` 名字的版本（0.3.0 / 0.3.1 / 0.4.0 / 0.4.1）
都写着同一条 `^0.84.4`；再往前的 0.1.x / 0.2.x 挂在旧的 `@mariozechner` 名下，
不是同一个包。而我们锁 `0.84.3`，差一个补丁号。

**那条边界是声明出来的，不是真实的。** 逐个核对了插件在
`.pi/extensions/workspace-history.ts` 里实际用到的 SDK 面：

- 七个 import 全是 `import type`，运行时会被擦掉
- 五个运行时方法（`pi.exec` / `pi.on` / `pi.registerCommand` /
  `ctx.navigateTree` / `ctx.waitForIdle`）在 0.84.3 的 `.d.ts` 里都在
- 十一个订阅的事件名在 0.84.3 的事件联合里都在

换句话说 `^0.84.4` 是上游的保守取整，不是它需要 0.84.4 的某个新东西。

**但 `overrides` 三种写法 npm 全部拒绝**（嵌套形式、`$` 引用形式、顶层形式），
每次都是同一条 ERESOLVE。剩下的路只有三条，都不该顺手做：

| 做法 | 代价 |
|---|---|
| SDK 抬到 `0.84.4`+ | `preflightHostDeps` 强制**精确 pin**，抬版本要重跑整套 worker 门禁，是独立一片 |
| `--legacy-peer-deps` | 全局关掉 peer 校验，为一个插件放弃另外三个包的保护 |
| vendor 进仓 | 要自己跟上游同步，且这个包的价值（撤销安全网）撑不起这个负担 |

**要拍板的是**：等 SDK 例行升版时顺带带上它，还是现在就为它单开一片抬 SDK。

**建议**：等。它是撤销安全网，不是安全缺口——缺了它没有任何东西变得不安全，
这跟子代理换包那条的性质完全不同。SDK 抬版本时在同一片里试装一次即可。

## Q-R3 — `pi-web-access` 的 170M 值不值？

免配置（默认走 Exa 公共服务，不要 key）、能力最全（搜索、正文提取、
GitHub 仓库 clone、PDF、视频理解），用户原话「随包默认用 pi-web-access 好一点」。

**但实测净增 170M**：只装 pi SDK 是 131M，加它之后 301M。包本身只有 7.5M，
炸在依赖树上（正文提取、PDF 解析、DOM 模拟）。

给出体积证据后用户未再坚持，R03 暂定放推荐列表。

**若日后要随包**，先查它的依赖能不能按能力裁剪（只留搜索与正文提取，
砍掉视频和 PDF）。另外联网默认开还有隐私姿态问题：默认就往第三方服务发查询。
