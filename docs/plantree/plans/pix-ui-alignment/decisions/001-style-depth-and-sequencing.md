# D01 — 风格对齐深度与排期

- **日期**：2026-09-02
- **状态**：Active
- **拍板人**：用户

## 背景

用户体验 pi-app 与 pix 后提出一批界面改造诉求。其中「视觉风格向 pix 靠拢」有三种深度完全不同的做法，工作量与回归面差一个数量级；同时 Pi-only 收敛计划的 T37 发版门禁尚未收口，两批工作抢同一份代码基线。

这两件事必须先定，否则后续每个任务的范围都悬空。

## 决定一：样式层只对齐密度与字体

**采纳**：保留现有 `docs/design-system.md` 的语义 token 结构与颜色体系，只把字号档、行高、间距档、圆角档、中性灰阶向 pix 靠拢。

**未采纳的两个方案，以及原因**：

- *整套替换成 pix 的 token 体系*（含 `--surface-panel` / `--surface-muted` / `--surface-soft` 三层表面、`--link` / `--switch-on` / `--chip` 等）。视觉上最像 pix，但 `docs/design-system.md` 是 CLAUDE.md 里的强制规范，整套换等于重写规范，且全仓每一处界面都要重新点验。用户判断收益不值这个回归面。
- *新增可切换的「Codex 风格」皮肤*。风险最低、可回退，但要长期维护两套视觉，此后每个新组件都得过两遍。用户判断维护成本不划算。

**边界**：本决定只约束**样式 token 层**。组件形态（输入框布局、小控件样式、输出内容的渲染形式）是另一层，逐件对照后单独定，见 roadmap 的 U09。用户 2026-09-02 补充原话：「我对 pix 的喜爱包括但不限于它的整体布局，内容展示，聊天输入框以及小控件，还有输出内容的展示形式」，落点是组件层而非 token 层。

## 决定二：T37 收口后再开工

**采纳**：先把 Pi-only 收敛计划的 T37-d 剩余项（license notices、migration docs、release notes、CI packaged 触发）收口，打出可发布基线，再启动本计划。

**理由**：T37 剩的是发版文书与 CI 触发，收口成本低；大面积改 UI 期间如果没有干净的对照基线，出现回归时无法区分是 UI 批引入的还是既有问题。

**未采纳**：并行推进（UI 优先）、以及「只先做免绑定开聊一条」。后者曾被考虑是因为它是能力缺口而非视觉问题，但用户选择整批排在 T37 之后。

## 决定三：消息操作本轮只要复制

**采纳**：只保留「复制」。「回退」（pi-app 有）与「在新会话中继续」（pix 有）用户明确表示不是最高优先级，进 Deferred。

**实况修正**：复制功能**本仓已经存在**（`MessageTimeline.tsx:1409` 的回合级复制按钮），所以本条实际是「确认已满足，无需新建」，不是一个待办任务。

## 后果

- roadmap 的所有任务默认 Deferred 到 T37 收口，不设并行分支。
- 样式层任务落地后必须同步更新 `docs/design-system.md` 的 Token 分档，否则强制规范与实现脱节。
- 组件形态对齐（U09）需要先产出对照表再拍板，不在本决定的授权范围内。
