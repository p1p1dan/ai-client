## 决定一：双栏模式的语义（解 Q05）—— **已被 [D07](./007-two-column-is-two-columns-and-one-bar-per-column.md) 推翻**

> **2026-09-04 撤销**：本条写「双栏 = 内容栏 + 右辅助栏，右栏仍承载 `context`」，
> 而同批产出的原型 `a10-pix-ui-alignment-prototype.html` 画的是 `[data-mode="two"] .right
> { display: none }`——右栏整个消失。代码跟了本条，于是「双栏」渲染出三列。
> 用户看到实际界面后拍板以原型为准，改由 [D07](./007-two-column-is-two-columns-and-one-bar-per-column.md) 决定一执行。
> 下方原文保留：当时的推理（「双栏专注对话/开发，不为它另起 surface 承载方案」）本身没有错，
> 错的是由此推出「所以留一个只放 context 的右栏」——那仍然是第三列。

**采纳**：双栏模式 = **只承担 AI 对话与 AI 开发**。Files / Git / Terminal 等既有 surface 在双栏下**刻意不提供长期入口**——需要看文件、跑 git、开终端时，用户**切回三栏模式**使用，而不是在双栏里为它们另设浮层、标签页或抽屉。

**理由**：用户在拍板时原话——「双栏模式，我认为就只主要进行 AI 对话和 AI 开发，不怎么需要看文件，git 和终端什么的功能」。既然双栏的定位就是专注对话/开发，为它另起一套 surface 承载方案（浮层 / 中栏标签页 / 抽屉）属于**为不会被用到的场景买单**，与「利落简约」的诉求相悖，也违背 D01 的「收益撑不起回归面」判断。

**对 U02 / U03 的影响**：

- **U02（布局模式开关）** 的双栏分支因此**收敛为「精简栏」语义**：双栏 = 内容栏 + 右辅助栏，右栏仍承载 `context`（上下文预览）；Files / Git / Terminal / editor 等开发面板**不属于双栏**。这同时回答了两个待定：双栏下不引入新的 surface 承载方式，三栏才是「什么都能干」的模式。
- **U03（TUI 收起右栏）** 与 U02 是耦合的模式状态机问题，合并设计成立；双栏语义定下来后 TUI 形态 = 左栏 + 右侧整块 TUI，属双栏的「专用子模式」，右侧不再有其他 surface。
- 三栏模式下，`run` 面板的挂载位置仍需在 U06 单独定（右栏顶部切换？还是独立栏位？），不在本决定范围。

## 决定二：免绑定工作目录会话的 cwd 与信任态（解 Q01）

**采纳**：cwd 落在**隔离临时目录**，该类会话**默认不信任**（不满足项目信任门 `projectTrusted`），**逐次请求授权**，写入路径默认拒绝。

**理由**：这是安全边界，不是交互细节。没有绑定目录的会话，agent 工具可读写范围由 cwd 决定；落在用户主目录暴露面过大，落在临时目录则把默认暴露面压到最小。默认不信任 + 逐次授权 + 写路径默认拒绝，与 Pi 计划 T05 的项目信任门语义一致，且可复用同一套授权机制。

**对 U05 的影响**：

- 免绑定路径是新开的，**不**复用「welcome 引导卡」的等待逻辑（`chatEmptyState.ts` 的 `deriveChatEmptySurface` 会挡住发送）。
- 这类会话在 UI 上要有**身份标识**（区别于已绑定项目的工作态会话），且信任态可升级——用户在其中显式绑定目录后，按正常信任门流程走。
- 涉及的安全实现细节（临时目录的创建/清理、cwd 注入 pi runtime、授权落点）在 U05 切片实现时细化，但**方向已定死**，不再是「顺手机动」。
