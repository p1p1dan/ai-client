# D04 — 免绑定会话跨重启可见性：给索引行加 `unbound` 标记（解 Q13）

- **日期**：2026-09-03
- **状态**：Active
- **拍板人**：用户（采纳 [Q13](../open-questions.md) 三条候选中的第三条）

## 背景

批次 4 落地免绑定开聊后暴露一个**既有**缺口：免绑定会话的索引行里 `workspacePath` 记的是隔离临时目录，
重启后这个路径没有对应的 `ChatWorkspace`（它本来就不该出现在项目树里），于是
`mergeSessionIndex`（`sessionIndexMerge.ts:139-153`）把它判为 orphan 丢掉——对话历史还在 pi 的 JSONL 里，
但侧栏看不到、用户也没有入口打开。

这条丢弃逻辑本身不是 bug：它同样处理「用户移除了一个文件夹，其名下会话失去宿主」。免绑定会话只是把这种
罕见情况变成常见情况。详见 [U05 evidence §七](../evidence/2026-09-03-u05-u03b-unbound-chat.md)。

## 决定：索引行显式标记 `unbound`，侧栏合成临时分组

**采纳**：

1. `SessionIndexEntry` 增加**可选** `unbound?: boolean`。
2. Main 在 `recordCreated` 时按 `ScratchWorkspaceService.isScratchPath(workspacePath)` 写入。
3. `mergeSessionIndex` 见到 `unbound` 就把该行合成到一个临时分组里，**不再**走 orphan 丢弃分支。

**理由**：这是三条里唯一**行为诚实**的一条——会话确实还在，索引里也确实有行，用户就应该能看见并打开它。
另外两条都是用「让它消失」来掩盖「它存在但不可见」，等于把数据留在磁盘上却拒绝承认。

标记由 Main 从路径推出、而不是渲染器声明，与 U05-c 已确立的 `unbound` 归属一致（渲染器不能自称免绑定）。

**未采纳**：

- *路径一：不管*。临时会话用完即弃这个说法只对「用户主动关掉」成立；崩溃或正常退出后历史仍在磁盘，
  索引会攒下永远看不见的行，越攒越多且没有清理入口。
- *路径二：退出时自动归档*。会丢掉用户可能还想接着聊的历史，且「归档」在本仓语义是用户的显式动作，
  由系统代劳会污染这个语义。

## 约束与已知陷阱

- **索引文件是裸 JSON 数组**（`sessionIndex.ts` 头注释）：只能加**可选的 per-entry 字段**，
  不能包 envelope、不能加版本号——否则旧 build 解析抛错、以空索引启动、下次 flush 写回 `[]`，全部会话消失。
- **`recordCreated` 是逐字段重建，不是 spread**（`SessionIndexService.ts:71-103`）：新字段必须显式带
  `?? existing?.unbound`（或每次重新推导），否则第二次 `recordCreated` 会把标记抹掉。
  `agent` 字段栽过同样的坑，注释就写在那里。`commitResumed` 用 `...existing`，不受影响。
- **不做静默写迁移**：批次 4 之前创建的免绑定会话行没有这个字段，保持原样；不在 load 时回填，
  理由与 `agent` 字段相同（load 时 normalize 会让下一次无关 flush 把字段刷进每一行，
  把兼容读变成不可逆写迁移）。这批老行仍然不可见，属已知残留。

## 后果

- 触及**共享类型 + Main 写入 + 渲染器合并**三处，超出批次 4 范围，因此单独开为 roadmap 任务
  **U13**，排在批次 5（U08-2）之后。
- 临时分组的展示形态（分组标题、是否可折叠、行内是否复用 U05-b 已有的 `temporary` chip）留给 U13 实施时定，
  不在本决策里锁死。
- 「用户移除文件夹后其会话变 orphan」这条既有行为**不在**本决策范围内，保持现状。
