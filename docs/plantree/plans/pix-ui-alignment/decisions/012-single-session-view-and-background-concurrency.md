# D12 — 中栏回到单会话视图，后台并发由 worker 池明示承担

**日期**：2026-09-06
**拍板人**：用户（点验反馈第 5 条 + 三个后续选项）
**触发**：批次 8 落地的会话 Tab 条在真实使用中「确实很别扭」。
用户点名要回到 D08 之前那种「chat 页只显示一个对话，点左栏标题直接切换」的形态，
但附加了一条 D08 之前**没有**的要求：切换走的会话，任务要照常执行。

## 推翻了什么

- **[D08](./008-vscode-dock-shell.md) 决定三**（中栏一个已启动会话一个横向 Tab）——整条作废。
- **[D09](./009-tab-close-ends-conversation.md)**（关 Tab = 结束对话）——随载体消失而失效。
  它解决的问题（「关掉的东西在后台还活不活」）由本决定的并发模型重新回答。

D08 决定一、二、四（图标轨道 + 面板、右栏只做文件与编辑器、删列数开关）**继续有效**。
本决定只动中栏的会话载体。

## 取证结论：后台继续执行不是新功能，是既有能力没被说出来

开工前先查了 `WorkerManager` 的回收规则（`WorkerManager.ts:1962` `isSafeToEvict`），
一个 worker 要被回收必须**同时**满足四条：

1. 它不是当前前台会话（`ownerWebContentsId === null`）；
2. 它没有正在执行的回合（`activeRequestId === null`）；
3. 它没有待审批的阻塞请求；
4. 它没有进行中的会话树变更。

第 2 条意味着**正在跑任务的会话从来就不会被回收**。而 `claimEntry`（同文件 1922 行）
的语义是「一个窗口同时只认领一个 entry」——认领新会话会把旧会话的 owner 清空，
所以「切走」在 Main 看来就是「不再是前台」，不是「关闭」。

**因此用户担心的「切走了任务就停」在当前架构下不会发生。**
D08 引入 Tab 时并没有为此增加任何后台能力，Tab 只是把「哪些会话已启动」画了出来；
去掉 Tab 也不会减少任何后台能力。真正缺的是三样东西：一个能替代 Tab 的启动态提示、
一个够用的并发上限、以及回收发生时的说明。

## 决定

### 决定一 — 中栏只显示一个会话，点左栏那一行切换

删除 `openSessionIds` 有序打开态、会话 Tab 条与 `+` 新建按钮。
`activeSessionId` 重新成为中栏显示什么的唯一依据。
GUI/TUI 开关与 D08 把它放在 Tab 条右端的安排一并回到中栏横条。

左栏列表**保留** U15-c 那套启动态标记（实心 = 运行中 / 空心 = 已启动 / 无 = 未启动）——
Tab 条消失后，它成为「哪些会话在后台活着」的唯一出口，比之前更重要。

### 决定二 — 并发上限放宽到 10，按内存自动降档

`resolveDefaultWorkerCapacity` 现为 4 / 3 / 2（按 >8GiB、4–8GiB、≤4GiB 三档），
`AICLIENT_PI_WORKER_CAPACITY` 的合法区间是 1–8。

改为**默认与硬上限都提到 10**，降档规则保留并按同一比例上移。
理由是用户按「同时开着的对话数」提的这个数字，而每个活跃会话是一个独立
utilityProcess 加一份模型上下文——内存是真实成本，小内存机器仍要降档，
否则开满之后的表现是 `worker_capacity_reached` 报错，比少开几个更糟。

### 决定三 — 回收时提示一次，不改回收策略

保持「自动回收最久没用的空闲会话」这个策略本身（用户在三个选项中选了它，
没有选「先问你放弃哪个」）。改的是它现在是**静默**的：
回收发生时要在界面上说明「某某会话已转入后台，点开可继续」。

不采用「弹窗让用户挑」是因为它把一次后台维护变成一次必答的中断，
而回收的实际代价只是下次点开要重新加载（pi 会话是文件持久的，内容一条不少）。

## 未采纳的两个方案

- **保留 Tab 条但改成只读的「后台会话指示器」**。它仍然占一条横条的高度，
  而同一份信息左栏列表已经在表达；批次 8 的教训正是 chrome 层数太多。
- **把空闲超时（15 分钟）一并延长或取消**。它与上限是两条独立的回收线，
  用户这次只对上限提了要求；动它需要单独的资源取证，留作 open question。

## 影响与代价

- **U15-c 的验收看点 ③④ 作废**（「点左栏会话在中栏新开 Tab、可多开、可关」
  与「关 Tab 后会话仍在左栏列表里」）——描述的控件不存在了。
  ①②⑤⑥ 继续有效。
- **U19 的确认框失去载体**。「结束这个对话的运行时」这个动作本身仍然需要一个入口，
  但它不再挂在关 Tab 上；落点见 roadmap U24。
- **fullscreen diff 藏掉 Tab 条**这个 U15 遗留问题自动消失（没有 Tab 条可藏）。
- 内存占用上限按 10 个 worker 重新估算，需要在 U24 的 evidence 里实测留档。
