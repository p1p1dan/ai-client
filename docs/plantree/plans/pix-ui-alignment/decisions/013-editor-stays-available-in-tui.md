# D13 — TUI 下也能看文件：编辑器列不再被 TUI 抑制

**日期**：2026-09-06
**拍板人**：用户（二选一中选「TUI 下也能看文件」）
**触发**：累计 GUI 点验反馈第 3 条——「TUI模式为什么点击文件没有编辑窗口了，只有一个大的chat页面」。

## 推翻了什么

**[D02](./002-layout-cwd-and-evidence-scope.md) 中「TUI 是布局的极限形态」那一条**，
以及它在 U03-a 里的落点 `WorkspaceShell.tsx` 的
`const editorAllocated = !isTui && editorOpen`。

D02 其余部分不受影响。D19 的「TUI 交接由单一写者负责」也不受影响——
本决定只动布局分配，不碰 `presentationMode` 的写入路径。

## 根因：一行代码的含义被后来的改动换掉了

U03-a 写下那行时，右栏还是一个能装多样东西的面板（Context、Run、文件……），
「TUI 时收起右栏」的意思是**把宽度让给终端**，代价只是少看一个面板。

[D08](./008-vscode-dock-shell.md) 之后，右栏**只剩文件与编辑器**。
于是同一行代码的含义变成了「终端开着的时候你不能看文件」——
点文件毫无反应，连一个「为什么没反应」的提示都没有。

**这不是缺陷代码，是一条过期的决定。** 写它的时候它是对的。

## 决定

`editorAllocated` 不再由 `isTui` 参与判定，等于 `editorOpen`；
右栏的挂载条件同步去掉 `!isTui`。终端与编辑器在 TUI 下并排共存。

## 为什么这不会毁掉 D02 想要的形态

`editorOpen` 派生自 `tabs.length`（`deriveEditorOpen`）——**没有打开任何文件时它为假**。
所以「dock + 一整条终端」仍然是 TUI 的默认样子，只是不再被强制。
用户主动点开一个文件，才会分出编辑器列；关掉最后一个标签页，终端自动收回整行。

代价是明示的：TUI 下开着文件时，终端确实变窄了。
但那是用户当场用一次点击换来的，而不是他无从影响的固定规则。

## 未采纳的两个方案

- **TUI 下点文件弹一个「请先切回 GUI」的提示**。它把一个布局限制变成了一次教学，
  而限制本身没有理由存在——右栏容得下，中栏也没有必须独占的道理。
- **TUI 下让文件在覆盖层里打开（盖住终端）**。`expanded` 覆盖层已经能做到这件事，
  且它对 GUI/TUI 一视同仁；再为 TUI 单独定一条「只能覆盖、不能并排」的规则，
  就是又一条会在下一次布局改动里过期的特例。
