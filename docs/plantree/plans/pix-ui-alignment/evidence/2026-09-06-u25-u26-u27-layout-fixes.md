## 一、U26 — TUI 下也能看文件（[D13](../decisions/013-editor-stays-available-in-tui.md)）

### 根因不是缺陷代码，是一条过期的决定

`WorkspaceShell.tsx` 的 `const editorAllocated = !isTui && editorOpen` 是 U03-a 按
D02「TUI 是布局的极限形态」写的。写它的时候右栏还能装 Context、Run、文件等多样东西，
「TUI 时收起右栏」的意思是**把宽度让给终端**。

[D08](../decisions/008-vscode-dock-shell.md) 之后右栏**只剩文件与编辑器**，
同一行代码的含义变成「终端开着就不能看文件」——用户点文件毫无反应，连提示都没有。

### 改动

两处去掉 `isTui` 项：宽度分配 `editorAllocated = editorOpen`，
以及右栏的挂载条件 `{(editorOpen || fileIntentPending) && (`。

**D02 想要的形态没有丢**：`editorOpen` 派生自 `tabs.length`，没开文件时为假，
所以「dock + 一整条终端」仍是 TUI 的默认样子，只是不再被强制。
关掉最后一个标签页，终端自动收回整行。

**未动**：`chatVisible = isTui ? true : chrome.chatVisible` 与
`diffTabActive: !isTui && diffTabActive` 保持原样——终端**住在 chat 列里**，
在 TUI 下隐藏 chat 等于隐藏终端本身。这两条有断言守着。

## 二、U27 — 左栏图标轨道与标题行对齐

用户诉求：轨道整体下移，与右侧栏目「标题栏下方的内容页」齐平。

现状是 `<nav>` 从 dock 顶部一路到底，而这个壳里**其它每一列都以一条 `h-9` 横条开头**
（面板自己的 `DockTitle`、中栏的 `SessionBar`、编辑器的标签条）。
轨道不参与这条基线，于是第一个图标自成一行，跟谁都不齐。

**改动**：`<nav>` 的第一个子元素改为 `<div aria-hidden className="h-9 shrink-0" />`，
同时**去掉原来的 `pt-1`**——4px 的内边距叠在 36px 占位上，正好是这次要消除的那种错位。

用与标题行同一个 `h-9` token 而不是某个 padding 值：要跟随的就是那条横条的高度，
两边读同一个 token，标题行将来若改高度，这里的偏移不会独自留在原地。

## 三、U25 — 窗口最小尺寸（方向已由用户改定）

### 原方向被推翻

上一轮我给出的定性是：布局分配器给聊天列 400px、编辑器列 520px 设了地板，
空间不足时**故意溢出**而非压缩（`overflowWidth` 就是记这个），
编辑器工具条最右端的按钮因此被推出可视区。

用户 2026-09-06 拍板：**不做复现，也不做压缩**，
「就是不要在窗口太小的时候出现图标挤兑异常的现象就行（限制最小画幅）」。

### 改动

新增 `src/shared/shellMinimums.ts`：

```
SHELL_MIN_WIDTH = SIDEBAR_MIN_WIDTH(324) + CHAT_MIN_WIDTH(400) + EDITOR_MIN_WIDTH(520) = 1244
```

`MainWindow.ts` 的 `minWidth: 685` 改为 `SHELL_MIN_WIDTH`，`minHeight` 同样改为常量
（值仍是 600，垂直方向没有报告问题）。

**为什么用左栏的「展开态最小宽」而不是收起态的 44px 轨道**：
按轨道算得 964px，但用户一旦打开面板，溢出立刻回来——而这不是他能预判的。
地板取的是「**每一种合法布局状态都放得下**」的最小窗口，不是「某一种放得下」。

**为什么放在 `shared/`**：推导用的数字归渲染层的布局模型，
而必须遵守它的窗口在 Main 创建。任一侧留一份拷贝就是同一个尺寸的第二个真相，
而且会悄悄漂移——症状是几个月后「按钮又跑到屏幕外了」。
`shellMinimums.test.ts` 直接读渲染层源码核对这三个常量，漂移在测试里失败，不在截图里。

## 五、改写的既有断言（一处）

**`panelVisibilityStatic.test.ts`**「空编辑器列不占布局盒、但待处理的 file intent 仍要挂载它」——
断言串里的 `{!isTui && (editorOpen || fileIntentPending) && (` 去掉 `!isTui`。
这条测试守的两个不变量（intent 必须有消费者、只有 `editorOpen` 才给布局盒）**都没变**，
且 D13 去掉的正是让该测试描述的死锁在 TUI 下复发的那一项：
`!isTui` 让右栏在终端开着时无法挂载，而 D08 之后文件只在右栏打开——
于是 TUI 下点文件就是 round-10 ⑥ 记录过的那个零消费者死锁。

## 七、欠项

- **GUI 点验未做**。看点：① TUI 下点文件，编辑器与终端并排出现；
  ② 关掉最后一个文件标签，终端收回整行；③ 左栏图标第一个与面板标题行下方内容齐平；
  ④ 窗口拖到最窄时编辑器工具条右端按钮仍完整可见可点。
- **U25 的原始现场从未复现**。定性来自代码路径，改法按用户拍板换成了限制窗口，
  所以「1244px 是否真的够」这件事只有算术保证，没有实测。点验第 ④ 条就是补这个。
- **`minWidth` 变大的代价未评估**：小屏（如 1280×800）用户现在无法把窗口缩到很窄，
  1244px 已接近这类屏幕的可用宽度。若有人反馈，退路是让左栏在窄窗口下先被压缩，
  再把地板降到收起态的 964px。
