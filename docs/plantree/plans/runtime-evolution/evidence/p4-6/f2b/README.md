# F2-b 取证 · 临时会话删除前 / 删除后 / 重启后

Role: evidence。日期：2026-09-11。对应[执行顺序](../../../README.md#执行顺序)第 5 批第 5 项与
[F2-b 取证要求](../../../topics/field-followups.md#f2-b-取证)。

`node scripts/run-f2b-probe.mjs`。原始输出 [f2b-report.json](f2b-report.json)。

要求里写明了不许怎么推断：**不能凭 UI 消失推断文件被物理删除**。所以每个时点都从两侧各取
一份——`session-index.json` 直接读磁盘、临时目录直接 `ls`——而不是问界面。

## 先把三个入口分开

侧栏里一条临时对话，鼠标划过会出现三个按钮，语义完全不同：

| 入口 | 走哪条链 | 做什么 |
|---|---|---|
| **关闭**（`Close session`） | `chat:closeSession` | 解绑 worker，把行从侧栏移掉。**不写索引，不删目录** |
| **归档**（`Archive session`） | 行内按钮 → 确认框「归档」→ `chat:archiveSession` | 索引置 `archived:true`；unbound 会话还会 `scratchWorkspaceService.release()`，**目录当场删掉** |
| **删除**（只有临时行才有的第三个按钮） | `temp:workspace:*` 的确认+删除链 | 本轮未测，见末尾 |

还有一条与三个入口都无关、却决定第三个时点的事实：`ScratchWorkspaceService` 在**应用启动
和退出时都会 `wipeAll()`**，把整个 scratch 根目录连锅端。

## 三个时点的实测

两条临时会话，各发一句真实消息把目录逼出来，然后一条走「关闭」、一条走「归档」，
这样一次重启就把两条路都记全。

| 时点 | 走「关闭」的那条 | 走「归档」的那条 | scratch 根目录 |
|---|---|---|---|
| **T0 删除前** | 行在，`archived:false`，目录在 | 行在，`archived:false`，目录在 | 两个子目录 |
| **T1 删除后（未重启）** | **行原样不动**，`archived:false`，**目录还在** | 行在且 `archived:true`，**目录已删** | 只剩一个 |
| **T1.5 应用已退出** | 同 T1 | 同 T1 | 只剩一个 |
| **T2 重启后** | 行还在，`archived:false`，**目录没了** | 行还在，`archived:true`，目录没了 | **整个根目录 ENOENT** |

具体路径与索引字段（sessionId / workspacePath / runtimeIdentity / unbound / archived）
逐时点记在 [f2b-report.json](f2b-report.json) 里。截图：
[删除后](f2b-after-delete.png)、[重启后](f2b-after-restart.png)。

## 四条结论

1. **「关闭」什么都不删。** 索引行和目录在 T1 原样不动，只是行从侧栏消失了。
   现场那句「删了之后就不见了」如果指的是这个入口，那么**界面消失 ≠ 文件被删**——
   这正是取证要求特意写明不许推断的那一条，现在有了两侧读数支撑。
2. **「归档」当场删目录。** `release()` 在归档这一步同步跑掉，T1 就能看到目录没了、
   索引行还在并置了 `archived:true`。索引与磁盘在这条路上是一致的。
3. **重启会把所有临时目录连锅端，与用哪个入口无关。** 只「关闭」过的那条，
   目录在 T1/T1.5 都还在，重启后消失；它的索引行仍是 `archived:false`。
   所以**重启之后必然存在「索引行在、`workspacePath` 指向一个已不存在的目录」的状态**。
   这是设计（U05-a：重开时按 resume 路径重建一个空目录），不是索引损坏，
   但它和「索引行仍在但不可见」的现场描述长得很像，排查时要先分清。
4. **退出时的清理这一轮没生效。** T1.5（应用已退出、尚未重启）目录仍在，是**启动**那次
   `wipeAll()` 才清掉的。注意本轮停应用用的是 `pkill`（`stopDevApp` 的做法），
   进程收到的是信号而不是从界面正常退出，所以这**只能**证明「被杀掉时退出清理不跑」，
   不能证明正常退出也不跑。两者的差别对用户可见（正常退出的人和崩溃的人，
   下次启动前磁盘上残留的东西不一样），值得单独验一次。

## 探针自己踩的两个坑，都会让人读出假缺陷

- **归档是要确认的。** 行上那个按钮只把确认框打开（`requestArchive` → AlertDialog）。
  第一版点完就走，索引当然没变，读出来就是「点了归档但 `archived` 还是 false」——
  一个并不存在的缺陷。现在探针会点确认框里的「归档」。
- **侧栏可见性不能用整屏 `innerText` 判断。** 会话列表会滚动、分组会折叠，
  文字不在 `innerText` 里不等于这一行不存在，而 F2-b 要分的恰恰是「行在不在」和
  「看得见看不见」。改成从 store 读会话列表。

## 顺带记一条：临时会话的索引 `title` 是空的

本轮建的四条临时会话，索引行里 `title` 全是 `""`，而更早的临时会话（如
`写一个test123.txt文件`）是有标题的。本轮没有深究是哪一步没写进去——它不属于 F2-b 的
取证范围，但侧栏上一条没有标题的对话对用户是有影响的，单独记在这里备查。

## 还没做的

- **第三个入口（临时行的「删除」按钮）未测。** 它走的是 `temp:workspace:*` 那条确认+删除链，
  而那条链按设计只接受临时基目录的**直接子目录**；scratch 目录特意嵌在
  `unbound-sessions/` 下一层，就是为了让这两个功能删不到对方的目录。这条边界值得单独验。
- **正常退出（而非被 kill）时的退出清理未测**，理由见结论 4。
- **未打包、未在加密 Windows 上回归。** 按用户 2026-09-11 的规矩并入最后一次上机。
