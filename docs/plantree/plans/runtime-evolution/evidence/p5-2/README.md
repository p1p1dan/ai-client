## P5-2-0 的两条实测结论改变了实现方式

调研阶段只能确认参考依赖的宿主行为「名字存在」，这批真跑了一遍。十条探针全过，其中两条推翻了原本的假设：

**一、取消不是当场生效的。** 工具执行中 `agent.abort()`，工具的 signal 确实收到，
但循环不会当场结束——pi 记下 tool result，又发一次 provider 请求，那次回来时
`stopReason` 才是 `aborted`。工具在 abort 时抛异常还是正常返回，行为完全一样。

后果有两个：`TaskStop` 必须等真实收敛才能报「已停止」（否则那次多出来的请求还在飞）；
被停掉的子任务**不是零成本**。

**二、`terminate` 要整批一致才生效。** 0.84.4 的类型注释写明「every finalized tool
result in the batch」。所以子代理的 `maxTurns` 必须**逐个调用**求值——批次层面判一次，
两调用批次里的上限根本不会生效。

## 写测试时抓到的两个真缺陷

都不是测试写错，是实现漏了，且两个都**静默**。

**用户 Stop 后 run() 提前结束。** 子代理还在收敛时 `run()` 就 resolve 了，
而它就是 worker 认的回合边界——等于释放槽位、发 idle，然后子代理还在烧 token。
修法是 `drain()`：`abortAll()` 只是「请你停」，drain 停完还要等到真停。
这样「回合结束了」才等于「没有东西还在烧」。

**子任务在父代理空闲前跑完，报告直接丢了。** 交回逻辑拿「还在跑的」当「还没汇报的」用，
可那时它已经不在运行集里。契约 §3 本来就要求「稳定交付标识」，之前没做。
补了 `deliveredAt`：自动交回、`TaskWait` 读到的已结算项、`TaskStop` 停掉并已汇报的项
都打标，`TaskList` 不打（心跳不是报告）。漏报和重复整合两头都堵上。

## P5-2-4 的两条设计选择

**隔离靠条目类型，不靠过滤器。** 子代理的消息写成 `custom` 条目，而
`buildSessionContext` 只把 `message` 条目变成模型上下文——所以「子代理
永远不进父上下文」是**条目类型本身的性质**，不是一条要靠人记得加的过滤。
后者撑不过一次重构。

**事件通道不是记录。** `subagent.activity` 是有上限的实时摘要；终态、
usage 和完整报告都从 JSONL 记录里来。契约明写「不允许阻断终态、usage
或完整报告」，两条路分开就是为此。

顺带把状态枚举从四值扩到六值（加 `stopped`/`truncated`）。不扩的话渲染层
reducer 的四值白名单会把它们**直接丢弃**——比「用 failed 吞掉」还糟。

## P5-2-6 逐条比对抓到的四处不一致

契约禁止拿「我们已有 subagent 面板」跳过这一节，逐条走完确实值回票价。
面板本身没问题，问题在原生后端喂给它的东西。两处是静默的：

**委派记录漏到了父会话时间线上。** `aiclient.subagent` 不在「不上线」名单里，
于是每条子代理消息都发成 `custom.entry`，而渲染层把 `custom.entry` 变成父会话里的
一条系统消息——子代理的整份 transcript 以裸 JSON 出现在用户面前，也出现在父对话里。
SA14 的「条目类型隔离」本该挡住这件事，挡住的只是模型上下文那一半。

**报告在面板里被丢掉了。** T-34 时代 Agent 行的输出就是子代理最后一条文本，
所以面板按位置丢掉最后一条 text 以免重复显示。原生 `Task` 返回的是 ack，
报告走 `TaskWait` 或无气泡的内部交回——自动交回路径上，那条被丢掉的文本
就是用户唯一能看到的报告。「报告一次」成了「报告零次」。

另外两处是缺失而非错误：**思考从来没被投影过**（lane 一直有 thinking 行，没人填），
**工具行没有参数**（每行只显示动词，不显示文件名）。
