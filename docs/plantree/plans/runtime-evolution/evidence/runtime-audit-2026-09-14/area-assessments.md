## AREA core-host — P0 骨架 + host 层  nodes=['P0-1', 'P0-2', 'P0-3', 'P0-6', 'P1-0', 'P1-8', 'P4-2']
SUMMARY: 这个区域（P0 骨架 + host 出口层）的工程质量在本仓属于上游水准：contracts.ts 把 P0~P5 的服务形状一次性钉死并附上「为什么这么定」的说明；host/io.ts 与 host/exec.ts 几乎逐条对得上 p1-0-host-contracts.md 的契约文字（分块读、maxBytes+1 溢出判定、TSD 单次回落、双流合计预算、timeout/abort/dispose 共用一条 stop 路径、POSIX 进程组与 Windows 进程树分治、依赖方向 runtimeHostIo→runtimeExec）；bootstrap 的构造顺序与失败清理是反向对称的，不会返回半活 runtime。D11「按进程身份而非语言推断载体」这条也是真的按进程身份做的：worker 入口用「有没有 parentPort」判定，Main 侧只在 app.isPackaged && win32 且随包 node.exe 存在时才 spawn 它（否则直接抛错，不回落 PATH 里的 node），workerHost 在 electron-utility 下坚决不把 Electron 自己的 execPath 当 TSD helper。

问题集中在三类。第一类是「后加的路径没跟上先有的成熟度」：P5-3 给 exec 出口加的长驻子进程（spawn/kill/killTree）在清理可见性、Windows 重入保护、监听器回收、并发释放这四点上都比同文件里的 runPipe 弱一截，而这条路径在 Windows 上从未跑过。第二类是「证据与状态之间的时间差被版本戳掩盖」：RUNTIME_CONFIG_VERSION 冻结在 runtime_p3_complete_v1 已经跨了五批行为变更，导致 94 个提交前的 P1-8 现场 stamp 与今天的输出逐字段相同，同时也让 D9 的命中率基线失去分组依据。第三类是释放期的错误屏蔽：dispose 里 trace flush 的黏性失败会永久吞掉 exec 的清理失败，而契约第 5 节恰好点名这一条不能吞。

安全面上没有发现路径穿越或命令注入（command 强制绝对路径或裸名、args 以 argv 传递不拼 shell、helper 路径不进脚本文本、childEnv 是显式快照不隐式继承），trace 的 version_stamp 里确实没有 key 和 baseUrl；唯一的泄漏面是失败分支把 pi-ai 未脱敏的 provider 错误正文原样写进 runs.jsonl —— 而仓库里已经有一个现成的脱敏函数没被用上。P4-2 的开关删除做得干净，残留只剩注释与一份仍在指导最后一次上机的过期现场清单。
STRENGTHS: 契约先行做到位：contracts.ts 用 473 行把 P0~P5 全部服务形状、Cordis Context 扩展、错误模型、host/exec 类型一次定完，且每个设计选择都写了「为什么不是另一种」，P1/P2/P3 并行开发的前提是真的存在的 | host/io.ts 的读取语义逐条落实契约：先按 maxBytes+1 分块读再判溢出（不是整文件入内存后截断）、offset 超 EOF 返回空且不标 truncated、无论 offset 是否为 0 都先探 TSD 头、探测与目标窗口共用同一个文件句柄并在 finally 关闭 | TSD 回落的纪律严格：只允许一次、走固定 helper、路径以独立 argv 传（测试专门用 `a $literal ; file` 这种文件名验证）、helper 自己再验一次读到的头仍是 TSD 就失败、不换别的 Node 重试 | exec 的 runPipe 把「取消、超时、输出超限、dispose」收敛到同一个 stop() 入口，并区分 escalation（SIGTERM→SIGKILL）与 cleanupDeadline（宽限用尽报 exec_cleanup_failed 并附部分结果），正常退出后仍对进程组补一刀 SIGKILL 清后代 | runner 载体那个真缺陷修得对且有测试钉住：leader 是 runner 而非命令本身，命令自己退出不触发 leader 的 close，于是改用独立 IPC 通道回报退出——测试注释写明了「这是怎么被发现的」 | D11 载体判定确实按进程身份：worker 入口按 parentPort 有无判 carrier，Main 只在 packaged+win32+随包 node.exe 存在时才 spawn（缺失直接抛错，不回落 PATH），workerHost 在 electron-utility 下拒绝把 Electron execPath 当 TSD helper，workerCarrier.test.ts 把这三条都钉住了 | hostBoundary.test.ts 用源码扫描强制 fs/child_process/node-pty 与 process.send/parentPort/chdir 只能出现在 host 层，是 D11「不得逐个工具打补丁」的机械保障 | commandEnvironment 正确处理了 Windows 的 Path/PATH 大小写合并与 undefined 删键，且有测试断言不污染父进程环境 | trace 把持久化失败与模型结果分开：run 仍报成功，persistence_error 单列，flush 另抛——hostBoundary.test.ts 用「把 runs.jsonl 建成目录」这种真实失败验证 | 版本戳读 git 时显式处理了 linked worktree（.git 是文件 + commondir），这正是本仓开发形态，注释还说明了不用 git rev-parse 的理由
WEAKNESSES: P5-3 新增的长驻子进程路径成熟度明显低于同文件的 runPipe：清理宽限用尽假报「已退出」、Windows killTree 无重入保护且 taskkill 失败不可见、abort 监听器不摘、spawn 与 shutdown 并发可漏回收 | RUNTIME_CONFIG_VERSION 冻结在 runtime_p3_complete_v1 已跨五批行为变更，使 §15 版本戳丧失分代能力，并直接削弱了 P1-8 现场证据与 D9 基线的可比性 | dispose 的错误汇总有屏蔽：trace flush 的黏性失败会让 exec 清理失败的检查永不执行，恰好撞上契约「清理失败必须可见，不能吞掉挂住的子进程」 | TSD helper 的 exec 预算把 stderr 与 stdout 算进同一个 maxOutputBytes，只给 stderr 留 4096 字节，configured Node 的告警噪声足以把一个可读文件判成 io_tsd_unreadable——而这正是唯一未实测的加密机链路 | 失败分支的 provider 错误正文未脱敏未截断就进 trace 和 run 结果，同仓已有 redactSensitiveErrorText 却只用在重试记账那一条路上 | DEFERRED_SERVICES 的 A3 机制已经失灵：唯一一条声明指向一个早已实现的服务（还差一个字母），配套门禁用硬编码子集永远判不出重叠 | HostIo 的错误形态不统一：非绝对路径同步 throw 而非拒绝 Promise，readDirectory 的校验与 disposed 判断因 async generator 而惰性，且不进 pending 所以 shutdown 不等它 | bootstrap 默认 host 传空 env，任何不显式给 host 又启用 tools 的调用方，其子进程只剩一个 PATH（无 HOME/TMPDIR/SystemRoot） | D1 点名的 Cordis 能力（响应式属性传播、Fork/Isolate 隔离、热插拔）一项未落地，插件间没有任何机械隔离，全靠人遵守 contracts.ts | 文档与状态不同步：evidence/p1/README.md 仍停在 2026-09-08 说 Windows 未实测，而任务树写五态已通过；P4-6 仅存的上机清单仍要求设置已删除的 AICLIENT_RUNTIME_BACKEND

问题集中在两类：一是错误路径没有护栏——Task 在拿到并发槽位之后、把控制权交给 SubagentRun 之前有一段无保护区间，任何抛出都会留下一条永不结算的 running 记录，而父 run、用户 Stop、会话 dispose 三条出口全都在等这条记录的 completion，结果是整个会话被永久卡住，连关都关不掉；二是「报告不能漏」这条被反复强调的不变量在三个边角上仍会漏（TaskStop 覆盖已完成项、prune 不看未交付标记、打标先于交付）。另外有一条明确的验收标准被实现违反：自动交回的内部报告是以真实 user 消息形态进系统的，因此会在聊天里冒出一条用户从没打过的气泡，并作为最后一条用户消息落盘——契约和任务矩阵两处都明文禁止这件事。

测试覆盖在「机制」层很好，在「竞态与错误路径」层偏薄：没有任何假时钟用例（而 signoff 声称有）、没有跨会话取消用例、没有裁剪后重读用例、委派工具的权限包装层没有端到端用例。
STRENGTHS: registry 被从编排里拆出来单独成模块，并发闸门/回收/等待谓词可以脱离 provider、session、host 直接驱动，这正是竞态类缺陷唯一可回归的写法；10 并发用轻量闸门验证而不是真起十个子代理，也符合低资源开发机的约束 | admit() 全程同步（running 计数、Promise 句柄登记、records.set 之间没有 await），因此 11 个并行 Task 的准入判定不存在竞态；失败请求不登记任何东西，也就不会占住它没拿到的名额 | drain() 与 abortAll() 的区分抓住了 P5-2-0 探针的核心结论——abort 只是「请你停」，pi 还要多发一次 provider 请求才收敛，所以 run promise 必须等到真停；TaskStop 同样 await 真实 completion 而不是发完 abort 就报「已停止」 | 子代理事件不外逃的边界画得很准：turn_end/agent_end/agent_start 留在 SubagentRun 内部，父 projector 不会被子代理的终态结束 run；「does not end the parent run on a delegate finishing」用 idle 事件计数把它钉住了 | maxTurns 逐个工具调用求值，而不是每批判一次——这是 P5-2-0 探针实测 0.84.4「terminate 要整批一致才生效」之后的正确适配，而且探针用例本身留在了回归套件里 | 流内失败的恢复走「弹掉失败的 assistant 消息再 continue()」而不是重启子代理，测试用 toolStarts===1 明确断言已执行的工具没有被重放——对 fixer 这种会写文件的角色，这条断言是有实际价值的 | 隔离用条目类型（custom）而非过滤器，配合 buildSessionContext 只折 message 条目，使「子代理永远不进父模型上下文」成为数据形状的性质而不是一条要靠人记得加的规则
