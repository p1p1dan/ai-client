# 跨区域接缝审查与完整性批评（原文）

Role: evidence（source material）；来源：2026-09-14 只读审计补跑（额度恢复后）。接缝审查 7 条发现（1 high、5 low 确认、1 被推翻）；批评者给出置信度、20 条覆盖缺口与 18 条未经执行验证的声明。

## CROSS REVIEW
SUMMARY: 这次审的是 13 个区域之间的缝，不是区域内部。总体判断：接缝的「机械正确性」比我预期的好——H/20 双格式头在 codec / store / TUI 守卫 / pi CLI 真实源码四处的字段名和链条形状逐条对得上；取消信号从 worker.stop 一路传到 provider 退避 sleep、子代理 Agent、审批卡 signal，每一跳都真的挂上了；子代理转录与父模型上下文的隔离不是靠过滤器而是靠条目类型，我顺着 pi-agent-core 的 buildSessionContext 源码验证过确实成立；Main 侧的事件转发有 sessionId 归属闸。

真正的问题集中在一类模式上，而且这一类只有跨区才看得见：**一侧声明了语义、另一侧没接线，中间那段注释还在替它背书**。子代理的「继承父回合模型」写在注释里、实现是目录第一条；「继承父思考档位」有字段有 JSDoc、全仓没有生产者；「声明 auto 也不能越出工作区」写在权限内核的 JSDoc 里、evaluate 的分支顺序恰好相反；「per-call 隔离所以两个子代理永不串档」建立在 provider 的 toolCallId 全局唯一上，而 pi-ai 的 Google 适配器会合成可能撞车的 id；模型目录的 dropped 诊断算出来了，唯一的读者在唯一需要它的失败路径之前就抛错了。这五条的共同点是：单区域审计员读自己那半边时，注释和实现是自洽的——分歧只在另一半。

另外 P6 退役的清扫在「跨 Main / RPC / runtime 三层的字段」这一维还有残留（leafCheckpoint），区域审计的视野都只到自己那一层。
WEAKNESSES: 「一侧声明、另一侧没接线」是本次接缝审计最主要的缺陷形态：子代理模型、子代理思考档位、leafCheckpoint、dropped 诊断四处都是同一个形状——中间那段注释仍在描述一条没接通的线，单读任一侧都看不出来 | 权限内核的两条注释给出了实现不支持的保证：gearFor 说子代理 auto 不能越出工作区（实际能），scopeDelegateTools 说两个子代理永不串档（实际取决于 provider 的 id 唯一性）。这类注释比没有注释更危险，因为它会让下一个人跳过核对 | per-call 权限隔离与审批路由共用 provider 给的 toolCallId 作为进程级键（scopedGears / permissionId / toolMessages 三处），没有任何一层做过命名空间化 | 模型目录的诊断只有一个出口且在最需要它的失败路径之后：目录全空时用户拿到的是一句「catalog is empty」，算好的 id:reason 全部丢弃 | P6 退役的清扫按「哪些文件跑 legacy」画的线，跨 Main→RPC→runtime 三层的载荷字段（leafCheckpoint）没进这条线；这类残留区域审计天然看不见
  NODE subagent-core: complete-with-gaps — 编排核心本身（并发闸、结算、报告不漏、事件不外泄）站得住，但「子代理继承父会话设置」这条跨区接缝是断的：模型回落到目录第一条而不是父回合的模型（cross-01），思考档位字段声明了语义却没有生产者（cross-02）。两处都只在 subagent 内部看不出来——要同时读 agent-loop 的模型解析和 nativeWorkerRuntime 的 bootstrap 组装才暴露。per-call 权限档的隔离键直接用 provider 的 toolCallId（cross-04），也是跨 provider 适配器才看得见的假设。
  NODE permissions: complete-with-gaps — judgement 的顺序纪律（deny 先于 gear）确实落在代码结构上，子代理 per-call scope 不动全局 gear 这个设计是对的。但两条跨区保证没兑现：gearFor 的 JSDoc 明文保证「子代理声明 auto 也不能越出工作区」，而 evaluate 在 gear==='auto' 处就 return allow，排在工作区包含性判定之前（cross-03）；allow-session 授权的 grantKey 不含委派归属，卡片上的归属信息与授权的实际作用域不一致（cross-05）。
  NODE loop-model: complete-with-gaps — 重试层与 agent loop 的取消传导逐层核对下来是通的（agent.abort 抖到 activeRun 的 controller，工具 signal、审批 signal、退避 sleep 都挂在上面；子代理的 delayWithAbort 同样可取消）。缺口在诊断出口：模型目录的 dropped 只有 run_start 注记一个读者，而目录全空这唯一需要它的场景恰好在 trace.begin 之前抛错（cross-06）。
  NODE worker-runtime: complete-with-gaps — bootstrap/reload/dispose 的主干与 Main 的契约对得上，permissionPrompt / questionPrompt / previewPrompt 三条 drain 路径在 dispose 时都走到了。缺的是 P6 退役后的清扫：leafCheckpoint 仍在载荷里、仍参与幂等比较，而唯一剩下的引擎不读它（cross-07）。
  NODE session: complete-with-gaps — 逐条核过 H/20 的四方一致性：bookkeeping 行的 parentId 链、lane/fact 行对 CLI 的可见形状、firstKeptEntryId 与 pi CLI session-manager.js:217 读的字段名、resume 就地升级与写入锁的先后（锁先拿、tmp+rename 在锁内、失败路径 unlink 锁）——这些都对得上，没有新缺口。TUI 入口守卫改成「只拦未升级的 v4」与 store 的升级时机也是自洽的。已确认的 seq 陈旧与压缩锚点两条仍是本接缝最重的问题，不重复。
  NODE cutover: complete-with-gaps — 「删掉跑 legacy 的代码」这一层做干净了；没做的是「因为 legacy 走了而失去消费者的那一层」，这一点已被区域审计覆盖。跨区新增的一条是 leafCheckpoint（cross-07）——它不在 agent-host 里，而在 Main 持久化 → RPC 校验 → runtime 三者之间，单看任一侧都像还在用。
  NODE rpc-projector: complete — 跨区角度核对了两件事：Main 的 handleWorkerEvent 有 `event.sessionId !== entry.logicalSessionId` 的归属闸，子代理记录走的是 INTERNAL_CUSTOM_ENTRIES（appendEntry 不发 custom.entry），buildSessionContext 对 custom 条目在无 entryProjectors 时确实产出空数组——「隔离靠条目类型」这条经第三方库源码验证成立。子代理终态词汇的两套拼写（事件 cancelled / 历史 aborted+timed_out）在渲染层的 historyStatus 里有完整映射，不构成缺口。

### [cross-01] HIGH bug confirmed | subagent-core | src/runtime/plugins/subagent/index.ts:412 | 子代理不继承父回合的模型，而是落到目录第一条
DESC: `SubagentPlugin.resolveModel` 的第三档注释写的是「Task.model > definition pin > parent」，但实现用的是 `adapter.defaultRef()`——`ModelAdapterPlugin.defaultRef()` 返回的是 `this.order[0]`，也就是目录里第一个 provider 的第一个模型，与本次 run 用的模型没有任何关系。父回合的模型在 `AgentLoopPlugin.execute` 里是 `request.model ?? restoredRef ?? adapter.defaultRef()`（request.model 来自 GUI 模型选择器，restoredRef 来自会话里最后一条 model_change / assistant 消息），这条信息从来没有传给 subagent 插件：`bindRun()` 只带 sessionId 和 runId。四个内置子代理（explorer / code-reviewer / test-runner / fixer）的 frontmatter 都没有 `model`，所以这条回落是默认路径而不是边角。
SCENARIO: 用户目录里第一个 provider 是便宜的 gateway 小模型，用户在 GUI 里把会话切到 Claude Sonnet 5 并让它委派 code-reviewer。父回合用 Sonnet，子代理静默跑在目录第一条小模型上；委派面板显示的 `resolvedModel` 也是那一条，但没有任何地方提示「这不是你选的模型」。反向同理：目录第一条是贵模型时，每次委派都按贵模型计费。
REFUTER(CONFIRMED,high): 逐行核实成立。`src/runtime/plugins/subagent/index.ts:412` 第三档确实是 `adapter.defaultRef()`，而 `src/runtime/plugins/model-adapter/index.ts:68-70` 的实现就是 `return this.order[0]`；`order` 由 `register()`（同文件 :149-157，注释明写「First writer wins, so catalog order decides defaultRef()」）按 `parsePiCatalog` 遍历 `models.json` 的 providers 顺序 push，与本次回合用的模型无关。父侧解析在 `src/runtime/plugins/agent-loop/index.ts:114`（`request.model ?? restoredRef ?? adapter.defaultRef()`），但传给子代理插件的只有 `bindRun({ sessionId, runId })`（agent-loop/index.ts:173，接口定义在 subagent/index.ts:161-165 的 `SubagentRunContext`，只有 sessionId/runId 两个字段）——父回合解析出的 ref 没有任何通道进入 subagent 插件。四份内置定义（src/shared/subagentBuiltins.ts:32-99）的 frontmatter 只有 name/description/tools/maxTurns，没有 model，所以这是默认路径。另外这不是「注释理想化」而是契约违反：docs/plantree/plans/runtime-evolution/topics/p5-2-subagent-contracts.md:23 明写「Task.model > definition.model > parent model；未固定才继承父模型」。判 high：默认路径静默换模型，能力与计费都跟着变，界面上的 resolvedModel 只会复述那条错的。
WAIVER(no): docs/plantree/plans/runtime-evolution/topics/p5-2-subagent-contracts.md 第23行「Task.model > definition.model > parent model；未固定才继承父模型」；docs/plantree/plans/runtime-evolution/evidence/p5-2/signoff.md SA12行「Task override > pin > parent；不可用即失败并列出可选项，绝不回落」 — 文档两处都明确承诺子代理模型解析第三档是父回合模型，且 signoff 表把这条标记为已测试通过（绝不回落）。这与代码实际回落到 adapter.defaultRef()（目录第一条）直接矛盾——不是文档认下的取舍，而是文档声称已实现、实测却不成立的缺陷，没有任何 waiver 条目覆盖这个具体差距。

### [cross-03] LOW security confirmed | permissions | src/runtime/plugins/permissions/index.ts:211 | 子代理声明 permission: auto 可以越过工作区边界，而 gearFor 的注释明文保证不会
DESC: `gearFor` 的 JSDoc 写得很具体：「A scope can only change which of ask / accept-edits / auto applies. Every deny — policy, path, scope, plan mode — is decided BEFORE the gear is consulted in `evaluate`, so a delegate declaring `auto` still cannot cross a deny rule, **reach outside the workspace**, widen its tool set…」。但 `evaluate` 里 `if (gear === 'auto') return 'allow';`（第 250 行）排在 `!containsPath(this.config.cwd, request.path)`（第 263 行）和 `request.unresolvedPaths`（第 260 行）之前。deny 三类确实在 gear 之前，「工作区外」不是。`permission: auto` 是 `parseSubagentDefinition` 接受的合法取值（src/shared/subagentDefinition.ts:365-374），而 `scopeDelegateTools` 把它放进 per-call scope，`gearFor` 让该次调用在 auto 下解析。于是一个会话档位为 ask（最保守）的父会话，只要委派给一个声明了 auto 的子代理，就能在无任何审批卡的情况下往工作区外写文件。
SCENARIO: 用户在 `<agentDir>/subagents/deploy.md` 里写 `permission: auto`（照 frontmatter 文档写的），会话档位保持「每次询问」。模型调用 Task 委派给 deploy，该子代理执行 `write /home/user/.ssh/config`（不在 deny 名单里的工作区外路径）——evaluate 在 gear==='auto' 处直接 allow，既没有审批卡也没有工作区外提示；同样的写入由父代理发起时会弹卡。
REFUTER(CONFIRMED,low): 代码次序确实如报告所述：`evaluate` 在 `src/runtime/plugins/permissions/index.ts:249-250` 取 gear 并对 auto 直接 return 'allow'，而工作区包含性判定在 :260-268，policy 的 external_directory 规则只在 :227-231 参与 deny 计算、其 'ask' 结果要到 :267-270 才被消费——都排在 auto 之后。scopes 在 GUI 路径下为空（nativeWorkerRuntime 未传 `permissions.scopes`，bootstrap.ts:222-233 只转发 options 里给的），所以没有额外兜底。`permission: auto` 确是合法 frontmatter 取值（src/shared/subagentDefinition.ts:364-375），经 `scopeDelegateTools`（subagent/index.ts:620-640）进入 per-call scope。所以 gearFor 的 JSDoc（:202-213）里「reach outside the workspace」那句与实现不符，这点成立。但报告给的具体场景是错的：`/home/user/.ssh/config` 命中默认策略的 `'~/.ssh/*': 'deny'`（src/agent-host/permissionPolicy.mjs:61），而 `pathPolicy` 的 deny 在 :234-236 判定，排在 auto 之前，会被拦下；真正能越界的是 .ssh/.env/*.pem 之外的普通工作区外路径（如 /tmp 或隔壁仓库）。另外契约文档本身只承诺「不能扩展工具白名单、越过 deny 或把父 plan 改成 agent」（docs/plantree/plans/runtime-evolution/topics/p5-2-subagent-contracts.md:53），并未承诺工作区边界，而 auto 档本身就是会话级也会放行工作区外写入的同一行代码。故降为 low：实质是注释多给了一条代码没有兑现的保证，且触发前提是用户自己在定义里写下 auto。
WAIVER(no): 无（gearFor 的 JSDoc 本身承诺「reach outside the workspace」不可能发生，但无任何 P5-2/permissions 相关文档段落把这条具体越界路径列为已知限制或推迟项） — 读取 src/runtime/plugins/permissions/index.ts 源码确认：evaluate() 在第250行 gear==='auto' 时直接 return 'allow'，早于第263行的 containsPath(cwd, path) 工作区边界检查；而代码注释明确保证 auto 档「reach outside the workspace」不会发生。这是代码自身注释与实现的矛盾，文档层面（SA10「显式 auto 也跨不过 deny」）讲的是 deny 规则而非工作区边界这条独立检查，没有条目豁免这个具体的越界场景。

### [cross-04] LOW race refuted | subagent-core | src/runtime/plugins/permissions/index.ts:190 | per-call 权限档以 provider 给的 toolCallId 为全局键，并发子代理可能撞键
DESC: `scopeToolCall(toolCallId, scope)` 把 delegate 的档位和身份写进一张进程内的 `scopedGears` Map，键是工具调用 id；`scopeDelegateTools` 的注释断言「Keyed by tool call id and torn down in a `finally`, so two delegates with different gears running at the same time never cross over」。这条断言建立在「toolCallId 全进程唯一」之上，而 toolCallId 是 provider 给的，父 Agent 与每个子代理 Agent 各自独立向 provider 取。pi-ai 的 Google 适配器在 provider 不给 id（Gemini 的 functionCall 常常不给）时自己合成 `${函数名}_${Date.now()}_${本流计数器}`，计数器是每条流各自从 0 起。两个并行 Task 启动的子代理，同一毫秒内解析出各自第一次同名工具调用时，会得到完全相同的 id。同一个 id 还同时是 `permissionPrompt` 的 `permissionId` 和 projector 的 `toolMessages` 键。
SCENARIO: 父模型在一条消息里发两个 Task，分别委派给两个 permission 不同的子代理（一个 inherit、一个 auto），模型是 Gemini。两个子代理几乎同时开始并各自第一次调用 read，pi-ai 给出同一个 `read_<ms>_1`。后注册的 scope 覆盖先注册的：先注册那个子代理的调用改按另一个的 gear 解析、审批卡上署另一个子代理的名字；先完成那个的 `release()` 又把仍在跑的那个的 scope 删掉，它后续的调用退回会话档位且卡片不再显示委派归属。同一 id 还会让两张审批卡挤在 permissionPrompt 的同一个 pending 槽上。
