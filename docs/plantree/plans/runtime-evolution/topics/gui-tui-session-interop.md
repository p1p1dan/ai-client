# GUI / TUI 会话互通

Role: implementation-plan。日期：2026-09-10。依据：用户 2026-09-10 决定「即使工作在我们的目录，会话也得保持 GUI 和 TUI 可以互通」，推翻同日早先的 TUI-1 方案 C。

## 方向变更

2026-09-10 上午定的方案 C 是：native v4 会话不进入旧 Pi TUI，入口给出明确说明。同日下午用户重新考虑后要求恢复互通能力。**方案 C 的入口保护实现保留**（它仍是格式不兼容时的正确兜底），但目标从「拒绝并说明」改为「让它能开」。

这不是与 ARD 冲突，而是**回到 ARD 一侧**：成功标准 6 的验收动作里有「Edit/Write 后 TUI 与编辑器看到的内容一致」，而 native v4 会话根本进不了 TUI，这个动作就无法执行。互通恢复后该验收重新可做。ARD 的 2026-09-10 范围注记需同步改写。

## 可行性已验证

[验证记录](../evidence/gui-tui-session-interop/README.md)：双向读写四轮交替全部通过，用的是双方各自的真实读写器。结论是**一个文件、双格式**，不是两个文件。

用户原本设想的上限是「最多维护两个对话文件」。两个文件是更差的选项而非兜底：两个写入方各写一份，聊完内容分叉且无法合并，用户看到哪份取决于从哪进。单文件双格式只有一份真相。

## 本轮决定

- **单文件双格式**。头一行同时带 `type:"session"` 与 `kind:"header"`；entry 行保持 v4 形状，CLI 会忽略它不认识的字段。
- **容忍而非改写**。读到 CLI 追加的 v3 行时在内存里补齐缺失字段，不回写文件、不重排已有行。会话文件仍是 append-only。
- **互通成为 P6 前置**。P6-1 要把默认切到 native，而 native 正是当前不通的一头；不先解决，切换即等于取消 TUI 能力。
- **并发仍靠锁挡**，不靠格式。`PiTuiExclusiveGuard` 与 `writerLock.ts` 的既有边界不变：TUI 持有会话时 GUI 发送路径必须先释放。

## 执行清单

- [ ] I1：写入端头一行补 `type:"session"`（含 `timestamp` 等 v3 头字段），不改 entry 行形状。
- [ ] I2：解码端补五处容忍——字符串 `timestamp` 转毫秒；缺 `kind`+`seq` 的行按 main lane 的 entry 处理并推导 `seq`、前进 lane 游标；`session_info` 映射为 `fact:'name'`。
- [ ] I3：撤下 TUI 入口对 v4 的主动拒绝（`piTuiSession.ts` 的 `inspectPiTuiSessionSupport`），改为只拒绝真正打不开的形态。
- [ ] I4：复杂形态验证——压缩、分支、工具调用在双向下的表现。
- [ ] I5：真实回合验证——真实 provider 跑一轮，GUI↔TUI 交替，确认时间线渲染正确。

## 验证案例

1. GUI 建会话 → TUI 打开 → 聊两句 → 回 GUI，四条消息顺序与父子链一致；再从 GUI 发一条，TUI 重开仍能看到全部五条。
2. 会话在 TUI 里改名后，GUI 显示同一名字（第 5 处差异）。
3. GUI 侧发生压缩后 TUI 仍可打开；TUI 侧的分支操作 GUI 能正确展示。
4. TUI 持有会话时 GUI 发送被拒绝，提示要求先关闭终端；反之亦然。
5. 旧的纯 v3 会话与纯 v4 会话都仍可打开（不因新增容忍而破坏既有两类文件）。

## 范围外与风险

- 不改 v4 的语义模型，不引入格式转换或双写。
- CLI 升级若改动 v3 写法，本方案的容忍清单需重新验证；[验证记录](../evidence/gui-tui-session-interop/README.md)里已登记这一条。
- 互通打开后，CLI 能写入我们的会话文件，意味着一个我们不控制的写入方进入了这条链路。会话锁是唯一的防线，实现时必须确认 TUI 路径确实持锁。
