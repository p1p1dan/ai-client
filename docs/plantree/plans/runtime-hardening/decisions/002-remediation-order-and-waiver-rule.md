# 决策 002：修补顺序与「文档取舍」的计数规则

日期：2026-09-14。状态：已采纳（顺序与规则来自用户对审计的要求）。

## 修补顺序

安全与数据完整性（批次 A）→ 功能正确性（批次 B）→ 退役清扫与文档回写（批次 C）；补审（批次 D）只读、与 A/B 并行；现场（批次 E）最后一次上机。

理由：A 里每条要么能绕过权限、要么会把用户数据写坏或让进程卡死，且都有反驳者核实过的完整触发路径；B 是错误行为但不丢数据；C 不改变运行行为。开发机能验的先验，现场项攒到一次上机（沿用 D16 与用户 2026-09-11 的规矩）。

## 「文档取舍」的计数规则

用户要求：文档里明确作出取舍的内容，代码没覆盖不算缺陷。审计按此执行，规则如下：

- 算取舍（不计入）：文档明确写「不做」「推迟到 X」「接受此限制」「用户拍板决定」。共 3 条。
- 部分取舍（计入但打折）：文档豁免了「没验证」或相邻能力，没豁免这条具体缺口。共 12 条，roadmap 里照常排任务。
- 不算取舍：「待现场验证」「待复验」只豁免缺现场证据，不豁免代码本身的缺陷；「注释或文档声称已做」是正面承诺，与代码不符时按缺陷计。
- 被反驳者推翻（20 条）与待定（27 条）不进 roadmap；待定里有具体补用例路径的（session-02、session-04/05）挂在对应任务下先补用例。

## 严重级取值

以反驳者判定为准（它比区域审查员多读了调用方与第三方库源码）。两个区域独立报出同一缺陷时取较高者。
