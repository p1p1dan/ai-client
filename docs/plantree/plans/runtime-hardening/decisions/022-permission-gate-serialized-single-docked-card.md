# 决策 022：授权闸串行化，活卡收进输入框上方的浮层单卡

日期：2026-09-18 · 拍板人：用户 · 状态：已决 · 任务：T074（批次 G，已落地）

## 问题

用户直接提出：「如果同时有多个授权卡，居然是顺序输出在页面上显示全部授权卡片，然后点击上面的授权后，再去后续的挨个选择？我想的应该是做成一个弹出式卡片，在聊天框上方浮现，一次只显示一个授权任务，按先后顺序依次显示，授权卡左上角可以显示 2/5 来表示有几个需要授权的任务。或者就应该是阻塞的，一个工具调用申请没有批准或处于等待，就应该阻塞，不会进入下一个授权。」

模型一次发起多个工具调用时，每个调用各自过一次权限闸（`PermissionEngine.check()`），于是多张完整授权卡在消息流里纵向平铺。更要命的是每张卡的 120 秒倒计时**同时开跑**：排在后面、用户还没看到的卡可能没轮到就已经超时自动拒绝。

## 候选与取舍

编排者把三条路摆给用户选：

- **候选 A（选定）**：浮层单卡 **+** runtime 串行化，两件一起做。
- **候选 B**：只改 UI 浮层，runtime 照旧并发发起授权请求。
- **候选 C**：只做 runtime 串行化，卡片仍留在消息流原位。

用户选 A。取舍依据：

- 候选 B 治标不治本——排在后面、还没显示出来的授权仍在倒计时，「没轮到就超时自动拒绝」这个真正的缺陷原样保留。
- 候选 C 解决了倒计时问题，但卡片会随输出往上滚走，用户看不见它。
- 候选 A 的代价是「多个工具调用都需要授权时会串行变慢」。用户知情并接受。

用户提的两个方案（「浮层单卡」与「阻塞」）其实不互斥：串行化让队列深度多数时候是 1，浮层负责把那一张摆在用户必然看得见的位置，`N/M` 负责告诉用户后面还排着几个。

## 决定

采用**候选 A**：

- **runtime**：权限引擎加 FIFO 排队锁，任一时刻最多一个请求处于「已发卡、等用户回答」。锁在 `notify` 与 `setTimeout` 之前获取，所以排队中的请求既不发 `permission.requested`，也不启动超时计时器——它的 120 秒从被发卡那一刻才开始算。
- **渲染层**：活卡搬到 Composer 正上方的浮层（非 Dialog、无遮罩，输入框始终可用），只画队列里最早一条，左上角显示 `queuePosition/queueDepth`。消息流里的内联卡退化为冻结副本。

## 理由

- 把锁放在计时器之前，是「排队中不倒计时」唯一正确的落点；放在 `approve` 内部（`permissionPrompt.ts`）来不及，那时计时器已经起来了。
- 浮层复用 `PendingQuestionDock` 已经验证过的同构形态（在 ScrollArea 之外、从 store 队列取最早一条、按 id 作答），不新发明交互。
- 队列深度必须由 runtime 报上来：串行化之后渲染层的 `pendingPermissions` 里同时只有 1 条，自己数永远只能数出「1/1」。这条已用测试实测否证，不是推断。

## 后果与备注

- `permission.requested` 新增两个**可选**字段 `queuePosition` / `queueDepth`。`queueDepth` 的语义是「此刻闸门已知的总数」而**不是承诺值**：后到的请求会把总数抬高，`1/3` 之后出现 `2/5` 是正确行为。字段注释里写死了这一点，避免渲染层误当定值。
- 队列计数存在 `PendingPermission` 队列记录上，**不写进 `permission_request` block**：它是转瞬即逝的闸门状态，写进 block 会被冻进历史转录，回看旧对话会显示一个毫无意义的「2/5」。
- 进度只在 `queueDepth > 1` 时显示。孤立的一次授权显示「1/1」是噪音；字段缺失时不显示，也不得画出 `undefined/undefined`。抑制规则落在纯函数里而非 `.tsx`，因为本仓 vitest 跑在 node 环境、`.tsx` 里的规则断言不到。
- 自动放行（policy allow/deny）**不进队列**，并行只读工具不会被无谓串行化。
- 子代理与主代理共用同一把锁但不成环：授权在工具执行之前就返回，锁不覆盖工具运行段，且派发子代理的 `task` 工具根本不过闸。
- **`drain()` 的语义随之变窄**：它只能触达已经问过的请求，排队中的看不见。所以单独调 `drain` 的效果是「答掉当前这张，下一张顶上来」，而不是「取消整批」；清空队列必须同时 abort。两个生产调用点（`dispose()` / `reload()`）都已满足，语义写进了文档与用例。若未来有人把 `drain` 当「取消全部」用会踩坑。
- **行为变化**：回合已消失但 block 仍未解决时（`session.failed` / `session.stopped` 清队列但不把 block 标 resolved），内联处不再留一张点不动的「等待中」卡。与提问卡早已采用的取舍一致。
- 红线不变且有专门用例：任何情况下都不能出现「有待批授权但屏幕上一张卡都没有」。用例同屏渲染时间线与浮层，断言**恰好一张**可答卡且它在浮层里。
- 未处理：`queueDepth` 单调性没有做平滑，UI 上会看到分母跳变。这是刻意的（见上，它本来就不是承诺值）。
