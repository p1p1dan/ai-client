# 决策 023：新增第四档权限模式「完全放行」（bypass permissions）

日期：2026-09-18 · 拍板人：用户 · 状态：已决 · 任务：T078（批次 H）

## 问题

T033 现场反馈 #2：权限档设为「全自动」时仍会弹出授权卡。根因是 `PermissionsPlugin` 的放行条件是 `gear === 'auto' && !unresolvedPaths`（`permissions/index.ts:359`）——`unresolvedPaths` 来自 bash 静态分析对无法解析的路径的标记（`$VAR`、`$(...)`、`for` 循环等，`bash-analysis.ts`），这类命令即使处于「全自动」也会被拦下来问用户。这与「全自动」这个名字给用户的预期不一致：用户理解的「全自动」是完全不打断。

## 决定

在现有的手动 / 建议 / 全自动三档之上，新增第四档「完全放行」（bypass permissions）：在全自动的基础上，连 bash 静态分析解析不出的路径也直接放行，不再弹卡。进入该档需要显式二次确认（防止误触），激活期间界面上要持续可见一个提示（防止用户忘记自己开着这一档）。

## 理由

用户当场拍板：「全自动」名不副实，既然叫全自动就不该还在某些情况下弹卡；愿意为更彻底的自动化承担相应的风险，但要求二次确认和持续可见的提示作为安全边界。

## 后果与备注

- 这一档与现有三档的具体交互形态（二次确认的样式、持续可见提示的位置）留给 T078 落地时设计，本决策只定「要不要做」与两条安全边界：进入前二次确认、激活期间持续可见。
- 落地前 `unresolvedPaths` 的判定路径（`permissions/index.ts:359`、`bash-analysis.ts`）保持不变；新档只是在判定结果之上再加一层放行开关，不改判定逻辑本身。
- 这一档不改变 allow-session 的既有语义（见[决策 003](003-allow-session-stays-session-scoped.md)），两者是正交的两个机制。

## 追加注记（T078 落地后，2026-09-18）

- **bypass 档下保留的硬拒绝清单**：`allowedTools` 白名单之外的工具、用户显式 deny 规则、内置路径黑名单（`*.env`、`~/.ssh/*`、`*.pem`、`*.key`、`id_rsa*`、`~/.aws/credentials`）、plan 模式裁剪、deny scope——这些在 bypass 档下依然拦截，不因「完全放行」而失效。bypass 只是在 `unresolvedPaths` 这一层判定结果之上再加一层放行开关，不触碰上述边界。
- **对本决策撰写时前提的更正**：本决策原文默认「全自动」档已经挡住了大部分危险命令，bypass 只是多放行 `unresolvedPaths` 那一小类。落地时发现默认策略 `BASH_RULES = {'*': 'ask'}` 本身**没有**内置的 `rm` 拒绝规则——也就是说 `rm -rf` 这类命令在 bypass 档下会直接执行，不经过任何拦截。这不是 T078 引入的新洞，是默认策略原有的边界，只是「完全放行」第一次让它变得可以被直接触发。是否要为 bypass 档单独加一份最小的破坏性命令黑名单，登记为 [Q022](../open-questions.md)，尚未拍板。

## 追加注记（Q022 拍板，2026-09-18）

- **结论**：完全放行档不加任何破坏性命令黑名单。用户原话：「不要，选择了这个就是把权限完全放开」。
- bypass 档下保留的硬拒绝清单不变，仍是上一条追加注记里列出的那五道防线：`allowedTools` 白名单之外的工具、用户自配的 deny 规则、内置路径黑名单、plan 模式裁剪、deny scope。这些是系统性防线，不是逐条判断「这条命令危不危险」，所以不算违背「完全放开」的字面意思。
- 不再为 bypass 档新增 `rm` 类破坏性命令黑名单。
