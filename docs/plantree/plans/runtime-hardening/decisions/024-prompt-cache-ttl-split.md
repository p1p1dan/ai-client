# 决策 024：prompt cache TTL 主对话 1h / 子代理 5m 分离，暴露为设置项

日期：2026-09-18 · 拍板人：用户 · 状态：已决 · 任务：T077（批次 H）

## 问题

T033 现场反馈 #8（本轮现场最疼的一条，是「正常输出慢」的主因）：对一份真实转录（`contextFX/session-1789701613704-i5jfwqz.jsonl`，跨度 17,759 秒、261 条消息）逐条分析后发现，全程出现 4 次「完全未命中」提示缓存（`cacheRead=0` 且 `cacheWrite>50,000` tokens），全部发生在距上一次请求超过 5 分钟之后：停顿 5.7 分钟 → 首字前 29 秒；停顿 5.7 分钟 → 51 秒；停顿 6.9 分钟 → 11 秒；停顿 17.8 分钟 → 50 秒。对照缓存命中时 98 个样本的首字前中位数只有 6.8 秒。已排除的替代解释：上下文体积（体积更大的模型分桶反而首字前快 4.7 秒）、默认思考强度（方向相反）、走了额外网络路径（命令行工具与本应用同一网络环境）。详细数据见 [t033-field-day/07-findings.md](../topics/t033-field-day/07-findings.md)「性能深挖」节。

## 决定

把 prompt cache 的过期时间（TTL）拆成两档：主对话 1 小时、子代理 5 分钟，并把这两个值暴露成设置项，对齐 Claude Code 客户端已有的 `promptCacheTtl` / `subagentPromptCacheTtl` 概念。

## 理由

数据直接证明：超过 5 分钟没有新请求，缓存就会过期，下一次请求要把整段对话重新写入缓存，首字前等待时间从 6.8 秒的正常水平涨到 29～51 秒。这是本轮现场「输出变慢」反馈的主因，且是可以通过调整缓存有效期解决的已知机制（Claude 官方 prompt cache 本身支持更长的 TTL 档位）。

## 后果与备注

- **待验证**：把主对话 TTL 改成 1 小时后，实际收益取决于本应用当前使用的中转 / 网关是否把 `cache_control` 的 `ttl: '1h'` 参数原样透传给上游——如果中转在这一层被吞掉或改写，改了设置也不会生效。这一点必须在 T077 落地后用真实请求的 `cacheWrite` 触发情况分桶验证，已登记为 [open-questions.md](../open-questions.md) 的 Q021。
- 1 小时是 Claude 官方 prompt cache 支持的较长 TTL 档位，5 分钟是默认档位；子代理会话通常更短命，用更短的 TTL 更省成本，两档分离而非统一改成 1 小时。
- 本决策只定 TTL 策略与设置项本身，具体如何在 `cache_control` block 里表达两档、如何回落（中转不支持 1h 时怎么办）留给 T077 落地时处理。

## 追加注记（Q024 拍板，2026-09-18）

- **结论**：缓存 TTL 由设置项控制，用户自己设定；默认值维持主对话 1 小时 / 子代理 5 分钟不变。用户原话：「我感觉留个开关在设置里，我自己设置」。
- 现状已有两页各一个开关：主档在 PiModelManagementSettings，子档在 PiSubagentsSettings。
- 不做运行中热切换：改设置只对下一次启动的 runtime 生效，不影响正在跑的会话。
- 一次性工具调用（`nativeUtility`）固定留 5 分钟档，不跟随主档改动。

## 追加注记（性能实测推翻主因判断，2026-09-18 下半场）

- **本决策「问题」「理由」两节里「5 分钟缓存过期是本轮现场『输出变慢』反馈的主因」这一判断被当天更完整的实测推翻**：用真实公司渠道请求做六组对照（我们的 runtime 冷/热缓存、裸调用开/关思考、裸调用带/不带工具定义、用户自己的 Claude CLI），缓存对首字延迟的贡献只值约 **2.3 秒**（冷缓存 28.2s → 全命中 25.9s），量级远小于现场观测到的「首字 6.8s → 29～51s」那个落差；真正的大头是**思考（extended thinking）token 量**——关闭思考后总时长从 30.7s 降到 11.3s（降 64%），首字从 25.0s 降到 6.9s，且三组数据的思考 token 量与耗时完全单调对应。完整数据见 [evidence/batch-h-field-fixes-2026-09-18/perf-2026-09-18.md](../evidence/batch-h-field-fixes-2026-09-18/perf-2026-09-18.md)。
- **本决策本身不撤回**：主对话默认 1 小时依然值得做——省成本（避免短停顿后的重复全量写入）、省这 2.3 秒——只是它不再被当作「解决输出慢」的方案。上面「问题」「理由」两节的原文保留不删，本注记是对其因果判断的更正，不是否定这个决定。
- 与 Q021 的关系：本决策「后果与备注」一节记的「待验证：中转是否透传 `ttl:'1h'`」已用同一批真实请求端到端确认——中转如实透传且上游确实按 1 小时处理，[Q021](../open-questions.md) 已结案。
