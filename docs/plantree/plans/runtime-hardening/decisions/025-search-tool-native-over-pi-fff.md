# 决策 025：搜索工具优先改自有实现，`@ff-labs/pi-fff` 仅作设计参考

日期：2026-09-18 · 拍板人：编排者裁定 · 状态：已决

## 问题

T033 现场反馈 #8 的「工具耗时」细项：模型在需要搜索时习惯直接用 bash 硬跑 `grep -ran`（单次 183 秒）、`find .`（单次 120 秒），而本应用自带的 glob（按路径搜索）工具在 Windows 大目录树下也偏慢（2 次调用平均 50.8 秒）。第三方包 `@ff-labs/pi-fff` 提供按使用频率（frecency）排序、分页游标、感知 git 状态、自动判断用正则还是按字面搜索等能力，在讨论中被提出作为可能的替代方案。

## 决定

搜索类工具的改造优先在本应用现有实现基础上做——补强提示词让模型认得该用 grep/glob 工具而不是 bash 硬跑（见 [T083](../roadmap.md)），并优化 glob 在大目录树下的性能。`@ff-labs/pi-fff` 只作为设计参考，不直接引入依赖；只有在评估后发现「直接整包采用」的替换成本明显低于自己实现时，才改为引入。

## 理由

本应用已有自己的搜索工具实现与 runtime 插件体系，直接引入第三方包会带来额外的依赖维护与集成成本；`pi-fff` 的能力设计思路（frecency 排序、分页游标等）值得借鉴，但当前没有证据表明它比自建实现更省成本。本仓对随包依赖一贯从紧（见 [T025 死代码与死字段清扫](../roadmap.md) 摘除多个无生产者的随包依赖），新引入依赖同样要过这道纪律。

## 后果与备注

- 本决策不新开独立任务，落地体现在 T083（H-7，工具提示词补强 + glob 大目录树性能）以及未来任何触及搜索工具的任务里。
- 若后续评估发现整包采用 `pi-fff` 成本更低，需要重新拍板，不能默默引入依赖。
