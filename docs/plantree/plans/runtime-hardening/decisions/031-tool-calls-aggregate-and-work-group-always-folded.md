## 问题

用户 2026-09-19 直接提出的第三条界面诉求：

> 「过程条目太碎。两段正文之间穿插『思考 / 读取 / 读取 / 运行 / 编辑 / 思考』。要按 zcode 的做法聚合成少数几条，并且默认折叠、不自动展开。」

现状是：一个回合内**连续出现**的工具调用被渲染成一行一条，最多能在两段正文之间平铺六行过程信息；工作组运行中还会自动展开，把过程全部铺在读者眼前。读者从提出问题到读到答案之间，要先趟过一串「读取 / 运行 / 编辑」。

（本条决策的工程执行清单在 [topics/chat-typography-and-process-fold.md](../topics/chat-typography-and-process-fold.md) 的任务 5 / 6，含逐文件的改动点与测试影响面。）

| # | 结论 |
|---|---|
| D3 | 聚合口径：一个回合内**连续出现**的工具调用**不分类型**（读取 / 搜索 / 运行 / 编辑 / 写入）合并成一条 |
| D4 | ~~夹在中间的**思考会打断聚合**，前后各成一条，思考自己单独一行~~ **→ 2026-09-22 推翻，见顶部修订** |

| D7 | 折叠头**保持英文**（`Working 12s · Reading App.tsx` / `Worked for 47s · 9 steps`），沿用 2026-09-19 已定的决策；组内工具行、思考行仍是中文 |

**一处口径统一（施工方知情用）**：用户在「思考是否打断」那一问看到的预览文案是按类型分组的（「读取 2 个文件」），与 D5 选定的「总步数 + 最后动作」不一致。**以 D5 为准**。聚合段内只有 1 个工具调用时不聚合，回落成现在的单行原样（沿用现有「≥2 才聚合」规则）。

**D6 的作用范围只到工作组这一层**，不往下改：组内**单条思考行**在流式中默认展开，这是 T098 同一天刚按用户反馈 #8 做的（原诉求是「思考进行中无法折叠」）。工作组既然始终折叠，组内那一层用户平时也看不到，**保持现状不动**。

## 候选与取舍

- **候选 A（选定）**：两层聚合（item 层跨助手消息缝合同一串工具 + row 层按「思考 / 带授权的 run」切段、段内 ≥2 才聚合成一条），工作组默认折叠、运行中也不展开。
- **候选 B**：只做 row 层聚合，不缝合跨助手消息的相邻工具组。**不够** —— 工具条目是按**助手消息**切块的，同一串连续工具会分散在多个 `toolGroup` 里，同一段废话里仍会看到多条聚合行，用户诉求里的「聚合成少数几条」达不到。
- **候选 C**：保留「运行中自动展开」，只做聚合。**与诉求正相反** —— 用户明确要「默认折叠、不自动展开」。

取舍：选候选 A。B 只解决一半，C 直接违背诉求。

## 决定

采用**候选 A**，并**正式推翻[决策 021](021-turn-work-group-restores-elapsed-and-fold.md) 的「运行中自动展开」那一半**。

### 1. 推翻的是哪一半

决策 021（2026-09-18 由**同一个用户**拍板）选定候选 A 时定下的工作组形态是「**运行中展开**、header 显示『工作中』，结束后 header 变『已工作 57 秒』并自动折叠」。本次推翻的是前半句。

**推翻理由：用户当下诉求。** 与 021 自己推翻 2026-08-29 / 2026-09-10 两条旧裁定时的理由**完全同构**：021 当年推翻旧裁定的依据是「用户是这两条旧裁定的同一个拍板人，本次直接提出了相反诉求」；本次是同一个用户在**次日**对同一处界面提出了相反诉求，适用同一条判据。外部参照（zcode 的做法）也只是参照，与用户当下诉求冲突时以用户诉求为准。

### 2. 保留的是另一半（一条都不能少）

021 除「运行中自动展开」以外的全部结论**继续成立**：

- **结束后折叠**（本次改成「始终折叠」，是加强不是废弃）。
- **头部报时长**：完成的工作组要报告自己的耗时（`formatWorkedForRow` / `deriveTurnStats`），**时长未知时（例如回放的历史回合没有元数据）回落到步数，绝不编造秒数** —— A07 的「never fabricate seconds」红线不受本决策影响。折叠头结束后显示 `Worked for 47s · 9 steps`，正是这条的延续。
- **纯派生、零 `useEffect`**（021 的原文要求）：让「StrictMode 下触发两次」与「重渲染把读者展开的组关掉」在结构上不可达。本次改动**仍然纯派生**，开合判定是 `forcedOpen` / `userOpen` / 默认值 三个入参的纯函数。
- **未应答的授权 / 提问强制展开**：`turnWorkGroupAwaitsUser` 是红线，D6 的「始终折叠」**不覆盖**它，该函数一个字不改。工作组永远折叠之后，它是**唯一**还能自动展开工作组的规则。
- 工作组用原生 `<details>` 而非 `@coss/ui` 的 `Collapsible`（后者的 panel 带 `overflow-hidden`，会创建 containing block 并静默破坏置顶气泡的 `position: sticky`）—— 这条有据偏离继续有效。
- 折叠头的**英文**（D7）也沿用 021 之后 2026-09-19 已定的决策。

### 3. 两条必须保留的例外（对「不分类型聚合」的有意偏离）

1. **带 permission（授权）记录的 run 不进聚合**，而是作为**分隔符**单独成行。理由不是洁癖：工作组这次改成永远折叠，授权记录如果再被埋进聚合行的 detail 里，用户就要**点两次**才看得到一次授权记录。这是对 D3「不分类型聚合」的**有意偏离**，理由写进代码注释。
2. `turnWorkGroupAwaitsUser` 一个字不改（见上）。

### 4. 运行中的聚合不抖（防抖四道）

新文案要求**运行中**也显示聚合行，所以旧规则「遇到 running 就停止聚合」的前缀限制删掉，running 的 run 正常进段。这**偏离了 A07「running 行不给 chevron」的旧规则** —— 该规则同一天已为思考行退役过一次（T098），按同样方式登记偏离。

四道防抖：① key 用首个 run 的 blockId，段增长不换 key；② 段只增不减，N 单调递增、聚合行不会退回单行；③ 唯一一次结构翻转是段内第 1→2 个 run，用户的展开态由既有的 `resolveToolRowOpen` 规则自动承接，不用写新代码；④ 文案只在尾部变化，行首位置不动，视觉上是就地刷新。

### 5. `settled` 从开合判定的入参里删掉，不是留着不用

`turnWorkGroupOpen` 的入参改成 `{ forcedOpen, userOpen }`。`TurnProgressHead` 仍然需要 `settled`（spinner、label、当前动作 clause 都用它），只是不再传给 `turnWorkGroupOpen`。删而不是留，是因为该文件自己的戒律禁止保留「无人消费的导出规则」。

### 6. 头部必须显示「当前在做什么」（这条不是锦上添花）

工作组永远折叠之后，折叠头是整个回合**唯一**的进度证据。如果在工具间隙（正在思考、等授权、两次调用之间）返回 `null`，用户看到的就是一个**只有秒数在跳的裸头 —— 和卡死没有区别**。所以新增纯函数 `deriveTurnCurrentAction`：倒序扫 items、倒序扫 `toolGroup.entries`，取第一个 `status === 'running'` 的 run；**没有 running 的 run 时回落到最后一个已完成的动作**。spinner 也要保留。

## 理由

- 用户是同一个决策的拍板人，次日在同一处提出相反诉求，且给了目标形态的参照实现（zcode）。判据与 021 当年推翻旧裁定完全一致。
- 过程信息在运行中的自动展开，在「工具调用可能跑上好几分钟」的现实下代价变了：021 定这条时工具调用还短；T101 刚落地的「执行中即显示」让运行期变长、过程行变多，展开态摊在屏幕上就成了噪音。诉求 3 里「太碎」正是这个组合的结果。
- 聚合的口径（不分类型、思考打断、总步数 + 最后动作）由用户逐条拍板，不是编排者的取舍。

## 后果与备注

- **授权可见性的回归防线**：带 permission 的 run 作分隔符且独立成行，是本决策最容易翻车的一点（「不分类型聚合」若字面执行到授权行上，叠加「永远折叠」就是「点两次才能看到一次授权」）。测试里要有一条专门钉它。
- **「运行中看起来卡死」的回归防线**：`deriveTurnCurrentAction` 的回落规则必须做，测试要覆盖「无 running 时回落到最后完成的动作」。
- **跨助手消息合并会丢掉流式思考的 block id**：合并后的 toolGroup 只保留第一个 item 的 `messageId`，来自后半段消息的思考取不到流式 block id，「正在思考」的实时追加会**静默失效**（不报错）。解法是给合并产物加 `messageIds` 数组，渲染处遍历取第一个非空。
- 这次会让**一批现有断言从绿变红，且是预期的**（逐条对照表见施工清单的「任务 5 / 6 的测试影响面」一节）。施工方必须能分清「我改红的」和「我改坏的」。
- 语言混排（头部英文、组内中文）是**刻意的**，不是缺陷 —— 依据是 2026-09-19 已定的决策（`messageTimelineWiring.test.ts` 与 `turnProgress.test.ts` 各有一条测试焊死头部英文）。
