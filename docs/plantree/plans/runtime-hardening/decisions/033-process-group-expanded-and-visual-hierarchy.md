## 问题

`1e33b7fe`（2026-09-22，feat: 区分最终回复与中间说明并优化过程摘要）落地后，用户在连续几轮反馈中收敛出一组新诉求，并明确提出「跟 zcode 对齐」。逐条原文：

1. 「有时候我感觉中间输出的内容太多太杂太细碎了。」
2. 「在流式执行过程中，由于我们是不知道那条才是最终输出，所以过程中都在折叠头中显示，确定流式完毕后，输出分割线，把最终输出提出折叠头。」
3. 「与之前不同的就是，按照你说的使用新的缩进间距，而旁白和最终输出可以字体字号相同。」
4. 「工具调用中，有时候指令太长了，没有办法看全。折叠头可以显著一点，有时候内容多了根本找不到折叠头。」
5. 「折叠头默认展开，输出结束了也保持展开状态。」「中文还是英文跟随系统吧。」
6. 「如果折叠头吸顶的话，会不会和思考的吸顶冲突了？」→ 用户自答：「或者思考就不吸顶，展开后思考折叠就搞个显著的背景行？」

其中第 5、6 条与本仓既有决策**直接冲突**，是本决策存在的原因；第 1 条是 overarching 动机。第 2 条的形态（流式期间不判终稿）同时消解了 `1e33b7fe` 遗留的争议点 A/C，见下文 D1。

## 候选与取舍

**关于过程组的判定时机：**

- **候选 A（选定）**：流式期间**不判定**终稿，整轮只有一个折叠头（含旁白、思考、工具、授权），头里只有数量；`processSettled` 为真时出现分隔线，把最后一段正文**提取**到组外。
- **候选 B**：在流式过程中实时判定「最后一段 answer = 终稿」（= `1e33b7fe` 现状）。**不够** —— 它带来两个方向相反的误判，且都已在评审中阐明：过度触发（无工具的纯长回复，前两段被误降级）；触发不足（`answer → 工具 → 结束` 时，尾随的旁白后面还跟着工具，它并非终稿却仍在组外保持亮色）。后者正是 T107 时代「各种调用穿插在 agent 的输出中」的原始投诉形状。
- **候选 C**：变灰绑「后面又出了一段字」。**与 B 同类**，且流式期间必然出现颜色跳变（先亮后灰）。

取舍：选候选 A。它把一次连续的颜色/结构变化压缩成**整个回合只发生一次**的结构变化，从根上消除抖动；且 `processSettled` 已经在 `MessageTimeline.tsx:1997` 存在，不需要新增任何 store 字段。

**关于思考行的吸顶：** 见 D3。

## 决定

采用**候选 A**。以下为完整设计。

### D1 · 单折叠头 + 流式完毕提取终稿

- 整轮只有**一个**折叠头；头里**只有数量**（`已处理 N 个步骤`）。
- 组内容 = 旁白 + 思考 + 工具 + 授权，按 block 顺序。
- 流式期间（`!processSettled`）：组**默认展开**，全部内容可见，**不存在「终稿」概念**。
- 流式完毕（`processSettled`）：出现分隔线（文案「最终输出」），最后一段正文**移出组外**，保持普通答案色。

**这条同时消解 `1e33b7fe` 的两个遗留争议**：

- **争议 C（流式时颜色会跳）**：不存在了。流式期间没有任何东西被提前点亮，也就没有「突然变灰」。
- **争议 A（「最后一段字」是否终稿的坏定义）**：判定时机从「实时逐段」改成「流式完毕的一次性提取」，过度触发与触发不足两个方向同时消失。

**待落地时确认的实现细节**：`processSettled` 为真时，最后一段 answer 段落需要一个前向判据——规则是「其后不再跟着 process 段落」，而非「它是最后一段」（后者会在 `answer → 工具 → 结束` 时把尾随旁白误当终稿）。

### D2 · 组默认展开，结束后保持展开（**推翻 031 D6**）

用户 2026-09-22 明确要求：「折叠头默认展开，输出结束了也保持展开状态。」

**这推翻 [决策 031](031-tool-calls-aggregate-and-work-group-always-folded.md) 的 D6**（「工作组**始终折叠**，运行中也不自动展开」）。031 D6 是同一用户在 2026-09-21 拍板的，理由是不想运行中被自动展开打断阅读。按 031 自己确立的判据（「同一个拍板人对同一处界面提出相反诉求时，以用户当下诉求为准」），本决策同样适用。

落地改动：

- `turnProcessFold.ts` 的 `turnWorkGroupOpen()`：`forcedOpen → userOpen → true`（默认值从 `false` 改为 `true`）。
- 仍然**纯派生、零 `useEffect`**（021/031 的共同要求继续有效）——默认值变化不引入任何副作用。
- `turnWorkGroupAwaitsUser`（未应答授权强制展开）是红线，**一个字不改**。组默认展开之后它依然是「唯一能自动展开组」的规则，方向安全。
- 用户的显式点击**仍然优先**：`userOpen !== null` 时以用户为准，所以用户可以收起。

### D3 · 思考行不再吸顶，改为显著背景行（**退休 T096 / 决策 028 的吸顶思考头**）

用户指出折叠头吸顶会与思考头吸顶冲突，并自答替代方案：思考不吸顶，改为显著的背景行。

**冲突的完整形态**（不只是两个 `top-0` 相撞）：

1. 思考行用 `thoughtFoldHeaderClass()` → `'sticky top-0 z-10 …'`；折叠头也要 `sticky top-0`。思考行在组**内部**，组有底色，视觉上会被压住。
2. 两者在**同一个** stacking context 里抢 `top-0`（思考头 `z-10` 落在 `[data-slot="scroll-area-viewport"]` 内，而该视图带 mask、mask 形成 stacking context），不是分层关系。
3. **最麻烦的一层**：思考头的「吸顶 + 收起时回滚」是**配套机制**。`ToolRows.tsx` 的 `pinsHeader = view.body === 'thinking'`，收起时调用 `scrollPinnedFoldHeaderIntoView()` 把滚动位置算回思考块自然顶部（`stickyFoldScrollTarget()`，`messageTimelineScroll.ts`）。思考不再吸顶，**这段补偿逻辑及其测试一并成为死代码**。

**决定**：

- 思考折叠头**移除吸顶**（`pinsHeader` 不再附加 `thoughtFoldHeaderClass()`）。
- 改为**显著的背景行**：与折叠头**共用同一套视觉语言**（`--accent` 底色 + `border-border` 边框 + 圆角），使「可折叠的层」在界面上一致。
- **连带退休**：`thoughtFoldHeaderClass()`、`scrollPinnedFoldHeaderIntoView()`、`stickyFoldScrollTarget()`，以及它们在 `chatTimelineLayout.test.ts` / `messageTimelineScroll` 相关套件中的断言。删除时**同批**完成，不留孤儿函数。
- ⚠️ **成本记录，不隐藏**：T096（决策 028）原本要解决的问题是「读一个很长的思考正文时，收起它的按钮会滚出视野」。本决策以「思考正文自带高度上限 + 内部滚动」替代——头始终可见，且不含滚动位置依赖，正好避开 `chatTimelineLayout.ts` 记录的 F10 振荡红线（吸顶元素高度不得随滚动状态变化）。
- `messageTimelineScroll` 里 `SCROLL_SURFACE_SELECTOR` 的 `subagent-detail` 分支同样受此影响，需一并核查是否有其它调用方。

### D4 · 折叠头吸顶 + 显著化

用户：「有时候内容多了根本找不到折叠头。」

- **吸顶**（`sticky top-0`）：这是该诉求的正面解法。仓库已有先例，且 `chatTimelineLayout.ts` 记录了唯一前提——**吸顶元素高度不得随滚动状态变化**。折叠头高度固定，满足该前提，故 F10 的振荡在结构上不可达。
- **底色 + 边框 + 圆角**：用 `--accent`（与用户气泡同档），不新造颜色。
- **数量徽标**：右侧 badge 报次数，滚动中也能看到进度。
- 数量词条沿用 `{{count}} steps processed`（→ 「已处理 N 个步骤」）。

### D5 · 折叠头语言跟随系统（**推翻 031 D7**）

用户：「中文还是英文跟随系统吧。」

- `TurnProgressHead` 改绑 `useI18n()`，不再绑 `englishTranslate`。
- **推翻 [决策 031](031-tool-calls-aggregate-and-work-group-always-folded.md) 的 D7**（「折叠头**保持英文**」），并退休其两条守卫：
  - `messageTimelineWiring.test.ts` 的 `[HEAD-EN-1]`；
  - `turnProgress.test.ts` 的 `[HEAD-EN-2]`。
- D7 的英文例外本是**为该头形态（英文步骤数行）而发**；头形态由本决策重做后，例外失去载体。
- ⚠️ **需同步处理**：`turnProgress.test.ts` 里同时断言了 `Worked for …` 系列的英文 helper 覆盖与 `zhTranslations` 条目，两者还被 `turnWorkZoneRow` 与 Run panel 共享。退休时必须区分「随本决策一起退休的部分」与「其它表面仍在用的部分」，别连带删掉仍被引用的词条。

### D6 · 长指令必须能看全（真 bug 修复）

用户：「工具调用中，有时候指令太长了，没有办法看全。」经查，这**不是截断问题，是内容永久不可见**：

1. `toolCard.ts` 的 `toolRowArgClass()` 返回 `min-w-0 truncate`（单行截断），且纯文本 arg **没有 `title` 兜底**（只有 `link` 分支的按钮带 `title={link.path}`）。
2. `ARG_COVERED_FIELDS.Bash` 把 `command` 列为「已在一行摘要里覆盖」：

```ts
Bash: ['description', 'command'],
```

于是 `deriveToolInputBody()` **不会为 Bash 生成完整输入体**——展开工具行也看不到完整命令。

**决定**：

- 把 `command` 从 `Bash` 的 covered 列表移除，让展开后能看到完整输入体。这是最小改动，且只影响 Bash 一族。
- 行内 arg 允许**换行**显示完整命令（而非单行截断）作为轻量补充。
- **不用 `title` 当主解法**：触屏与键盘够不到，且悬停读长命令不可用。

### D7 · 缩进节拍与层级

用户：「按照你说的使用新的缩进间距。」

- 旁白之间：**8px 标准档**（自然段落间距）。
- 操作块内部：**4px 紧凑档** + 12px 左内缩 + 一条极淡引导线（`color-mix(--border 60%, --background)`）。
- 完整指令 / 输出：在操作块引导线**内侧再进一层**。
- 三级层次对应 design-system 既有档位，**不新造任何尺寸或颜色**。
- 连续同类操作**聚合为一条**（可展开），但**被旁白或思考打断**——这一条与现有实现一致（`groupTimeline` 遇 text/thinking 即 `flush()`；`mergeAdjacentToolGroups` 只合并相邻组），**不需要改代码**。带授权的操作不并进聚合（031 既有例外继续有效）。

### D8 · 旁白与终稿同字号

用户：「旁白和最终输出可以字体字号相同。」

- 两者均为 `--text-chat-body`（16px）、同一行高，**只差颜色**（`turnIntermediateToneClass()` 的 `text-muted-foreground` vs `turnAnswerToneClass()` 的 `text-foreground`）。
- **这条已是现状**：`1e33b7fe` 引入的 `turnIntermediateToneClass()` 本来也只改颜色不改字号。**无需改动**，作为决策记录在此，避免后人「顺手」给旁白降档。
