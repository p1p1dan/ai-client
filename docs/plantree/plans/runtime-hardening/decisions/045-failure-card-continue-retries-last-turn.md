# 决策 045：失败卡「继续」改为重试上一轮

日期：2026-09-24。来源：T135（T128 GUI 复验 X3），用户当日拍板「改成重试上一轮」。落地任务 **T135**。

## 背景

- 现状：失败卡的「继续」把上一条提示词作为新消息再发一次，模型会收到两条相同的 user 消息；确定性输出下会原样复现同一次失败。

## 规则

1. 「继续」改为重试上一轮：不追加新的 user 消息，基于失败前的上下文重新发起这一轮。
2. 失败那一轮已产生的部分输出如何处理（丢弃重来 / 保留续写）在实现时按 runtime 现有的回合恢复机制定，定下后回写本条。
   **已定（T135，2026-09-25）：只丢弃失败的那条回复，这一轮已完成的工具轮次保留，从失败前的上下文续跑。** 这就是 runtime 现有流中断恢复的规则（`agent-loop/streamRecovery.ts` 规则 2），「继续」相当于它的手动版。做法：worker 把会话 leaf 移回失败回复的父节点（`session/retry.ts`，跨过末尾的失败回复及其后的 runStop / loopGuard 记录），失败回复不删除、留在被放弃的分支上，重试的新回复作为它的兄弟节点长出来；然后 `agent.continue()` 重新请求，不追加 user 消息。理由：一是这一轮已执行的工具已经改过工作区，从 user 消息整轮重来会把写文件、跑命令再做一遍，模型也会忘掉自己做过什么；二是失败回复本来就不进模型上下文（`snapshot` 过滤 error / aborted），模型这次拿到的正是失败那次请求的上下文；三是放进废弃分支而不删，分支树里仍能查看失败那次的输出。

## 落地说明（T135）

- 通路：失败卡「继续」→ `chat:retryLastTurn` → `WorkerManager.retryLastTurn`（与 send 同一条接纳路径，闩锁、Stop 看门狗、崩溃路径一视同仁，决策 046）→ `worker.send{mode:'retry'}`。渲染层不画乐观气泡，以本请求的 `session.status: running` 作为接纳证据；失败卡保留到该 running 到达为止。
- 按钮只在失败已收尾（`session.failed` 之后的 idle 已到）时可点，否则禁用并提示「上一轮仍在收尾」；本会话有发送在飞时提示「正在重试上一轮…」。禁用时点击不穿透。
- 找不到可重试的一轮（上一轮已完成、从未落盘、历史已被压缩、重载到了别的 leaf）：worker 拒绝（`retry_unavailable`），不起 run、不发事件、不改文件。渲染层**不自动重发**——这时会话记录里的最后一条提示可能属于更早的一轮——而是把它放回空输入框（非空则不动）、撤下失败卡并提示用户确认后自己发送。
