## 与 roadmap 字面不同的做法（已认可）

**T037**

- main-aux-02 发现原文 FIX 的后半句「`release()` 服务层自己拒绝仍有活 worker 的会话」没有做，接受「唯一调用点（`chat.ts` 归档分支，`setArchived` 全仓唯一调用方）顺序写死 + 一条用例钉住」。理由：让服务层自己判断 worker 是否存活需要注入 `WorkerManager`，而 scratch 服务目前被 `LegacyImportService` 等轻量模块引用，会拖入不必要的依赖；且修好 main-aux-01 之后越界路径已经进不了 map，这条断言会是永远不会触发的死代码，写不出判红用例。
- main-aux-03 采用「记住本次运行从设置解析出的每一个根」（`knownRoots`），不做跨重启持久化——这是发现原文给出的两个备选之一，也是唯一不改动 `session-index` 行结构（T038/T040 的文件）的做法。代价：换过临时根之后如果应用退出重启，旧根下的会话从「目录留盘、带信任残留运行」变成「cwd 不存在、打不开」，方向更安全但表现更硬。这一半已转 T040 追加项 4。

**T038**

- 读坏没有按验收字面「二选一」（保留旧版拒绝写 / 改名备份重建），而是按失败种类分三条分支：`ENOENT` 安静当首次运行；内容坏（JSON 坏 / 顶层非数组 / 行缺 `sessionId`）才备份重建；读不动（`EACCES`/`EIO`/`EBUSY`，最常见于 Windows 杀软短暂占用文件）保留上一版并拒绝写，`loaded` 保持 `false` 以便文件解锁后自动重读。理由：对「读不动」这种纯粹的这次读不到、内容其实没坏的情况做改名备份，等于亲手把一份好文件从应用视野里搬走，是更严重的数据丢失。
- 接受一处行为变化：索引处于「读不动」状态时，新建聊天（`recordCreated`）现在会当场抛错，而不是像以前那样静默成功、用空表悄悄覆盖用户全部历史会话。
- 2000 行上限与 10 秒回合合并窗口都是无实测依据的拍值（发现本身是静态推断），上机后如果 T024 容量对账表给出有数据支撑的值，需要回来调整（两个值都在文件顶部是独立常量）。

**T039**

- windows-02「已跑完的命令不再由收尸结果决定成败」这条规则被同时应用到 POSIX：进程组信号发送失败（非 `ESRCH`）也从「让一条已退出的命令 reject」改成「记 `cleanupError`、运行本身仍算成功」。这是 `runPipe` 与 T022 既有的 `createTreeKiller` 合流后的必然结果，也符合发现本身的道理（命令自身结局已知，收尸干不干净是另一回事），有独立用例钉住这条 POSIX 侧的行为扩大。
- windows-03 的修补落在 `src/runtime/host/exec.ts`（`resolveWindowsCommand`），没有动发现原文点名的 `src/runtime/plugins/mcp/index.ts`。理由：MCP 把 command 原样交给 `exec.spawn`，真正 `shell:false` 起进程的是 exec 层的两个载体；在 exec 层解析一次，MCP 与所有走 exec 的调用方一起受益，在 `mcp/index.ts` 解析则只修一半。
- windows-04「没装 Git for Windows 时」采用验收给出的第一个选项（不登记 bash 工具），没有做第二个选项（登记但说明前置条件）。理由：同文件对 `ask` / `browser_preview` 已经写死「宿主没有承载面就不注册」的规则，两个选项并存会让规则自相矛盾。
