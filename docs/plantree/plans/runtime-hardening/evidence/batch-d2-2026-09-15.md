## 与 roadmap 字面不同的做法（已认可）

**T037**

- main-aux-02 发现原文 FIX 的后半句「`release()` 服务层自己拒绝仍有活 worker 的会话」没有做，接受「唯一调用点（`chat.ts` 归档分支，`setArchived` 全仓唯一调用方）顺序写死 + 一条用例钉住」。理由：让服务层自己判断 worker 是否存活需要注入 `WorkerManager`，而 scratch 服务目前被 `LegacyImportService` 等轻量模块引用，会拖入不必要的依赖；且修好 main-aux-01 之后越界路径已经进不了 map，这条断言会是永远不会触发的死代码，写不出判红用例。
- main-aux-03 采用「记住本次运行从设置解析出的每一个根」（`knownRoots`），不做跨重启持久化——这是发现原文给出的两个备选之一，也是唯一不改动 `session-index` 行结构（T038/T040 的文件）的做法。代价：换过临时根之后如果应用退出重启，旧根下的会话从「目录留盘、带信任残留运行」变成「cwd 不存在、打不开」，方向更安全但表现更硬。这一半已转 T040 追加项 4。

**T038**

- 读坏没有按验收字面「二选一」（保留旧版拒绝写 / 改名备份重建），而是按失败种类分三条分支：`ENOENT` 安静当首次运行；内容坏（JSON 坏 / 顶层非数组 / 行缺 `sessionId`）才备份重建；读不动（`EACCES`/`EIO`/`EBUSY`，最常见于 Windows 杀软短暂占用文件）保留上一版并拒绝写，`loaded` 保持 `false` 以便文件解锁后自动重读。理由：对「读不动」这种纯粹的这次读不到、内容其实没坏的情况做改名备份，等于亲手把一份好文件从应用视野里搬走，是更严重的数据丢失。
- 接受一处行为变化：索引处于「读不动」状态时，新建聊天（`recordCreated`）现在会当场抛错，而不是像以前那样静默成功、用空表悄悄覆盖用户全部历史会话。
- 2000 行上限与 10 秒回合合并窗口都是无实测依据的拍值（发现本身是静态推断），上机后如果 T024 容量对账表给出有数据支撑的值，需要回来调整（两个值都在文件顶部是独立常量）。

**T039**

- windows-02「已跑完的命令不再由收尸结果决定成败」这条规则被同时应用到 POSIX：进程组信号发送失败（非 `ESRCH`）也从「让一条已退出的命令 reject」改成「记 `cleanupError`、运行本身仍算成功」。这是 `runPipe` 与 T022 既有的 `createTreeKiller` 合流后的必然结果，也符合发现本身的道理（命令自身结局已知，收尸干不干净是另一回事），有独立用例钉住这条 POSIX 侧的行为扩大。
- windows-03 的修补落在 `src/runtime/host/exec.ts`（`resolveWindowsCommand`），没有动发现原文点名的 `src/runtime/plugins/mcp/index.ts`。理由：MCP 把 command 原样交给 `exec.spawn`，真正 `shell:false` 起进程的是 exec 层的两个载体；在 exec 层解析一次，MCP 与所有走 exec 的调用方一起受益，在 `mcp/index.ts` 解析则只修一半。
- windows-04「没装 Git for Windows 时」采用验收给出的第一个选项（不登记 bash 工具），没有做第二个选项（登记但说明前置条件）。理由：同文件对 `ask` / `browser_preview` 已经写死「宿主没有承载面就不注册」的规则，两个选项并存会让规则自相矛盾。

**T040**

- `acceptFork` 选择「接上生产调用方」而不是删除，新增 `worker.fork.accept` RPC（协议版本仍为 1）。理由：全仓唯一的旧 `store.acceptFork` 调用点在死模块 `NativeSessionIndexAdapter.ts`，删除会让暂存标记永远清不掉，与验收「暂存标记不再永不清除」直接冲突；`contracts.ts:72` 早就留了 `acceptFork` 这个能力名。
- 暂存文件用 sidecar 标记 `<uuid>.jsonl.staged`，而不是验收字面「先落 `.staged` 名、提交后原子改名」。理由：fork 的新 worker 在索引行落库之前就已按路径打开转录文件，提交后改名要同步改 slot key、索引 `runtimeIdentity`、worker 自己的 `file` 字段三处，改动面远超本任务；sidecar 写在转录之前（意图日志在前），崩在任一顺序都留下扫描器认得的东西。
- 回收扫描落在 Main 的 `WorkerManager.ensureReady`，而不是 `src/runtime`。理由：「这个文件是不是已经被认领」只有会话索引答得上来，索引在 Main；而 Main 不应 `import` `src/runtime`（独立 npm 子包，会把 cordis 拖进 Main 包）。生产触发点目前只有 `chat:ensureHost`（渲染层启动握手），若将来要「不开聊天面板也会 fork」或无条件启动扫描，可把 `sweepStagedForkFiles` 提到 `main/index.ts` 的启动序列里，本次未这样做以免扩大文件范围。

以上三处编排者均已认可；审阅结论 `pass`。

**T045**

- 未做「锁超过 24 小时就自动判陈旧」。理由：会把开了好几天的会话的活写者判成陈旧，与模块契约（两个写者写同一个 JSONL 不可恢复）冲突。自动判据保留零误判的两条（早于本次开机、pid 是我们而进程不是），「没重启过、PID 被别的程序复用」这一种留给显式 `force`；因此「PID 复用不会把一把死锁永久锁死」的达成方式是重启自愈 + 用户强制接管自愈，而不是超时自愈。
- trace 轮转用跨进程目录锁，而不是验收更偏好的「`runs.<pid>.jsonl` 按进程分文件」。理由：改文件名会动到已落地的 T024 轮转契约（`runs.jsonl` / `runs.N.jsonl`）与现场取证脚本的读法，目录锁同时满足「追加不交织」这条，改名方案不满足。
- 改了任务文件范围外的 `src/runtime/plugins/session/store.ts`（11 行：`SessionConfig` 新增 `forceTakeover` 字段并接通 `acquireWriterLock` 调用）。理由：只把 `force` 参数加在 `writerLock.ts` 上，它在仓库里就没有任何调用方，是「记了没人读」的同一种形态；接到 `SessionConfig` 后 `force` 才真正被用例覆盖，剩下的只有 Main / IPC / 界面半边。

以上三处编排者均已认可；审阅结论 `pass-with-notes`——PID 复用且「没重启过机器」这一支，验收标准里「不会把死锁永久锁死」这句话要等界面半边（见下方转移表 T045b）落地才算真正解除，代码能力已经具备。

**T041**

- main-host-03 用发现原文给出的「更小改法」——`ManagedSlot.drainingEvents` 有界排空窗口，而不是验收字面「`retireAndDispose` 先 `await slot.dispose()` 再 `retireEntry`」。理由：字面改顺序会让一个正在拆的 entry 在最长 6 秒（3 秒 ACK + 3 秒退出确认）内继续留在 `entriesBySession` / `entriesByKey` 里且 `state` 仍是 `ready`——`send` / `compact` / 容量淘汰都可能把请求路由到一个正在消失的 worker，用户会看到莫名其妙的错误而不是 `session_not_ready`。排空窗口只放行 `permission.resolved` / `question.resolved` 两类「撤卡」事件，路由语义一点不动。

编排者已认可；审阅结论 `pass-with-notes`——报告「逐个 try/catch」的措辞比 main-host-02 的实际实现（只在导入槽这一段包了一层 try/catch，会话池本来就靠内部 `Promise.allSettled` 隔离失败）略强，属文档精度问题，不影响功能判定；main-host-03 的做法虽非验收字面但效果上仍满足「事件闸在 `slot.dispose()` 之后才关」。

**T046**

- **新开决策 014**：MCP 服务器每会话上限从固定 16 改为按内存分档 4/6/12（全机 12/36/120），编排者采纳，用户可推翻，详见 [decisions/014](../decisions/014-mcp-per-session-budget-by-memory-tier.md)。
