## 一、D13 根因

设置里的「保存位置」（`defaultTemporaryPath`）Main 侧恒读不到，原因是**读错了层级**。

`readSettings()`（`src/main/ipc/settings.ts:82-87`）返回的是 settings.json 的**顶层对象**。而这个文件的顶层只放
Main 自己拥有的键；用户在设置页改的每一个字段都在下面一层 `aiclient-settings.state` 里，因为渲染层是用
zustand 的 `persist` 中间件落盘的（`src/renderer/stores/settings/index.ts:494` 把 store 名定为
`aiclient-settings`，`stores/settings/storage.ts` 整对象读改写）。

本机实测文件形状（`~/.pilab/jyw-ai-client-dev/settings.json`，未打印任何凭据）：

```
$ jq 'keys'                                  → ["aiclient-settings", "credentialMode"]
$ jq '.["aiclient-settings"] | keys'         → ["state", "version"]
$ jq '.["aiclient-settings"].state|keys|length' → 55
$ jq '.defaultTemporaryPath'                 → null      ← 顶层没有
$ jq '.["aiclient-settings"].state.defaultTemporaryPath' → ""   ← 真值在这里
```

于是两处读取恒为 `undefined`，各自的 `?? ''` 把它变成「用户没选过」：

- `ScratchWorkspaceService.ts:83`（旧行号）`readSettings()?.[TEMPORARY_PATH_SETTING_KEY]`
- `TempWorkspaceService.ts:36`（旧行号）`readSettings()?.defaultTemporaryPath`

结果 `settingsTemporaryPath()` 恒返回 `''`，scratch 根与临时工作区基目录**永远回落默认的
`~/JYWAI/temporary`**。渲染层不受影响（它读自己的 store 拿得到真值，并显式把 `basePath` 传进
`temp:workspace:*`），所以用户看到的就是现场记录的那句「临时工作区去了新目录、临时对话还在老目录」
（证据 `dev-B/dev-02-t3-after-gui-change.txt`、`dev-02-t4-after-restart.txt`：改设置之后新建的对话
`e51a06d5` 仍落在旧根，重启后三条 DEV-2 会话的 `workspacePath` 全部仍指向旧根）。

**附带确认**：`ScratchWorkspaceService.ts:78-82` 那段 F2-a 注释（「让两个读者立刻看到用户刚改的 base
path」）在当前文件形状下拿不到——两个读者确实读的是同一份拷贝，但读的是同一个**不存在的键**。

### 统一入口的选择

先查了仓库里有没有现成的 `aiclient-settings.state` 解析函数，**没有共用函数**，只有四处各写各的临时解包：

| 位置 | 用途 | 处理 |
|---|---|---|
| `src/main/utils/shell.ts:118-122` | `shellConfig` | 解包正确，本次**不动**（见第六节遗留） |
| `src/main/index.ts:288-292` | `language` | 解包正确，不动 |

| `src/main/services/remote/RemoteServerSource.ts:1551` | 远端 shellConfig，读的是**另一个文件** | 不动 |

排除的两个假阳性：`PiPluginService.ts:141` 读的是 pi 自己的 settings 文件，不是本应用的；
`subagentCatalog.ts:96` 读的 `nativeSubagentsDisabled` 是 Main 自读自写的顶层键，形状自洽。

## 五、D6 判断：**与 D13 不同源**，已单独定位并修复

排查用了一个只读子代理把渲染层的显示链路走了一遍，结论如下。

### 排除 D13 同源的依据

- 侧栏是否显示一条会话，**完全不看路径**。分组判据是 `session.unbound` 这个标记
  （`sidebarTree.ts:217` 未绑定组、`:174` 项目组、`:433` 最近列表），标记逐字来自索引行
  （`sessionIndexMerge.ts:125-126`）。渲染层的 `getEffectiveTemporaryBasePath` 只用于临时工作区的
  创建/删除（`App.tsx:651,693`、`useComposerTarget.ts:343`），**从不参与分组或可见性**。
- 唯一的根前缀比较在 Main 内部且自洽：路径由 `ScratchWorkspaceService.ensure` 分配、由同一个实例的
  `isScratchPath`（`:150-154`）按 `resolveBasePath()` 加 `knownRoots` 判断，即使运行中换根，
  已分配的路径也不会被判成「不是 scratch」。
- 真正导致消失的那段代码**完全不涉及路径**，只看 `workspaceId` / `hostBoundSessionIds` / `runtimeIdentity`。

所以 D13 的修复既不会治好 D6，也不会加重它。

### D6 真正的根因

`rebindSessionsToTree`（`src/renderer/components/workspace-shell/useSyncChatWorkspaceTree.ts:116-162`）
**缺一条未绑定会话的分支**，而重启路径 `mergeSessionIndex`（`sessionIndexMerge.ts:151`
`if (!workspaceId && unbound)`）有。两条重建列表的路径对「未绑定」的认知不一致：

1. 未绑定会话的 `workspaceId` 是 `''`（U13 的设计），`workspaceById.get('')` 必然 `undefined`；
2. 于是它掉进「孤儿」规则（`:152` 旧行号），而跑过一轮的会话带着 `runtimeIdentity`，
   被 `continue` **直接从 store 里丢掉**；
3. 这个函数在**工作区树签名变化**时触发（`:457-462`）——临时工作区增删、worktree 列表回来、
   加/删仓库、切换选中的仓库都算；
4. 重启时不走这条路径，索引行从没被动过，所以「下次启动又全部回来」。

对得上证据：`dev-A1/dev-08-reclaim-on-next-boot.json` 的 `sidebarAfterBoot` 里 4 条 devA1 会话
`"ws": ""` 全部回来；`dev-09-27-temp-workspace-remove.json` 里 `sidebarBefore.scratchSession: null`
——索引行完好、界面上已经没了。

### D6 改动

`src/renderer/components/workspace-shell/useSyncChatWorkspaceTree.ts:131-155`（+25 行），
在「孤儿」规则**之前**插入一条分支：

```ts
if (!session.workspaceId && (session.unbound != null || session.runtimeIdentity != null)) {
  remapped.push(session);
  if (bound.has(session.id)) nextBound.add(session.id);
  continue;
}
```

判据说明：

- `!session.workspaceId` 在这个 store 里等价于「从来没绑定过项目」。工作区被删掉的会话保留的是
  **原来那个非空 id**（只是查不到），所以不会被这条分支误捕。
- 为什么不只看 `session.unbound`：`createUnboundChatSession`（`chatSessionActions.ts:116-143`）
  **不写这个标记**（注释明说「a live unbound chat created in this run has no index row yet」），
  它要等第一次发送落索引、下一次刷新才被补上。那个窗口里 `runtimeIdentity` 是唯一信号。
- 保留 `bound.has(...)` → `nextBound.add(...)`：和上面「工作区命中」分支一致，否则 store 会忘记
  这条会话还连着 worker。
- **没碰**未发送草稿的收养路径（无标记、无 runtimeIdentity 的仍落到 `:156` 收养进首选工作区），
  那是 U22 的行为，且草稿没有历史会被放错地方。

新增用例 `treeSyncPatch.test.ts:289-359`（5 条，见第四节）。

### 已排除但仍留档的两点

1. **`!preferred` 早退**（`useSyncChatWorkspaceTree.ts:108-110`）：工作区树为空时返回
   `sessions: []`，把未绑定会话也一起清空。同一缺陷类，但不是本次证据里观察到的那条触发路径
   （现场工作区一直存在），**本次未改**，建议单列线索。
2. **二阶风险**：`SessionIndexService.ts:204-222` 把显式的 `unbound: false` 当成「清除标记」，
   而 `sessionIndexMerge.ts:125-132` 每次刷新都从索引行重新推导活动行的标记。
   若 Main 的 `isScratchPath` 哪天对渲染层正当作 scratch 在跑的路径答 `false`，这条会话会
   **运行中和重启后都消失**。本次证据排除了这条（重启后 `unbound:true` 完好），但它是 D13 一类
   缺陷唯一可能波及可见性的通道，记在这里备查。
