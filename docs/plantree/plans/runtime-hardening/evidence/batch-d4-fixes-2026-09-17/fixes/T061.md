## 一、根因

### D1 / D24（high，同源）

`JsonlSessionStore` 有两道容量闸：**单行上限**（`SESSION_MAX_ENTRY_BYTES`，8 MiB）和**会话总预算**（`SESSION_MAX_BYTES`，32 MiB）。

单行上限在 T046 时就已经**放在写队列外面**做预检，代码注释写明了理由：「refusing this one write leaves the session writable」——拒了这一条，会话还能继续写。

总预算**没有对应的队列外预检**，只在队列内部检查（改动前 `store.ts:357`）。而 `enqueue`（改动前 `:378-390`）是这样接队的：

```ts
const work = this.tail.then(operation);
this.tail = work.then(() => {});   // work 一 reject，tail 就变成已 reject 的 promise
```

于是一次 `session_size_limit` 拒绝之后，`this.tail` 永远是那个已 reject 的 promise，此后每次 `this.tail.then(operation)` 都**不执行 operation**、只带着同一个错误 reject。同一个 store 实例从此只读——连一条纯文本都写不进去，哪怕文件里还剩 14 KB 余量。

这跟三处设计注释直接冲突：`store.ts` 的 capacity-04 注释、`agent-loop/attachments.ts:50-52` 的 capacity-01 注释（「发送当场被拒……会话本身照常可写」）、以及容量对账表第八节。**「会话本身照常可写」这一条原本是错的。**

### D24 的「静默」那一半——查清了，结论跟原判有出入

真机现象是「撞预算后打一句纯文本点发送，输入框被清空、时间线什么都不出、网关收不到请求、会话文件不长」。逐层跟下来，链路是这样的：

1. `agent-loop/index.ts:172`，`execute()` 的**第一句**就是 `await session?.flush()`。`flush()` 返回的正是 `this.tail`——中毒之后它是个已 reject 的 promise，所以这一句当场抛。
2. 抛在 `run()` 的 try 里，`run()` 的 catch（`:151-166`）照常发了 `session.failed` + `session.status: idle`，再 rethrow；`nativeWorkerRuntime.startSend` 的 `.then(_, error => log)`（`:397-402`）把 rethrow 吞掉只记日志——**这是设计好的，注释写明「loop 已经发过 session.failed 了」**。
3. 所以错误**确实**回到了渲染层：`chatSessions.ts:982` 把 `session.failed` 的 payload 写进 `lastError`，`ChatComposer.tsx:761` 把它渲染成 `Error: ${lastError}` 的红色 mono 块。

**所以「错误被吞在 appendMessage 的调用方」这个假设不成立**，`session_size_limit` 全程没有被吞。真机看着「什么都没发生」，是另外两个原因叠加：

- **抛点在 `startRun` 之前**。`execute()` 第一句就挂了，`this.ctx.runtimeEvents.startRun(...)`（`:217`）从没执行，所以没有 `message.started` 用户回声、时间线不开新回合；`turnHead.ts:270` 的 `ownsSessionFailure` 对「压根没有回合」的失败明确返回 false（注释原话：pre-admission failure「has no owner here at all」）。用户打的那句话就这么没了。
- **错误文案跟上一条一模一样**。第 5 条被拒时红块里已经是 `Error: session exceeds the configured size budget`，第 6 次纯文本失败又写同一句进 `lastError`，红块**内容零变化**——肉眼上和「红块一直挂在那儿、这次点了没反应」无法区分。

补充一条顺带查清的事实：`MessageTimeline.tsx:712` 那张会话级 `Session failed` 卡片，网关是 `status === 'failed'`；但 `session.failed` 后面**紧跟**一条 `session.status: idle`（`projector.ts:541` 与 `agent-loop/index.ts:160` 两处都这么发），`upsertSessionStatus` 不粘滞，于是 `failed` 立刻被 `idle` 覆盖，这张卡片实际上任何路径都留不住。**耐用的可见通道只有 composer 上方那个 `lastError` 红块。**这条不在 T061 范围内，只记录备查。

结论：D24 的「静默」不需要新造错误回程通道——现有通道是通的。**把 D1 修掉，第二句纯文本就根本不会失败**，静默死会话随之消失；本任务另外用一条用例把「拒绝确实作为 `session.failed` 回到渲染层」钉死，防止将来有人把它吞掉。

### D25（medium）

`preparePrompt`（`agent-loop/attachments.ts`）把图片构造成 pi 的 `ImageContent`，只有 `{type, data, mimeType}` 三个键；文件名只进 `PreparedPrompt.metadata`（`MessageAttachmentMeta`），那个数组**只**用来填实时事件 `message.started.attachments`（`agent-loop/index.ts:222`、`events/projector.ts:284`），从不落盘。

## 五、D25 方案取舍

**选的方案**：在落盘的 image block 上挂一个带命名空间的额外键 `aiclientName`。

**为什么不选另外两个**：

1. **pi 官方字段**：`ImageContent`（`@earendil-works/pi-ai`）只有 `{type, data, mimeType}`，没有给文件名留位置，也没有 index signature。没有「合规」的官方字段可用。
2. **挂在消息上的附件清单**（照 `internalMessage.ts` 的 `aiclientInternal` 那样，在 message 上挂一个 `MessageAttachmentMeta[]`）：清单要靠**下标**跟 block 对上，而两者**不是一一对应**的——文本附件被折进 prompt 正文、根本不产生 block。这个配对是第二处会出错的地方。挂在 block 上，名字就跟着它命名的那个东西走。

**为什么对既有读者无害**（逐条查过，不是推断）：

- **永远到不了 provider**：pi-ai 的每一个 provider adapter 都是**重建** image block，而不是透传。Anthropic 是 `{type:'image', source:{type:'base64', media_type: block.mimeType, data: block.data}}`（`dist/api/anthropic-messages.js:85-99`）；OpenAI 拼 `data:` URL（`dist/api/openai-completions.js:938-944`）；Google 拼 `inlineData`（`dist/api/google-shared.js:118-125`）。未知键在边界上被丢掉，请求不会变大，也不会被任何 API 拒。
- **文件对别人仍然可读**：会话 codec 原样序列化消息、原样带过未知字段（`internalMessage.ts` 的头注释就是靠这一点成立的）；任何按 `type === 'image'` 读的读者——包括 `pi --session`——会忽略不认识的键。
- **带命名空间而不是直接叫 `name`**：将来 pi 若给 content block 上的 `name` 定义自己的语义，不会跟我们的静默撞车。

**代价（明写）**：

- 文件名被复制进会话文件，每个附件多几十字节，计入 32 MiB 总预算。相对它标注的那坨 base64 是噪声级。
- 用户提供的文本从「只在内存里过一遍」变成「落盘持久化」。接受：同一个字符串本来就已经显示在时间线上、也随发送进了日志。
- **和决策 015 的关系**：015 要把附件字节移出 JSONL，届时得决定 payload 放哪。名字**故意**留在 block 上、不提前迁就那次搬迁——「贴在 block 上的标签」无论字节最后落在哪一侧都是对的。这一点写进了 `attachmentRider.ts` 的头注释。

### 被证伪的那条，以及改法

审阅（`/tmp/t032/reviews/group1.md` §三②）证伪了本记录与 `attachmentRider.ts` 头注释里的断言「未知键永远到不了 provider」。事实：十个 pi-ai adapter 里九个会重建 content block 并丢弃未知键，但 `pi-messages` 不重建——它把 `{ model, context, options }` 原样 `JSON.stringify` 发出（`node_modules/@earendil-works/pi-ai/dist/api/pi-messages.js:248-272`），而本仓把这个 API 列为用户可选（`shared/userProviders.ts`、`model-adapter/catalog.ts`、`binding.ts:70`）。所以「上线看不见」根本不是 adapter 的性质。

改法是把它变成本仓自己保证的性质，且只有一个出口：

| 文件 | 改动 |
|---|---|
| `src/shared/aiclientKeys.ts`（新建，87 行） | 命名空间常量 + `isAiclientKey`（判据是 `/^aiclient[A-Z]/`，不会误吞以同样字母开头的 provider 字段）+ `stripAiclientKeys` 深度剥离。**无改动时返回同一引用**，不分配、不破坏任何按引用比较的缓存 |
| `src/runtime/plugins/model-adapter/index.ts`（+44/-1） | `withoutAiclientKeys(models)`：用 Proxy 包住 `Models` 的四个吃 `Context` 的调用（`stream` / `complete` / `streamSimple` / `completeSimple`），在 `register()` 里套上。WeakMap 缓存保证同一 provider 的多个 model 拿到同一个包装对象 |
| `src/shared/attachmentRider.ts` | 注释纠正：不再说「每个 adapter 都会丢」，改成「runtime 在出网前剥掉；adapter 顺手丢是附带事实，`pi-messages` 不丢」 |
| `src/runtime/plugins/agent-loop/attachments.ts` | 同上，挂 rider 处那三行注释改指 model-adapter |

**为什么选 `register()` 而不是逐 adapter，也不是 `buildProviderModels`**：`register()` 是 `bindCatalog`（磁盘 models.json）与 `bindInjected`（离线 smoke 的 faux provider）唯一共同必经点，而 `ModelAdapterPlugin` 本身就是文件头写明的「runtime 通往 provider 的唯一一扇门」——出网调用全仓只有三处，都是 `resolved.models.streamSimple(...)`（`agent-loop/index.ts:436`、`subagent/run.ts:247`、`worker/nativeUtility.ts:239`），全部从 `resolve()` 拿注册表。逐 adapter 改要动十处并且下一个 adapter 还会漏。

### 用例（`src/runtime/__tests__/providerWireNamespace.test.ts`，新建 172 行 / 7 条）

用真 `ModelAdapterPlugin` + 真 `piMessagesApi`，走 recordingFetch 读**请求体本身**（照抄 `catalog.test.ts` 「what the bound provider puts on the wire」的做法）：

1. `pi-messages` 出网：message 上的 `aiclientInternal` 没了，image block 全等 `{type,data,mimeType}`，整个 payload 的 JSON 里既搜不到 `aiclient` 也搜不到 `holiday.jpg`；
2. **反向（落盘那一半）**：调用方自己那份 history 一个字没变，`aiclientName` / `aiclientInternal` 都还在——「落盘有、上线无」两边各钉一条；
3. 无 rider 的请求逐字不变（保证守卫不改造正常流量）；
4. `anthropic-messages` 同样搜不到 `aiclient`（这条是**控制组不是判据**，见下）；
5–7. `stripAiclientKeys` 单元：无改动返同一引用；`aiclientele` 这种同前缀字段保留；两个 rider 模块产出的键都满足 `isAiclientKey`（两个模块与剥离规则之间没有 import，这条是它们不走散的唯一守法）。
