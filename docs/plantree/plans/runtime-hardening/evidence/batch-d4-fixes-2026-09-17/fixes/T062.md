## 一、D3（medium）：模型目录两侧口径不一致

### 1.1 根因（复核了 `/tmp/t032/sections/investigate-vllmproxy-catalog.md` 的结论，成立）

选择器和 worker 读的**不是同一份东西**：

| 侧 | 目录来源 | 过滤 |
|---|---|---|
| 渲染层模型选择器 | `chat.listPiModels()` → `readPiModelCatalog()` → `PiModelConfigService.readCatalog()` → 磁盘 `<agentDir>/models.json` | 无 |
| worker | `WorkerManager.ts:3111` 注入 `resolveNativeModelCatalog()` → Main 用「凭据库用户服务 + 托管缓存」在内存现组 → 随 bootstrap 下发 → `bootstrap.ts:477-478` 走 `parsePiCatalog(dir: null)` | `parsePiCatalog` 四条丢弃规则 |

磁盘 `models.json` 是这条链路的**输出**（`writeRuntimeConfig`），不是输入。所以任何只写进磁盘、没进凭据库的 provider（本机的 `vllmproxy` 是 09-11 手工写的）都「列得出、发不出」，报 `no model "…" in the catalog (N available)`；而且下次在设置页动任何一个 AI 服务，`writeUserProviderRuntimeConfig()` 会按凭据库重写这个文件，把它连同选择器里那一行一起静默抹掉。

### 1.2 方案取舍（任务书授权我定，要求「影响面最小、对 TUI 无害」）

**选定：把选择器的输入换成 worker 拿到的那份文档**（`resolveNativeModelCatalog()` 的 `models` 半边）；拿不到（返回 `undefined`）时回落读磁盘——那正好是 worker 也回落读盘的分支（T021 规则，`nativeCatalog.ts:55-76`），所以两条分支各自内部都一致。同时把「磁盘上有、运行时目录里没有」的 provider 记一行日志。

**为什么不做调查报告建议的「`readPiModelCatalog` 也过一遍 `parsePiCatalog`」**：

1. **它单独做并不能修掉这个缺陷。** `vllmproxy` 在磁盘上形状完全合法、`auth.json` 里有非空 key，`parsePiCatalog` 不会丢它——选择器照样列得出，worker 照样没有。真正的分歧是**输入文档**，不是解析规则。
2. **把解析器搬进 Main 的代价是跨包搬家。** `parsePiCatalog` 在 `src/runtime/plugins/model-adapter/catalog.ts`，而 `src/runtime` 是独立 npm 子包（自带 cordis / pi-ai），根 `tsconfig.json` 明确 `exclude` 了它。Main 直接 import 会把 `contracts.ts` → cordis/pi-ai 一路拖进根 tsc，必然红。要共享只能把纯解析部分（约 230 行：`parsePiCatalog` / `parseModel` / `expandHeaders` / `readProviderKey` / 四个常量表）上提到 `src/shared`，并把 `RuntimeConfigError('models_json_shape')` 改成跨层错误——这是一次**核心 runtime 文件的大搬家**，超出一条 medium 修补的范围。
3. **而且它有独立的行为风险。** 一旦 Main 也跑 `parsePiCatalog`，凡是本地安装里「`models.json` 有、`auth.json` 没有对应 key」的 provider（`anthropic-messages` / `openai-*` 等 7 种协议）会从选择器里**直接消失**，而现在诊断（`dropped`）在界面上没有任何出口（那正是 T050 的题目）。模型无声消失比现在的「选了发不出」更难自查。

**对 TUI 无害**：本次一个字节都没改磁盘 `models.json` / `auth.json` 的写法与内容，pi CLI / 内嵌 TUI 读的还是原来那两个文件。只改了「选择器从哪拿数据」。

**残留（明写）**：本次对齐的是**输入文档**，不是**过滤规则**。`parsePiCatalog` 的 `no_api_key` / `no_base_url` / `unknown_api` / `no_usable_model` 四条仍然只在 runtime 侧执行，所以理论上仍可能出现「选择器列出、runtime 丢弃」的第二类分歧（最现实的触发条件：托管缓存里的 provider 继承 key 为空）。建议挂在 **T050**（能力目录诊断出口）后面做：先让 `dropped` 在界面上有位置，再把过滤搬到共享层，否则用户会遇到「模型凭空少了、没人解释」。

## 二、D19（medium）：H/21 中文「本应用没有这个模型」覆盖层触发不到

### 2.1 根因

`isModelMissingError()`（`modelMissingError.ts:34-37`）只认 `WORKER_MODEL_NOT_FOUND` 码或子串 `Pi model not found`。会话路径真正抛的是
`src/runtime/plugins/model-adapter/index.ts:75-78` 的 `RuntimeConfigError('model_not_in_catalog', 'no model "<p>/<id>" in the catalog (N available)')`。

**码其实一直存在，只是没上路**：`AgentLoopPlugin.run()` 的 catch（`agent-loop/index.ts:151-159`）发 `session.failed` 时只带 `error.message`，把 `error.code` 丢了。渲染层那一路（store 的 `lastError` → `MessageTimeline` 失败卡 / `ChatComposer` 状态条）只看得到一个字符串，于是只剩下英文句子可匹配——而两个既有信号都不在那句话里，覆盖层成了死分支。

### 2.2 修法（按任务书：在 runtime 侧给该错误一个稳定 code 并沿既有回程通道传到渲染层）

runtime 侧新增 `thrownRunErrorText(error)`：**抛出型**失败若带字符串 `code`，就按 `` `${code}: ${message}` `` 拼进 `session.failed` 的文本。这不是新发明的格式——worker RPC 的 `errorPayload`（`piWorkerRpcServer.ts:284-299`）和续聊路径的 `encodePiResumeError`（`historyError.ts`）本来就是这个形状，渲染层已经在按这个形状读码了。

范围刻意收窄到 catch 分支：**正常跑完但失败**的回合走 `RunProjection.finish()`（`events/projector.ts:524-546`），那条的 message 是供应商自己的句子，不动它——这也保证了 `sessionAttachmentFill.test.ts` 与 `runtimeEvents.test.ts` 里既有的 `session.failed` 文本断言不受影响（实测两个文件全绿）。

渲染层按**码**判断，不匹配英文句子：新增导出常量 `MODEL_NOT_IN_CATALOG_CODE_TOKEN = 'model_not_in_catalog'`，并入 `isModelMissingError` 的或条件。

顺带免费修好：续聊失败路径 `encodePiResumeError` 也会把这条归到 `model_missing`（它就是调 `isModelMissingError`）。

## 1. 先查清：为什么发送失败这条路上覆盖层出不来

复验报告把两个渲染点分别记成「历史恢复失败」和「要求时间线里有 error 消息」。读码后的实际情况是**三条路各自差一样东西**，
其中第一条的死因和报告写的不同，值得写死在这里：

1. `MessageTimeline.tsx:712` 的会话级 `Session failed` 卡片（模型缺失分支在 `:742`）——门是 `status === 'failed'`，
   不是历史恢复。而 runtime 在 `session.failed` **后面紧跟**一条 `session.status: idle`
   （`agent-loop/index.ts:161-164` 与 `events/projector.ts` 各一处），`upsertSessionStatus` 不粘滞，
   于是 `'failed'` 当场被 `'idle'` 覆盖，**这张卡在任何路径上都活不过一次渲染**。这条事实 T061 记录第一节末尾已查清并记为超范围。
2. `MessageTimeline.tsx:1171` 的错误气泡替换——要时间线里有一条 `role:'error'` 的**消息**。
   只有 IPC 级 catch（`chatSessions.ts:1574` 一带）才写这种消息；`session.failed` 事件只写 `lastError`，不写消息。
3. `HistoryErrorNotice` 那条确实只管历史读失败，与发送无关。

**发送失败这条路上唯一耐用的信号是 `lastError`**：它是 composer 上方那个红块的开关
（`deriveChatEmptySurface({hasError})` → `'error-notice'`），也正是复验现场唯一看见的东西。所以中文卡放在那儿。

## 6. 需要真机复验的点 + 遗留

1. **DEV-32 原样重做**：造一条模型已消失的会话，在 GUI 里发一句。应当看到 composer 上方是**中文卡**
   （标题「本应用没有这个模型」+ 正文 + 提示 + 「去 Pi 设置补上模型」按钮 + 下面一行等宽原文点名模型），
   状态条那一行也应当是中文。点按钮应当跳到「设置 · Pi」。
2. **反向**：随便造一个别的失败（比如 bootstrap 超时），composer 上方应当**仍是原来的红色等宽诊断框**，
   没有被这张卡吃掉。
3. **遗留一（同类、未修，不在本次授权范围）**：`AgentTerminal.tsx:208-218` 的模型缺失覆盖层四个字段
   （title / message / hint / actionLabel）**同样没套 `t()`**，`t` 就在同一函数里（`:224` 用了）。
   与状态条是同一个缺陷类，中文界面下这张 TUI 覆盖层整张是英文。本次没改是因为该文件与 R-B（TUI 侧）的工作面相邻，
   避免同时改同一片代码。建议下一批顺手补四个 `t()`，成本一行一处。
4. **遗留二（结构性）**：`MessageTimeline.tsx:712` 那张 `Session failed` 卡片因为 `session.status: idle`
   紧跟覆盖而**对所有失败类都活不过一次渲染**。本次是绕过它，没有修它。要真修需要让会话状态对 `failed` 粘滞
   （或让时间线卡片改读 `lastError`），属 runtime 事件语义改动，建议单独立项。
