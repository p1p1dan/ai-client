# T063（批次 D4）— D12：兼容根子代理定义「编辑后删不掉」

- 仓库 `/home/ai/code/ai-client`，分支 `feat/runtime-evolution`，基线 HEAD `b3d751e3`
- 缺陷来源：`evidence/batch-e-devbox-2026-09-17/defects-ledger.md` D12（DEV-3 判负），现象记录见 `/tmp/t032/sections/B.md` 的 DEV-3 节与 `dev-B/dev-03-*`
- 状态：已改代码 + 已加回归用例，**未提交**

## 1. 根因

设置页的「编辑」和「删除」走的不是同一份文件。

- 目录合并规则是「主目录 `<agentDir>/subagents` > 兼容根 `~/.agents/subagents` > 内置」，同名先到者赢
  （`src/runtime/plugins/subagent/catalog.ts:78-89`、`src/shared/subagentDefinition.ts:566-586`）。列表按这个规则去重，
  一个名字只出一行。
- 但写路径无条件写主目录：`save()` 先 `mkdir(this.directory())`，再写 `pathFor(name)` = `<agentDir>/subagents/<name>.md`
  （改前 `subagentCatalog.ts:236/237`、`:408`）。也就是说**编辑兼容根的定义 = 复制一份到主目录再改**，兼容根原件一字未动。
- 删除只删「列表那一行的 filePath」（改前 `:267-268`），也就是刚才那份影子副本。副本一没，兼容根那份按合并规则重新浮上来，
  **带着编辑前的旧内容**，要再删一次才真的没有。全程没有任何提示说「你编的是副本」。

真机四时点快照（`dev-B/dev-03-t0..t4`）与这条读码完全对得上：t1 兼容根 md5 不变、主目录新增 207 B 副本；t2 删一次后那行回到 ORIGINAL。

## 2. 方案取舍：选 A（按来源文件编辑 / 删除）

**选 A 的理由 —— 兼容根并没有「只读」的安全约束。**
runtime 侧注释里唯一的安全性论述是「**项目目录**永不扫描：仓库不能靠被打开就往用户目录塞一个可委派的子代理」
（`src/runtime/plugins/subagent/catalog.ts:9-16`），说的是 project root，不是兼容根。
`~/.agents/subagents` 在用户自己的 home 下、与 `~/.agents/skills` 同层；而本仓已经把 `~/.agents/skills` 当**写入目标**用
（`src/agent-host/userResourcePaths.ts:26` 直接让模型把技能装到那里）。手册里的「兼容根（只读）」是在描述当时的实现行为，不是安全要求。
此外 main 侧 `roots()` 的原注释本来就写着「用户应当看到定义**在哪**——所以一行带着它的文件路径，而不是被悄悄复制走」
（`subagentCatalog.ts:83-90`），也就是说 A 才是原设计意图，写路径是没跟上。

因此不取 B（保留影子 + 删除时连兼容根一起删 + 编辑时提示「已复制到主目录」）：B 要用一条提示去解释一个本可以不存在的副本，
且「我编的文件到底是哪一个」这个问题永远还在。

**A 之外多做的一点（并说明代价）：删除按「名字」清干净。**
删除时删掉**所有**声称这个名字的用户文档（两个根都算），而不只是列表那一行。理由：已经装过旧版本的用户磁盘上已经躺着影子对，
只改写路径救不了他们，一删仍会回弹。被影子盖住的那份文件在界面上没有行、runtime 也永远不会加载它，删掉它不会拿走用户能用到的东西；
留着它恰恰就是「删除像失败了」的成因。代价：删除动作可能一次删两个文件，而删除确认框仍写「This removes the definition file.」（单数）。
判断是文案与行为的偏差可接受，且不改渲染层可以少动一处 i18n；如果后续要精确，改这一句即可。

重命名同理：老名字的所有文件一起删，否则被影子盖住的旧定义会在「刚被改名走」的名字下重新出现。

## 4. 用例

正向（这 5 条就是 D12 的判据，改前必失败）：

1. `edits the compatibility root in place instead of copying it` —— 兼容根放定义 → 编辑描述 → 兼容根文件内容变成 EDITED，
   **主目录根本没被创建**（`readdir` 抛错），列表仍只有一行。
2. `is gone after ONE delete, and does not come back holding the old contents` —— **DEV-3 原序列**：放 → 编辑 → 删一次 →
   返回视图里没有该行；再 `read()`（等价于重开页面 / worker 每回合重扫）仍然没有，`broken` 为空，兼容根目录为空。
3. `deletes the copy an older build left behind, in the same one delete` —— 预置旧版本留下的影子对（主目录 EDITED + 兼容根 ORIGINAL），
   删一次后两个根都空、行不再出现。
4. `renames a compatibility-root definition without moving it out of that root` —— 改名后兼容根里只剩 `probe-renamed.md`，主目录未被创建。
5. `writes back to the file it came from even when that file has another stem` —— 文件名与 frontmatter `name` 不一致时，
   写回原文件而不是在旁边新建 `<name>.md`（否则同一个根里就有两个文件抢一个名字，正是本缺陷的形状）。

反向验证（改前改后都必须通过，用来确认修复没有越界）：

6. `still writes a NEW definition into the agent directory` —— 兼容根有别的定义时，新建的定义仍然落主目录，兼容根不被写入。
7. `still shadows a builtin into the agent directory, never into either original` —— 「自定义内置」仍写主目录的影子文档、不动内置；
   删掉影子后内置定义原样回来（内置覆盖 / 删除语义无回归）。
8. `deleting one definition leaves a differently named one in the other root` —— 删主目录的 helper，不碰兼容根里叫 theirs 的定义。

反向验证实跑记录（临时把 `subagentCatalog.ts` 回滚到 HEAD 再跑，随后原样恢复）：
`Tests 5 failed | 3 passed | 28 skipped` —— 1～5 条在旧代码下全部失败，6～8 条两侧都过。
