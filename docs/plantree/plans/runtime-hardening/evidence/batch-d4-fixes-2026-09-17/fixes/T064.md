## 1. 根因

### ① 用户那条消息「被吞」——其实没丢，是藏在一个图标后面

发送链路（真机走的就是这一条）：composer `handleSend` → `runSend` → `runCreateSequence` →
`window.electronAPI.chat.createSession(...)` → Main `chat:createSession` → `WorkerManager.createSession` → bootstrap。

`runSend` 在提交点（`ChatComposer.tsx:1380` 一带）就把输入框清空并把附件从活动列表摘走，同时留下一份快照 `committed`。
之后每条非成功出口都汇到 `finalizeOutcome`，由**唯一权威** `decideFailureAffordance(outcome, origin)`
（`queueRelease.ts`）决定这份快照的去处：`'resend'` = 塞进组件内的 `retryable`（渲染成圆形 ↺ 按钮），
`'restore-draft'` = 写回 composer 草稿（`restoreDraftIfComposerEmpty`）。

bootstrap 超时时，IPC 直接 reject，`runCreateSequence` 里没有 catch，异常一路抛到 `runSend` 的外层 `catch`：
写 `lastError`（那张红色错误卡），再按 `decideRunEntryOutcome({fatalHostError:true, 无 echo, 无进展})` = `'rejected'`
+ `origin:'direct'` 判给 `'resend'`。

**所以改前的真实状态是：文本与附件都还在，在 ↺ 里。** 截图右下角那两个圆按钮正是
`deriveActionButtons(hasFailed:true)` 返回的 `[retry, send]`（`queueRelease.ts:641-646`）。
点验代理看到「输入框空 + 会话区 No messages yet」就判定要重打——**这是可发现性缺陷，不是数据丢失**，
但对用户的结果一样：他重打了。

`'resend'` 这个判断本身没错（没被接纳的回合重发不会重复），它只是**看不见**；而且握手失败这一类
（模型不对、网关死了）恰恰是最需要「改一下再发」而不是「原样重放」的一类。

### ② `session-index.json` 的空壳行

`chat:createSession` 里 `sessionIndexService.recordCreated(...)` 在 `workerManager.createSession(...)` **之前**执行
（`chat.ts:287-303`），失败时没有任何回滚。于是留下 `title=""`、无 `runtimeIdentity` 的一行；重启后
`mergeSessionIndex` 用 `fallbackSessionTitle` 把它显示成「Session xxxxxx」。

（R5 round-2 撤销了「新建即写索引」，所以从未发过消息的对话在索引里是不存在的——那一行确实是这次失败的 create 写下的。）

## 2. 方案取舍

### ①：给「会话从未被创建」这一类一个显式事实，改判 `'restore-draft'`

- **不新造机制**：复用既有的 `restoreDraftIfComposerEmpty`（T045b/F2 §5.3 的那一个，带 provenance、可被晚到事件撤销）
  与既有的错误回程（`lastError` → 红色错误卡）。
- **不全面改判 `'rejected' + 'direct'`**：那会连 `session_busy` 耗尽、resume 失败、`chat.send` 被拒一起改掉，面太大。
  只给 `decideFailureAffordance` 加一个可选的第三参数 `{ sessionNeverCreated }`，由**只有 create 分支能说出口**的事实驱动。
- **只能「搬家」不能「复制」**：新分支只把载荷从 Retry 快照挪进可见草稿，`origin:'release'` 仍返回 `'none'`
  （队列自己持有那条 entry），所以任何情况下载荷都只有一份，不会出现「草稿里一份 + 队列/Retry 里一份」的双发。
- 为什么 Retry 按钮不会变成残影：`runSend` 在提交点就 `setRetryable(null)`，`finalizeOutcome` 不再重新武装，
  `handleRetry` 的 `shouldClearRetryableOnOutcome('rejected')=false` 也只是「不清」而非「保留旧值」——本来就是 null。

**dispatch 异常改在调用点 catch**，而不是留给外层 catch：外层分不清「create 失败」和「ensureHost 失败 / send 被拒」，
而后两者的会话可能是存在的。这与下面 resume 分支已有的 `resumeDispatchError` 写法同形。
用 `try/catch` 而不是 `.catch()` 链：`piModelWiring.test.ts:54` 用
`indexOf('window.electronAPI.chat.createSession({')` 定位载荷，链式写法会被 Biome 折行而让那条兄弟用例失效。

### ②：选「失败时删掉」，不选「推迟到 bootstrap 成功后再写」

推迟**不可行**（读码得出，不是偏好）：

- `WorkerManager.createSession` 在 bootstrap 成功后立刻 `commitIdentityIfMaterialized(entry)` →
  `sessionIndexService.bindRuntimeIdentity`，而后者对**没有索引行**的会话是 `throw`（`SessionIndexService.ts:391`）；
- `applyRuntimeEvent` 对没有行的会话直接 `return`（`SessionIndexService.ts:487-490`，注释原话就是
  「Normal ordering has recordCreated/recordResumed land first」），推迟会让 `session.created` 携带的
  `runtimeIdentity` 被静默丢弃。

所以删除是影响面更小的一种。删除做了两层收窄，以免反向破坏 T038 / T040：

1. **调用层**：只有「这次调用之前索引里没有这一行」才删（`assertPiCompatibleIndexRow` 顺手把它已经读到的行返回，
   不多读一次盘）。已经存在的行（可 resume 的会话、fork 行、归档行）一律不碰。
2. **服务层**：`removeUncommittedCreated(sessionId, workspacePath)` 仿 `removeImported` 的形状，
   只删「仍然正好是这次 create 写下的空壳」——有 `runtimeIdentity` / `piLeaf` / `legacyImport` / `archived` /
   非空 `title` / `workspacePath` 已改，任一条都否决并返回 false。写盘沿用 T038 的 `flush()` + 失败回滚内存。
3. 清理自身失败只 `console.warn`，**绝不覆盖用户正在等的那个 spawn 错误**。

未做（超范围）：失败时顺带 `scratchWorkspaceService.release`（没有索引行认领的 scratch 目录由启动扫描收尾）；
`chat:createSession` 的错误没有像 `chat:send` 那样加 `withWorkerErrorCode` 前缀（不改错误形状）。

# 回炉（R-A，2026-09-17）——修审阅判定的 blocking

## 1. 修了什么

审阅认定的数据丢失路径成立：`'restore-draft'` 只是一条**指令**，不是保证。`restoreDraftIfComposerEmpty`
在输入框非空（或已挂新附件）时按设计静默拒绝——这条拒绝本身是对的，改写用户正在打的字会毁掉别处不存在的东西——
但 D15 同时撤掉了这条路上的 ↺ 武装，于是拒绝之后：草稿没写、`retryable` 是 null、时间线没开、队列里也没有 entry，
文本和附件**在任何 store 里都不存在了**。发送期间输入框不禁用，60 秒 bootstrap 等待里打一个字就复现。

修法按审阅建议：**让恢复返回它到底有没有生效，拒绝时回落到旧的 ↺ 路径**，但回落的判断仍然放在唯一权威里。

| 文件 | 改动 |
|---|---|
| `src/renderer/components/chat/queueRelease.ts` | 新增 `decideDeclinedRestore(outcome, origin, context)`：`'rejected' + sessionNeverCreated + 非 release` → `'resend'`，其余一律 `'none'`。含说明为什么 `'committed'` 必须是 `'none'`（Host 已经把那条用户消息回显进时间线，文本还在屏幕上；在这里武装一键重发就是 A1 刚删掉的双发） |
