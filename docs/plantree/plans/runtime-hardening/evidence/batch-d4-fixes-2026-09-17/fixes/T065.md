## 一、D18（medium）— 两个窗口能同时对同一份会话 JSONL 起 `pi --session`

### 根因

三件事叠加，缺的是「谁也不知道别的窗口在干什么」：

1. `PiTuiExclusiveGuard`（`piTuiSession.ts`）是进程级单例，但它回答的是另一个问题——「有没有终端占着 GUI 即将写的那份文件」，而且 `transferTo()` 是**无条件转移**（pix 的 `tryAcquire` 一旦 key 漂移就会把所有终端永久锁死，注释里写了这段历史）。它从设计上就不会拒绝任何人。
2. 真正持有 PTY 的 `PiTuiPtyController` 是**按 windowId 分的**（`ipc/piTui.ts` 的 `controllers: Map<number, …>`），两个窗口的 `#live` 互相不可见，所以 controller 这一层也拦不住。
3. `writer.lock` 是 GUI worker 的，pi CLI 从不去拿（`piTui.ts` 原注释「the pi CLI never takes the worker's writer lock」）。

结果就是真机实测的形态：两个 pi 各自 open 时读一次树，各自把自己那轮挂在同一个 parentId 上，一份 JSONL 静默分叉成两支，界面全程零提示。

### 方案与取舍

新增一个**按会话文件键、记录归属窗口**的注册表，放在 Main：

- **拒绝，不做只读降级。** 只读降级要么改 pi 的启动方式（pi 没有只读模式），要么在 GUI 侧另做一套只读终端视图——改动面远大于本任务，且「拒绝 + 说清楚在哪个窗口开着」已经让用户能自己解决。
- **新类而不是改 `PiTuiExclusiveGuard`。** 后者的「总是转移」是被事故写进注释的既有决策，改成 test-and-set 会把它修过的 bug 放回来。两个 guard 回答两个不同的问题，各自保留。
- **同一窗口不拦，只拦跨窗口。** 一个窗口里每个聊天有自己的 terminalId，终端死后渲染层会重新铸一个 id；同窗口严格互斥会在这些正常流程上误伤，而同窗口的错配已有 `PI_TUI_SESSION_MISMATCH_REASON`（terminal-03）兜着。
- **释放挂在 `onState` 的 `dead` 事件上**，而不是 `onExit`。写完第一版后自查发现的坑：`#disposeAndConfirm` 与 `#reserveCapacity`（容量淘汰）都会先把条目从 `#live` 摘掉，于是后到的 `pty.onExit` 走的是 early-return，**`callbacks.onExit` 根本不触发**；容量淘汰更是从头到尾没有退出事件。`dead` 状态事件是唯一一条所有停止路径都会经过的缝。
- **额外加了一条 pre-flight**：`piTui.sessionSupport` 现在也会答「这份会话已被别的窗口占着」。它是**咨询性**的（真正的拦截在 open handler 里），存在的意义是让第二个窗口在**切换整个聊天界面之前**就把中文提示弹出来，而不是切过去再让终端起不来。

## 二、D17（medium）— 切回被挂起的 TUI 整屏空白

### 根因

两头各自都对，接缝上没人负责重绘：

- `PiTuiPty.ts` 的 `replayBuffer` 只累积**挂起期间**的输出，而挂起的 pi 空闲不产出，所以 resume 时没有任何字节可回放；
- 渲染层这边 `terminalId` 变化触发 `useXterm.ts:861-897` 的清理 + 重新 `initTerminal()`，新 xterm 实例的回滚缓冲区是空的。

真机上 `piTui.resize(id, 70, 20)` 逼一次重绘即整屏恢复（`dev-14-03-chatB-after-forced-repaint.png`）。

### 方案与取舍

在 resume 路径上发一次 **resize 抖动**（`rows+1` 再回到 `rows`），不发 SIGWINCH：

- **为什么必须抖动而不是「重发一次当前尺寸」**：TTY 只有在窗口尺寸**真的变化**时才会发 SIGWINCH（Linux `tty_do_resize` 先比对旧 winsize）。恢复时 xterm 的尺寸通常和挂起时一模一样，所以原本那句 `#resizeNow(cols, rows)` 在这个场景下是彻底的空操作——这正是缺陷能存在的原因。绕一行再回来保证至少有一次真实变化。
- **为什么不自己发 SIGWINCH**：那需要生产代码里拿真 pid 去 `process.kill`，与工程规范附录 B1（2026-09-14 事故）的方向相反；而且 Windows 没有 SIGWINCH。`resize` 是 node-pty 自己的跨平台 API，也正是真机验证过的那根杠杆。
- **放在回放之后**：先把 `replayBuffer` 冲出去，再要重绘，这样 pi 的整屏重绘是最后落在屏幕上的内容。
- **不加「仅当 replayBuffer 为空」的条件**：pi 是全屏 TUI，重绘用绝对光标定位，多来一次是幂等的；加条件反而多一条只在特定时序下走到的分支。

### 改动文件与行

| 文件 | 位置 | 内容 |
|---|---|---|
| `src/main/services/terminal/PiTuiPty.ts` | `:268-274` | resume 分支末尾调用 `#requestRepaint` |
| 同上 | `:496-516` | 新增 `#requestRepaint()`，注释写明 SIGWINCH 只在尺寸真变时才发、以及为何不自己发信号 |

### 用例

`src/main/services/terminal/__tests__/PiTuiPty.test.ts` 新增 `describe('PiTuiPtyController — a resumed terminal is told to repaint')` 3 条：
- 以**同尺寸**挂起再恢复（即缺陷的精确形态），断言 PTY 收到 `[100,30] → [100,31] → [100,30]`；
- 有回放内容时回放照旧，且最后一次 resize 在回放之后；
- **反向**：首次 spawn 不抖动（`resizes` 为空数组）——新 PTY 本来就按目标尺寸创建并自绘，多一次 reflow 是白费。

### 反向验证

把 `#requestRepaint` 调用摘掉后重跑：`nudges the size off and back so an idle pi redraws its screen` 失败；同时「首次 spawn 不抖动」这条在有无修复时都过，说明它钉的是窄度不是修复本身。

## 一、blocking —— open 失败的回滚是「过度释放」（D18 可复发）

### 根因

`releaseTerminal(windowId, terminalId)` 的语义是**「这个 PTY 死了」**：它遍历该窗口名下每一个会话键，把这个 terminalId 从每个键里摘掉。用它回滚一次「刚记账、open 却失败」的认领，就会连带摘掉**同一个 terminalId 此前已经成立、pi 仍在跑**的那份认领。

触发路径就是既有的 terminal-03：窗口 W 的终端 T 正开着会话 A（键 A={T}），此后同一个 T 收到 `sessionFile=B` 的 open，`#openExclusive` 抛 `PI_TUI_SESSION_MISMATCH_REASON`；此时 claim 已把 T 记进键 B，catch 里的 `releaseTerminal(W,T)` 把键 A 和键 B 一起清空 —— **会话 A 没人认领了，而 A 上的 `pi --session` 还活着**。另一个窗口这时开 A 就会被放行，正是 D18 的原形态。

### 改了什么

| 文件 | 内容 |
|---|---|
| `src/main/services/terminal/piTuiSession.ts` | 新增 `releaseClaim(sessionFile, windowId, terminalId)`：`normalizeSessionKey` 之后**只动这一个键**，且只在归属窗口对得上时才动。`releaseTerminal` 的跨键语义原样保留，继续专供 `dead` 事件 |

## 二、D17 真机未生效 —— 抖动为什么没用，新触发点为什么会用

### 查清的根因（用 DEV-14 / D4 复验证据定位）

先排除任务书列的另外两种可能：

1. **不是「切回不走 resume」**：`T065-tui-events.txt` 的 `states` 数组里，A 的终端在 `1789667762656` 收到 `state:"live"`，pid 与 terminalId 都没变，`piTui.status()` 仍列着它 —— 确实是 resume 分支（`#openExclusive` 的 `current` 命中）。
2. **不是「后面又来一次同尺寸 resize 把画面清掉」**：同尺寸 resize 在 TTY 层是彻底的空操作，而且读数是 `live` 之后**只回流 10 字节** —— 画面不是被清掉的，是**从来没画出来过**。
3. **不是 xterm 没 attach**：`terminal.open(container)` 与 `piTui.onData` 监听都在 `piTui.open` 之前完成（`useXterm.ts` 的 initTerminal 内），而且探针挂的是 IPC 层，Main 真发了字节探针就能看见。

真正的原因在**时序**：`#requestRepaint` 的两次 `resize`（`rows+1` 再回 `rows`）发生在**同一个同步 tick** 里。node-pty 的 resize 是同步 `ioctl(TIOCSWINSZ)`，SIGWINCH 又是不排队的标准信号 —— 子进程被调度起来时，两次 ioctl 早已都执行完，它读到的 winsize 和自己原本持有的**一模一样**。对 pi 来说「净变化为零」和「根本没变」不可区分，于是它只吐了 10 字节（没有重排、没有整屏）。而手工 `piTui.resize(id,70,20)` 是**一次、且留在那里**的真实变化，所以立刻整屏恢复。

一句话：老修法在结构上就没给子进程留下任何可观测的窗口。

### 改了什么（触发点挪到「前端重新 attach 完成之后」）

| 文件 | 内容 |
|---|---|
| `src/main/services/terminal/PiTuiPty.ts` | `#requestRepaint` → `#primeRepaint`：resume 时把 PTY **留在**一个子进程没有的尺寸上（`rows-1`；到了 `boundedDimension` 的 5 行下限则改成 `rows+1`，否则会被夹回原值又成空操作），**不再当场改回去** |
| `src/renderer/hooks/useXterm.ts` | 新增模块级 `confirmPiTuiSize(terminalId, terminal)`，在**两个** `piTui.open` 之后各发一次带真实 `terminal.cols/rows` 的 resize：initTerminal 里第一次 open 之后，以及「重新激活已停泊终端」那个 effect 里（切回聊天真正走的是后者） |

**为什么这次会生效**：现在子进程能观测到的是**两次真实跃迁**（停泊尺寸 → 预置尺寸，预置尺寸 → 真实尺寸），而不是零次；两次之间隔着一整个 IPC 往返（Main→渲染层→Main，毫秒量级），而 SIGWINCH 一到内核就把 pi 置为可运行，调度延迟是微秒到亚毫秒量级 —— 余量有一到三个数量级。而且第二次跃迁是**由渲染层 attach 完成这件事触发的**，所以它引发的整屏重绘不可能早于能显示它的那个 xterm。真机已经证明「一次真实尺寸变化 → pi 整屏重绘」这条因果（70×20 那次），这次只是把它变成必然发生的那一步。

诚实边界：如果 pi 在整个 IPC 往返期间一次都没被调度（2 核满载的极端），它会直接读到最终真实尺寸而错过中间态，行为退化回老样子 —— 这是概率边界，不是逻辑保证，故仍列入真机复验。选 `rows-1` 而不是 `rows+1`：预置期间 pi 画的那一帧比新 xterm 少一行，装得下，不会把顶行滚进回滚缓冲。

### 用例

`PiTuiPty.test.ts` 的 `a resumed terminal is told to repaint` 整组重写（3 → 5 条）：

- **同尺寸挂起再恢复**（缺陷精确形态）：断言 resize 序列是 `[100,30] → [100,29]`，且**结尾不等于 `[100,30]`** —— 老修法恰恰死在这条上；
- 渲染层随后的 `controller.resize('one',100,30)` 让序列收在 `[100,29] → [100,30]`，把「第二次跃迁由前端发起」钉住；
- 行数处在下限 5 时改为向上预置（`[100,6]`），否则会被 clamp 成空操作；
- 有回放内容时回放照旧、重绘在回放之后；
- **反向**：首次 spawn 不预置（`resizes` 为空数组）。

`piTuiSessionBinding.test.ts`（useXterm 的源码扫描测试）新增 3 条：`confirmPiTuiSize` 发的是 `terminal.cols/rows`；它在 `setCurrentSessionId(opened.terminalId)` **之后**；revive effect 里也有一份。

### 反向验证（实跑）

1. 在 `#primeRepaint` 末尾补回一行「改回目标尺寸」（即老修法形态）重跑 `PiTuiPty.test.ts`：4 条红（前四条），而反向那条「does not prime a terminal that was just spawned」照旧过 → 用例钉的是修复本身，不是形状。已还原。
2. 摘掉 revive effect 里的 `confirmPiTuiSize` 重跑 `piTuiSessionBinding.test.ts`：「sends it on the revive too」一条红，其余全过。已还原。

## 六、需要真机复验的点（本轮新增 / 变更）

1. **D17 重做（最关键）**：TUI 模式下 A→B→A、B→A→B 各切一次，期望恢复时**整屏立刻有内容**。另外三件要顺带看：① 预置期间（`rows-1`）那一帧有没有可见的跳行或底部空行闪烁；② pi 的输入框位置在两次重绘后是否正确；③ 用 `window.__dtui` 抓 `state:"live"` 之后的回流字节数 —— 这次应当是**整屏量级（数 KB）而不再是 10 字节**，这是最硬的判据。
2. **D17 的概率边界**：在开发机负载较高时（例如同时跑着构建）重复第 1 条几次，确认没有「偶发仍空白」——若真出现，说明 pi 在整个 IPC 往返期间没被调度，那就要把完成动作改成由「子进程首次回流」自时钟触发。
3. **blocking 修复（terminal-03 路径）**：一个窗口的终端开着会话 A，用 CDP 直接对**同一个 terminalId** 发一次 `piTui.open({sessionFile: B})` 让它被拒；随后从第二个窗口开 A，**应当仍被拒绝**，且 `/proc` 里只有一个 `pi --session A`。
4. **拒绝 toast**：第二个窗口进来就处在 TUI 模式时点「Start Pi TUI」，应弹中文 toast（「Pi 终端无法打开这个对话 / 该会话已在另一个窗口的终端中打开…」）而不是毫无反应；顺便确认另外两条新补中文的拒绝（终端已在跑别的对话 / 本轮未跑完）出现时也是中文。
