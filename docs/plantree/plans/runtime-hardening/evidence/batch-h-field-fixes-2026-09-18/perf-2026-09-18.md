# 性能实测：Q021 端到端确认 + 「输出慢」根因重测（2026-09-18 下半场）

Role: evidence。回应 [open-questions.md](../../open-questions.md) 的 Q021（中转是否把 `cache_control` 的 `ttl:'1h'` 原样透传给上游），并核验批次 H 立项时对现场反馈 #8「输出慢」的根因判断——[决策 024](../../decisions/024-prompt-cache-ttl-split.md)「理由」一节与 [07-findings.md](../../topics/t033-field-day/07-findings.md) 现象 #8——是否成立。

**结论（两条）**：

1. **Q021 完全结案**：真实请求端到端确认中转如实透传 `ttl:'1h'`，且上游确实按 1 小时处理。
2. **「输出慢的主因是 5 分钟缓存 TTL」这一判断被推翻**：缓存对首字延迟的贡献只值约 2.3 秒，量级远小于现场观测到的「首字 6.8s → 29～51s」那个落差；真正的大头是思考（extended thinking）token 量。[决策 024](../../decisions/024-prompt-cache-ttl-split.md) 把主对话默认设为 1 小时**依然正确**（省成本、省这 2.3 秒、避免短停顿后的重复全量写入），但不再是「解决输出慢」的方案，该决策的「理由」一节已追加注记更正。

本文数据全部来自 2026-09-18 当天的真实请求：公司渠道 `claude/claude-sonnet-5`，经 `cch-jyw` 中转；系统提示词 16,918 字节。

## 一、Q021：缓存 TTL 端到端确认

在此之前已排除的两个假设（详见 [open-questions.md](../../open-questions.md) Q021 历史记录与[批次 H 证据](README.md)）：① 应用确实发出 `ttl:"1h"`——开发机 CDP 点验抓到真实请求体，主对话三处缓存标记都带 `ttl`、子代理不带（见 [pointcheck/README.md](pointcheck/README.md) 「T077 缓存 TTL 上线」一节）；② 此前「`cacheWrite1h` 恒为 0」的证据基础是误读——那三份观测采集于 2026-09-17，早于 T077 把主对话切到 1h 档（2026-09-18 08:09 提交）一整天，采集时主对话本来就是 5 分钟档，读数为 0 是正确的，不构成「中转吞参数」的证据。

本轮新增的第三层证据，把「中转是否透传」与「上游是否真的按 1h 处理」一并证实：

| 证据 | 内容 |
|---|---|
| ① 真实请求的 `cacheWrite1h` | 第一轮 `usage.cacheWrite1h = 10742`，全部写进 1 小时档（不是 5 分钟档） |
| ② 间隔之后的缓存命中 | 第二轮与第一轮间隔 **13.5 分钟**——5 分钟档此时必然早已过期——命中的是 `cacheRead = 10742`，与第一轮写入量一致，证明生效的是 1 小时档而非 5 分钟档 |
| ③ 中转平台侧独立确认 | 用户在中转平台后台查询，独立确认「缓存确实是 1h」 |
| ④ 平台记录字段的含义 | 平台的请求记录形如 `{"type":"anthropic_cache_ttl_header_override","scope":"request_header","hit":true,"ttl":"5m"}`（示意格式）；平台明确说明 `cache_control` 完全跟随客户端下发值，记录只是展示、不是平台自己决定的——客户端发 `5m` 就显示 `5m`，发 `1h` 就显示 `1h` |

应用发出 → 中转透传 → 上游按 1h 处理并可被我们的计数器读到，三层证据现在全部闭环。**Q021 结案**，已在 [open-questions.md](../../open-questions.md) 标记。

## 二、「输出慢」根因重测（现场反馈 #8）

批次 H 立项时的判断：5 分钟缓存过期是「输出变慢」的主因（依据是对 `contextFX/session-1789701613704-i5jfwqz.jsonl` 的分桶分析，缓存未命中时首字前 29～51 秒、命中时中位数 6.8 秒，见 [07-findings.md](../../topics/t033-field-day/07-findings.md)「性能深挖」节）。2026-09-18 用六组对照重新测量，结论相反。

| 配置 | 思考 token | 首字前 | 总时长 |
|---|---|---|---|
| 我们的 runtime，缓存冷 | 537 | — | 28.2s |
| 我们的 runtime，缓存全命中 | 522 | — | 25.9s |
| 裸调用（绕开全部应用代码，思考开，无工具） | 976 | 25.0s | 30.7s |
| 裸调用（思考开，带 14 个工具定义） | 1,063 | 29.0s | 33.2s |
| 裸调用（思考关闭） | 0 | 6.9s | 11.3s |
| 用户的 Claude CLI（同模型同档位） | 未知 | 12.25s | 16.95s |

「裸调用」= 绕开本应用全部 runtime 代码，直接用同一模型、同一渠道发 HTTP 请求，用来把「应用自身代码」这个变量从「模型 / 网络本身」里剥离出来；「首字前」一栏里我们的 runtime 两行标 `—` 是因为这两次测量口径只取了总时长，未单独记录首字时刻。

### 结论

1. **缓存只值 2.3 秒。** 冷缓存 28.2s → 全命中 25.9s，只省 2.3 秒。这与现场观测到的「首字 6.8s → 29～51s」不是同一个量级，2.3 秒不可能是那个落差的成因。[决策 024](../../decisions/024-prompt-cache-ttl-split.md) 主对话默认 1 小时**依然正确**——省成本、省这 2.3 秒、避免短停顿后的重复全量写入——但它不是「输出慢」的解药，该决策「理由」一节的表述已追加注记更正（见本文第四节）。
2. **真正的大头是思考时间。** 关闭思考后总时长从 30.7s 降到 11.3s（降 64%），首字从 25.0s 降到 6.9s（几乎等于收到响应头的时刻）。三组裸调用数据的思考 token 量（976 / 1,063 / 0）与首字、总时长完全单调对应：思考 token 越多越慢。
3. **应用自身的代码不是瓶颈。** 绕开全部 runtime 代码的裸调用（30.7s / 33.2s）反而比走应用（25.9s）慢 5～7 秒。此前怀疑的「内部 loop 或解析环节有大问题」，在这组对照里不成立。
4. **中转固定开销约 7～8 秒。** 裸调用冷启动到收到响应头要 8.4 秒，缓存命中时压到 6.9 秒；应用侧一次极短输出（4 token）的那一轮延迟 5.9 秒，量级一致，指向这是中转本身的固定开销，与应用代码无关。
5. **14 个工具定义有代价，但不是主因。** 带 14 个工具定义比不带多花 3,664 token 缓存写入、首字多约 4 秒（25.0s→29.0s）、思考多 87 token（976→1,063）。
